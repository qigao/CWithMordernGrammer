# Chapter 3: From Function Pointers to Function Semantics — FunctionDesc, Callable, Lambda, and Bind

> **This chapter makes one distinction:**
>
> describing what a C function is and deciding how to execute it are different problems.

---

## 1. Plain C Baseline: Function Pointers Are Already Fast

An ordinary callback is enough for a direct call:

~~~c
typedef long (*map_fn)(int x);

long square(int x)
{
    return (long)x * x;
}

map_fn fn = square;
long y = fn(7);
~~~

If a call site only needs to store and invoke one function address, stop here.

The limitation appears only when several systems need semantic information that a function pointer does not carry: parameter direction, ownership, effects, properties, or stable function identity.

---

## 2. FunctionDesc Describes What the Native Function Is

Consider:

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

A descriptive object may look like:

~~~c
typedef struct cmeta_param_desc {
    const char *name;
    const cmeta_type_desc *type;
    uint32_t flags; /* IN / OUT / INOUT / ownership */
} cmeta_param_desc;

typedef struct cmeta_function_desc {
    const char *name;
    const cmeta_type_desc *return_type;

    const cmeta_param_desc *params;
    size_t param_count;

    uint32_t effects;
    uint32_t properties;
} cmeta_function_desc;
~~~

It answers:

| FunctionDesc fact | Example |
|---|---|
| identity | get_user |
| return type | int |
| parameters | repo / id / out_user |
| direction | IN / OUT |
| ownership/nullability | where admitted |
| effects/properties | metadata claims |

FunctionDesc is **native semantic truth**, not a universal invocation object.

---

## 3. Signature: Executable Shapes Must Be Finite and Checkable

CFlow does not need to support every possible C ABI shape.

It can admit a finite signature universe such as:

~~~text
int -> bool
int -> long
(long, int) -> long
~~~

Each supported shape can have a stable signature id:

~~~c
typedef enum cmeta_signature_id {
    CMETA_SIG_INT_TO_BOOL,
    CMETA_SIG_INT_TO_LONG,
    CMETA_SIG_LONG_INT_TO_LONG
} cmeta_signature_id;
~~~

Admission becomes explicit:

~~~text
FunctionDesc
    ↓ validate native shape
Signature admitted?
    ├─ no  -> UNSUPPORTED
    └─ yes -> executable projection allowed
~~~

A finite universe lets dispatch, adapters, formal models, and AOT lowering share the same execution shapes.

---

## 4. FunctionDesc Does Not Own Universal Dynamic Invocation

Once parameter metadata exists, it is tempting to design:

~~~c
invoke(desc, values, count);
~~~

for every C function.

Real C ABI still includes calling convention, struct return, alignment, variadics, pointer ownership, and platform differences.

Keep the boundary explicit:

| Object | Responsibility |
|---|---|
| FunctionDesc | description |
| exact adapter | execution |
| Callable | admitted executable representation |

A compiler can generate an exact adapter:

~~~c
static int
invoke_get_user(
    void *ctx,
    const GetUserRequest *request,
    GetUserResponse *response)
{
    UserRepository *repo = ctx;

    return get_user(
        repo,
        request->id,
        &response->user);
}
~~~

Execution still ends in an ordinary C call.

---

## 5. Callable Stores Only What Execution Needs

A conceptual representation is:

~~~c
typedef struct cmeta_callable {
    cmeta_signature_id signature;

    cmeta_callable_invoke_fn invoke;
    const void *raw_target;

    uint32_t effects;
    uint32_t properties;

    uint8_t capture[CMETA_CAPTURE_INLINE];
    uint16_t capture_size;
} cmeta_callable;
~~~

The fields answer different questions:

| Field | Role |
|---|---|
| signature | type/execution shape |
| invoke/raw_target | dispatch authority |
| capture | environment |
| effects | observable-behavior constraints |
| properties | semantic claims for admission/optimization |

Callable is not a mandatory layer for every C function.

Use it only when behavior must be stored, composed, executed through Graph, or projected across a boundary.

---

## 6. Lambda and Bind Mean Code + Capture + Lifetime

Traditional C callbacks often use:

~~~c
typedef void (*callback_fn)(void *user);
~~~

The difficult part is the lifetime of user context, not the function address.

A finite Lambda can store capture inline:

~~~c
typedef struct multiply_capture {
    int factor;
} multiply_capture;

static long
multiply_invoke(const void *capture, int x)
{
    const multiply_capture *c = capture;
    return (long)c->factor * x;
}
~~~

A builder can copy:

~~~c
multiply_capture cap = {
    .factor = 10
};
~~~

into bounded Callable storage.

Bind is the same idea applied to one argument. The arrow denotes a **partial-application transformation**, not a nested runtime call:

~~~text
multiply(a, b)
    + bind b = 10
    ↓ produce unary callable
callable(a) = multiply(a, 10)
~~~

The point is explicit code, capture, copy/destroy, and lifetime—not C++-like surface syntax.

---

## 7. Inline Capture Must Be Bounded

An explicit anti-pattern is:

~~~text
capture too large
    ↓ hidden allocation
secret malloc
    ↓ semantic contract unchanged on surface
API still reports ordinary value semantics
~~~

The problem is not “the next step happened”; it is that the implementation silently changed the allocation/lifetime contract.

A clearer contract is:

~~~text
capture_size <= inline_capacity
    -> OK

capture_size > inline_capacity
    -> TOO_LARGE / explicit heap-backed path
~~~

That keeps ordinary Callable semantics predictable:

- no hidden allocation;
- known object-size bound;
- explicit copy/destroy;
- predictable ABI/lifetime.

If heap-backed capture is needed, make it a different explicit owner/type.

---

## 8. Effects and Properties Are Different

Effects describe observable behavior such as IO, STATEFUL, or MAY_FAIL.

Properties describe stronger semantic claims such as DETERMINISTIC, IDEMPOTENT, ASSOCIATIVE, TOTAL, or NO_ALIAS.

Both are metadata first.

Seeing an ASSOCIATIVE bit does not prove arbitrary reassociation is valid.

A semantic law must authorize the rewrite.

---

## 9. Property Claim and Theorem Have Different Roles

For idempotence, metadata may say:

~~~c
callable.properties |= CMETA_PROP_IDEMPOTENT;
~~~

The real law is:

~~~text
∀x, f(f(x)) = f(x)
~~~

Only the law can authorize:

~~~text
Map(f); Map(f)
    ~>
Map(f)
~~~

The evidence layers are distinct:

| Layer | Role |
|---|---|
| property bit | candidate / admission claim |
| theorem | rewrite authority |
| trace/certificate | concrete rewrite evidence |

Lean does not prove that arbitrary machine code tagged IDEMPOTENT is actually idempotent.

It proves that **if the premise holds, the transformation preserves semantics**.

---

## 10. Callable Must Pass Admission Before Entering Graph

The complete path is an **admission/projection pipeline**, not the runtime stack of every invocation:

~~~text
FunctionDesc
    ↓ validate native compatibility
admitted signature
    ↓ generate/select exact execution adapter
Callable
    ↓ admit composable behavior
CFlow Graph
~~~

Composition first checks the type relation:

~~~text
f : A -> B
g : B -> C
────────────────
g ∘ f : A -> C
~~~

If the second function expects X instead of B, then **B != X ⇒ construction/admission fails**. This is a type-rule implication, not runtime control flow. The runtime does not guess with void pointers.

---

## 11. Function Capability and Interface Capability Are Different Shapes

A request-response operation naturally fits FunctionDesc + exact adapter.

A long-lived provider such as Executor naturally fits:

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

Both may enter the same Plugin runtime, but they are different semantic representations:

| Capability | Representation |
|---|---|
| Service / function | FunctionDesc + exact adapter |
| Provider / interface | InterfaceDesc + {self,vtable} |

Do not turn every function into a vtable, and do not flatten every provider into unrelated FunctionDesc exports.

---

## 12. Engineering Evidence

### Signature Admission

Unsupported ABI shape maps explicitly to **unknown signature ⇒ UNSUPPORTED**.

### Capture Boundary

Test the inline-capacity boundary directly:

| Capture size | Result |
|---|---|
| N bytes | accepted |
| N + 1 bytes | TOO_LARGE |

### Multi-TU Identity

Different Translation Units may hold different descriptor/adapter representations, while semantic function identity follows the authoritative representation rather than blind pointer equality.

### Performance

Compare at least:

- direct ordinary C call;
- typed wrapper;
- adapter/erased callable;
- capturing callable.

Do not replace measurement with the adjective “zero-cost.”

## 13. Canonical Example: Three Callables Ready for Graph

Later chapters reuse:

~~~c
bool is_even(int x)
{
    return (x & 1) == 0;
}

long square(int x)
{
    return (long)x * x;
}

long sum(long acc, long x)
{
    return acc + x;
}
~~~

Their shapes are:

~~~text
is_even : int -> bool
square  : int -> long
sum     : (long, long) -> long
~~~

The next chapter stops asking how to call one function and asks:

> **when relationships between typed behaviors also matter, how do we preserve them as Graph?**

---

## 14. What We Learned

This chapter established four boundaries:

1. FunctionDesc describes the native function.
2. exact adapter / Callable provides admitted execution.
3. capture/lifetime must be explicit and bounded.
4. property metadata cannot replace semantic proof.

DataBind, TinyMock, Plugin, and CFlow can therefore share one native function semantic source instead of inventing separate function-description systems.
