# Chapter 1: Where CMeta Begins — The Pain of Writing C Macros

> **Chapter path**
>
> This chapter deliberately starts with ordinary C, not with “how to write advanced macros.” We keep a Plain C baseline, then watch repeated code evolve into repeated facts. Only when repetition has stabilized into knowledge do we introduce macros, shared schemas, and type descriptions.
>
> The chapter follows the method used throughout the book:
>
> ~~~text
> Problem
>   → Plain C Baseline
>   → Minimal Macro Reuse
>   → Reusable Facts
>   → Type-aware Description
>   → Semantic Boundary
>   → Evidence
> ~~~
>
> Lean is not forced into this stage. The most important principle here is: **formalization should appear only when there is a real semantic question to answer.**

C is a very direct language.

A function is a function. A structure is a concrete memory layout. A function pointer is an address. What the compiler does is comparatively transparent, and the generated program is usually easy to relate to the machine behavior that follows.

That simplicity is one reason C has remained important in systems software, foundational libraries, embedded software, and performance-sensitive code.

But simplicity has another side.

As a program grows, a surprising amount of code is not repeated because the algorithms are difficult. It is repeated because:

> **the same pattern has to be written again for different types, structures, and functions.**

Suppose a library supports:

```c
int
long
float
double
```

and every type needs:

```text
compare
hash
copy
destroy
format
```

Very quickly, we get families of functions that have almost identical structure.

For example:

```c
int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}

int long_compare(const long *a, const long *b)
{
    return (*a > *b) - (*a < *b);
}

int float_compare(const float *a, const float *b)
{
    return (*a > *b) - (*a < *b);
}
```

None of this code is hard to write.

The real problem is maintenance.

If the comparison rule changes, several functions must change together. If a new type is added, the whole family is copied again. If one version is not updated, the project may still compile while the semantics quietly diverge.

So a very natural reaction in C is:

> If all these functions have the same structure, why not write a macro?

## 1. The First Macro Is Usually a Great Success

The comparison family can immediately become:

```c
#define DEFINE_COMPARE(T, name)            \
    int name##_compare(                    \
        const T *a, const T *b)            \
    {                                      \
        return (*a > *b) - (*a < *b);      \
    }

DEFINE_COMPARE(int, int)
DEFINE_COMPARE(long, long)
DEFINE_COMPARE(float, float)
```

A large amount of duplicated code disappears at once.

That is one of the most attractive properties of the C preprocessor.

It does not add a runtime.

It does not require a separate code generator.

It does not require a virtual machine or reflection system.

After preprocessing, the compiler still sees ordinary C:

```text
Macro
   ↓
Preprocess
   ↓
Ordinary C
   ↓
Compiler
   ↓
Machine Code
```

For a low-level library that wants a simple build and low runtime overhead, this is extremely useful.

The next steps are obvious:

```text
compare can be a macro
hash can be a macro
copy can be a macro
destroy can be a macro
```

It looks as if the problem has been solved.

The real difficulty has only begun.

---

## 2. Macros Remove Code Duplication, Then Macro Calls Start Duplicating

Suppose we now have:

```c
DEFINE_COMPARE(...)
DEFINE_HASH(...)
DEFINE_COPY(...)
DEFINE_DESTROY(...)
```

The code might become:

```c
DEFINE_COMPARE(int, int)
DEFINE_COMPARE(long, long)
DEFINE_COMPARE(float, float)

DEFINE_HASH(int, int)
DEFINE_HASH(long, long)
DEFINE_HASH(float, float)

DEFINE_COPY(int, int)
DEFINE_COPY(long, long)
DEFINE_COPY(float, float)
```

The function bodies are no longer duplicated.

But this information:

```text
int
long
float
```

is duplicated again and again.

The first abstraction solved:

```text
duplicated code
```

and immediately exposed a second problem:

```text
duplicated facts
```

The program really wants to say only once:

> I support the types `int`, `long`, and `float`.

So another natural step is:

```c
#define TYPES(X)       \
    X(int, int)        \
    X(long, long)      \
    X(float, float)
```

and then:

```c
TYPES(DEFINE_COMPARE)
TYPES(DEFINE_HASH)
TYPES(DEFINE_COPY)
```

This still looks like an ordinary X-Macro technique, but an important change has happened.

Originally the macro reused:

```text
code templates
```

Now it is reusing:

```text
data
```

namely:

```text
which types exist
```

The macro is no longer just source replacement.

It has started to act as a very small:

```text
compile-time description
```

---

## 3. From Reusing Code to Reusing Facts

Once this style appears, it quickly spreads.

For an enum:

```c
#define STATES(X)             \
    X(READY,   "ready")       \
    X(RUNNING, "running")     \
    X(DONE,    "done")
```

The same facts can generate:

```text
enum
strings
parse tables
debug output
```

Structure fields can be handled similarly:

```c
#define USER_FIELDS(X) \
    X(int, id)         \
    X(double, score)
```

and can generate:

```text
field declaration
field name
offset
size
serialization mapping
```

Function signatures can also be kept as facts:

```text
input type
output type
function name
```

Soon a project contains more and more things like:

```text
TYPE_LIST
FIELD_LIST
ENUM_LIST
FUNCTION_LIST
SIGNATURE_LIST
```

They look different, but they begin to share one shape:

```text
a finite set of records
        ↓
consumed by different macros
        ↓
different generated results
```

The role of the macro is changing.

It is no longer merely:

> copy this piece of text into several places.

It is becoming:

> **describe a fact once, then generate program artifacts from that fact.**

---

## 4. The C Preprocessor Was Not Designed for This

The problem is that the C preprocessor was not originally designed for this kind of structured work.

It is excellent at:

```c
#define BUFFER_SIZE 1024
```

or:

```c
#define MAX(a, b) ...
```

But as soon as we build reusable macro infrastructure, we repeatedly encounter unnatural rules.

Token concatenation is a classic example.

It looks as if this should be enough:

```c
#define CAT(a, b) a##b
```

Suppose:

```c
#define TYPE int
```

and then:

```c
CAT(TYPE, _value)
```

Without understanding argument-expansion rules, the result can differ from intuition.

So we often add another layer:

```c
#define CAT_I(a, b) a##b
#define CAT(a, b) CAT_I(a, b)
```

just to:

> **expand the arguments first, then concatenate them.**

Something that would barely be a concern in an ordinary language already requires special knowledge of expansion order in the preprocessor.

---

## 5. A Comma Can Even Change What a “Type” Means

Another classic problem is macro arguments.

This is straightforward:

```c
MACRO(int)
```

But if we pass an expression or type description containing a comma:

```text
(A, B)
```

the preprocessor naturally interprets it as:

```text
two arguments
```

rather than:

```text
one structure
```

So we start needing:

```text
parentheses
tuple
UNPAREN
```

For example:

```c
#define UNPAREN(...) __VA_ARGS__
```

Then another problem appears:

> How do we know whether the input is parenthesized?

So we introduce things such as:

```text
PROBE
IS_PROBE
IS_PAREN
SECOND
```

At this point the evolution is revealing.

We started with:

> write fewer duplicate functions.

Now we are studying:

> **how to recognize the structure of a token sequence during preprocessing.**

---

## 6. Even `for each` Has to Be Invented

With:

```c
#define TYPES(X) \
    X(int)       \
    X(long)      \
    X(float)
```

iteration is still direct.

But if the data comes from variadic arguments:

```c
FOR_EACH(M,
    int,
    long,
    float,
    double)
```

the C preprocessor has no real:

```text
for
foreach
iterator
```

So we have to build one.

A typical approach is:

```c
#define FOR_EACH_1(...)
#define FOR_EACH_2(...)
#define FOR_EACH_3(...)
#define FOR_EACH_4(...)
```

Then we add:

```text
NARG
```

to count arguments.

Then:

```text
CAT(FOR_EACH_, N)
```

to select:

```text
FOR_EACH_4
```

A very ordinary requirement:

> apply the same operation to four values.

has now involved:

```text
variadic arguments
argument counting
token concatenation
dispatch
expansion ordering
```

The question is no longer:

> Can this be implemented?

Most of the time, it can.

The important question becomes:

> **Has the complexity become too high for such an ordinary form of reuse?**

---

## 7. Nested Macros Are Even Harder

After `FOR_EACH` works, a new need appears quickly:

```text
FOR_EACH
    ↓
another FOR_EACH inside it
```

For example:

```text
iterate input types
    ↓
for each input type, iterate output types
```

Intuitively, this is just a nested loop.

But the C preprocessor has a special rule:

> while a macro is expanding, that same macro is temporarily disabled from expanding again.

So:

```text
FOR_EACH(FOR_EACH(...))
```

does not necessarily behave like ordinary recursion or nested function calls.

A practical workaround is to prepare different expansion families:

```text
FOR_EACH_A
FOR_EACH_B
FOR_EACH_C
```

The outer layer uses A, the inner layer B, and the next layer C.

This is not elegant, but it is deterministic and tends to be easier to make portable across compilers.

That leads to an important conclusion:

> **Instead of trying to turn the preprocessor into a universal language, accept its limits and build reliable tools inside explicit boundaries.**

---

## 8. The Most Painful Part of Macros Is Often Failure, Not Writing Them

Complex macros have a problem even larger than syntax:

```text
error messages
```

In ordinary C:

```c
int x = "hello";
```

the compiler can usually point directly to the type error.

But when a complex macro fails, the source mistake may be:

```c
Traits(User,
    (equal, user_equal),
    (hash, user_hash)
);
```

while the compiler reports something like:

```text
expected ')' before ...
```

or:

```text
unknown identifier ...
```

The real expansion path may already be:

```text
input declaration
   ↓
row unpack
   ↓
foreach
   ↓
tag dispatch
   ↓
token concat
   ↓
generated declaration
   ↓
C compiler error
```

In other words:

> **the user made the mistake at layer one, while the compiler sees the failure at layer six.**

The more complex a macro system becomes, the more another design requirement matters:

> Do not ask only whether a macro can work. Ask whether its failures remain understandable.

---

## 9. The Largest Limitation Is Not Any of These: Macros Have No Types

The previous issues are inconvenient, but they can all be worked around.

The real limitation is more fundamental:

> **the preprocessor does not know what a type is.**

To the C compiler:

```c
int
double
User
```

are distinct types.

To the preprocessor they are simply:

```text
token
token
token
```

It does not know:

```text
int is an integer
double is floating-point
User is a structure
```

It knows nothing about:

```text
sizeof(T)
alignment
copy semantics
destroy semantics
hashability
comparability
```

It does not know that:

```text
int -> double
```

is a function signature.

It does not know that:

```text
Vec<int>
```

means a generic type parameterized by `int`.

So with plain macros, much “type processing” is actually an emulation such as:

```text
INT
DOUBLE
USER
```

followed by manually maintained mappings:

```text
INT -> int
INT -> integer
INT -> descriptor
INT -> hash
INT -> compare
```

That brings us straight back to the original problem:

> **the same fact has been written several times again.**

---

## 10. C11 `_Generic` Opens a Door

C11 introduced a very important mechanism:

```c
_Generic
```

It is nowhere near a C++ template system, but it provides finite:

```text
type-directed selection
```

Conceptually:

```c
_Generic((value),
    int:    handle_int,
    double: handle_double)
```

If we already have a:

```text
finite list of types
```

then that list can potentially generate:

```text
type selection
descriptor lookup
callback signature
```

For the first time:

```text
macros
```

can be connected to:

```text
the C compiler's type system
```

That is a major shift.

---

## 11. Once Types Enter, Many Problems Become Structured

Suppose a type can describe not only:

```text
name
```

but also:

```text
size
alignment
kind
traits
identity
```

Then many things that previously depended on naming conventions become actual type relations.

For example:

```text
HashMap<K,V>
```

can require:

```text
K supports hash
K supports equal
```

An ordered structure can require:

```text
K supports compare
```

A function can have:

```text
input type
output type
```

rather than being only an address.

The system starts to evolve from:

```text
text generation
```

toward:

```text
type-aware generation
```

This was not the original plan.

It is simply the natural result of repeatedly trying to remove duplicated facts.

---

## 12. What the First Stage Actually Teaches Us

Looking back, every abstraction appeared because the previous layer exposed another kind of repetition, not because we wanted new syntax.

```text
duplicated code
    ↓
parameterized macros

duplicated macro calls
    ↓
shared lists

duplicated list-consumption patterns
    ↓
generic foreach / repeat

duplicated row representation
    ↓
unified schema

duplicated type knowledge
    ↓
typed description
```

The whole progression is:

```text
C code
  ↓
Macro reuse
  ↓
Macro data
  ↓
Structured rows
  ↓
Reusable preprocessor primitives
  ↓
Type-aware description
```

The driving question was never:

```text
"What other clever macro tricks can we build?"
```

It was:

> **How can we maintain one less duplicate copy of the same knowledge?**

---

## 13. A Principle That Never Changes Later

After these problems, one principle becomes clear:

> **A macro is not better because it is more powerful. It is better when minimal complexity can collapse repeated structure into one authoritative source of facts.**

That is why the later design consistently prefers:

```text
finite
explicit
bounded
predictable
```

instead of:

```text
unbounded recursion
universal template language
macro interpreter
```

The original reason for using macros was to:

```text
reduce complexity
```

If the result is a system more complicated and harder to debug than C itself, the original purpose has been lost.

---

## 14. The Next Step: When Macros Start to Know About Types

At this point we have two important foundations.

First, we know how to make:

```text
a set of facts
```

usable by several pieces of code.

Second, we have started to connect:

```text
C type
```

with:

```text
compile-time description
```

The next question follows naturally:

> **If we can describe types, can macros generate different code based on type?**

Then:

> Can we describe a Generic?

And then:

> Can several known types derive a new type?

The progression becomes:

```text
Reuse
```

to:

```text
Generate
```

and then:

```text
Derive
```

This is where scattered macro practice begins to turn into a real typed metaprogramming model.

## 15. Semantic Contract: What This Chapter Actually Establishes

At this point we have not created a new runtime, nor a new “template language.”

The chapter establishes a few deliberately small semantic promises that will be reused throughout the book.

### 15.1 After Preprocessing, It Is Still Ordinary C

Execution semantics do not change at this layer:

~~~text
facts / schema
      ↓
preprocessor
      ↓
ordinary C declarations / definitions
      ↓
ordinary C compiler
~~~

The macro layer can reduce duplicated knowledge, but it should not secretly own:

~~~text
object runtime
dynamic dispatcher
reflection VM
hidden scheduler
automatic ownership system
~~~

If an abstraction requires those things, it belongs to a later layer rather than to Macro Reuse.

### 15.2 A Fact Should Have One Authoritative Source

When we write:

~~~text
int
long
float
~~~

what we really want to say is:

> “The system currently supports these types.”

Compare, hash, copy, and destroy are merely consumers of those facts.

So the most important contract in this chapter is not the name of a macro. It is:

> **stable knowledge should not be copied by hand into several places.**

### 15.3 Generation Must Remain Finite, Explicit, and Checkable

This chapter does not try to build an infinitely recursive preprocessor language.

We accept a smaller goal:

~~~text
finite
explicit
bounded
predictable
~~~

That means:

- supported schemas are finite;
- expansion rules are explicit;
- the generated C can be inspected by the compiler;
- failures should occur as close as possible to the generation site;
- universality is not worth sacrificing debuggability.

These constraints become core CMeta design rules later.

## 16. What Lean Should — and Should Not — Do in Chapter 1

This chapter introduces an important methodological rule:

> **not every correctness problem belongs in Lean.**

At this stage the main questions are:

- does the preprocessor expand as intended?
- does the compiler accept the generated C?
- do different compilers behave consistently?
- do generated symbols match expectations?
- does the macro layer actually remove duplicated knowledge?

These are primarily toolchain and engineering-evidence questions.

We do not need a theorem merely to prove that:

~~~text
DEFINE_COMPARE(int)
~~~

will be preprocessed correctly by a specific compiler.

That is not the most valuable proof obligation here.

Lean becomes genuinely useful when later chapters introduce semantic questions such as:

~~~text
Given a finite set of types,
is a type mapping unique?

Given several input types,
is a derivation rule total / deterministic?

If two descriptors live in different Translation Units,
how do they denote the same semantic type?
~~~

In other words:

~~~text
Macro problem
    ↓
engineering evidence

Type relation
    ↓
semantic model
    ↓
Lean
~~~

This distinction matters.

**Lean is neither decoration nor a replacement for tests.**

## 17. Implementation Evidence: How Do We Know This Layer Did Not Become Heavy?

If this chapter describes a real Modern C engineering method rather than a bag of macro tricks, it should have concrete evidence.

### 17.1 Preprocess Evidence

For important macros, inspect the preprocessed result:

~~~text
macro/schema input
      ↓
compiler -E
      ↓
ordinary C
~~~

The reader should be able to verify that the output is still C they would be willing to write and maintain manually.

### 17.2 Compile-Pass / Compile-Fail

Test both:

~~~text
valid schema
    → compile

invalid schema / unsupported type
    → fail close to the declaration site
~~~

A professional typed C API is not only capable when usage is correct. It also makes errors happen early.

### 17.3 Cross-Compiler Evidence

The preprocessor is one of the easiest places in C to encounter compiler-specific corner cases.

At minimum, pay attention to:

~~~text
GCC
Clang
MSVC / compatible preprocessing mode
~~~

The goal is not to prove that every compiler is identical. It is to make explicit:

> which syntax belongs to the actual contract we rely on.

### 17.4 Runtime Evidence

The ideal result for this chapter is simple:

> **there is no new runtime cost center.**

If two versions ultimately generate the same or equivalent ordinary C functions, then the value of Macro Reuse lies in the build/control plane, not in the hot path.

This is the first appearance of an idea that will recur throughout the book:

> **Know more before execution, do less during execution.**

---

## 18. What We Learned

The lesson of Chapter 1 is not that macros can become extremely complicated.

It is almost the opposite.

We learned:

~~~text
Plain C
   ↓
observe stable repetition
   ↓
reuse code
   ↓
reuse facts
   ↓
make facts structured
   ↓
attach type knowledge
~~~

and a set of principles that will not change later:

1. **Plain C first**: do not abstract before real repetition exists.
2. **Code first, Meta later**: abstract stable knowledge, not accidental similarity.
3. **Single source of truth**: maintain each fact once.
4. **Finite / explicit / bounded**: do not turn the preprocessor into a second language.
5. **No hidden runtime**: the macro layer still ends as ordinary C.
6. **Use the right evidence**: compiler/test evidence for toolchain questions; Lean only for semantic laws.

The next question follows naturally:

> **When our “facts” begin to include type relations, how do we move from text reuse to typed computation?**

The next chapter continues from there: **how macros evolve from text reuse into Types, Traits, Generic, and finite type derivation.**
