# Chapter 1: Where CMeta Begins — The Pain of Writing C Macros

> **Chapter path**
>
> This chapter deliberately starts with ordinary C instead of “how to write advanced macros.” We keep a Plain C baseline, then watch duplicated code turn into duplicated facts. Only after repetition becomes stable knowledge do we introduce macros, shared schemas, and type-aware descriptions.
>
> The chapter follows the method used throughout the book:
>
> ~~~text
> Problem
>   → Plain C Baseline
>   → Minimal Macro Reuse
>   → Reusable Facts
>   → Type-aware Description
>   → Semantic Boundary
>   → Evidence
> ~~~
>
> Lean is not forced into this chapter. The first principle to establish is simple: **formalization should appear only when there is a real semantic question to answer.**

C is a very direct language.

A function is a function. A struct has an explicit memory layout. A function pointer is an address. The compiler is relatively transparent, and the generated program maps cleanly to the machine behavior we expect.

That simplicity is one reason C has remained important in systems software, foundational libraries, embedded systems, and performance-sensitive programs.

But the same simplicity has another side.

As a program grows, a surprising amount of code is repeated not because the algorithms are difficult, but because:

> **the same pattern has to be written again for different types, structures, and functions.**

Suppose a library supports:

~~~c
int
long
float
double
~~~

and each type needs:

~~~text
compare
hash
copy
destroy
format
~~~

Very quickly, we get many functions with almost identical structure.

For example:

~~~c
int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}

int long_compare(const long *a, const long *b)
{
    return (*a > *b) - (*a < *b);
}

int float_compare(const float *a, const float *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

None of this code is hard to write.

The real cost is maintenance.

If the comparison policy changes, several functions must change together. If a new type is added, an entire family of functions has to be copied. If one version is not updated, the code may still compile while carrying a subtle semantic mismatch.

The natural C response is:

> If the structure is identical, why not use a macro?

## 1. The First Macro Is Usually a Great Success

The comparison functions above can immediately be written as:

~~~c
#define DEFINE_COMPARE(T, name)            \
    int name##_compare(                    \
        const T *a, const T *b)            \
    {                                      \
        return (*a > *b) - (*a < *b);      \
    }

DEFINE_COMPARE(int, int)
DEFINE_COMPARE(long, long)
DEFINE_COMPARE(float, float)
~~~

A large amount of duplicated code disappears.

That is exactly what makes the C preprocessor attractive.

It adds no new runtime.

It requires no separate code generator.

It requires no virtual machine or reflection system.

After preprocessing, the compiler still sees ordinary C:

~~~text
Macro
   ↓
Preprocess
   ↓
Ordinary C
   ↓
Compiler
   ↓
Machine Code
~~~

For a foundational library that wants a simple build and low runtime overhead, this is valuable.

The next steps are obvious:

~~~text
compare can be a macro
hash can too
copy can too
destroy can too
~~~

The problem seems solved.

The real difficulty is only beginning.

---

## 2. Macros Remove Code Duplication, Then Macro Invocations Start Duplicating

Assume we now have:

~~~c
DEFINE_COMPARE(...)
DEFINE_HASH(...)
DEFINE_COPY(...)
DEFINE_DESTROY(...)
~~~

The code may become:

~~~c
DEFINE_COMPARE(int, int)
DEFINE_COMPARE(long, long)
DEFINE_COMPARE(float, float)

DEFINE_HASH(int, int)
DEFINE_HASH(long, long)
DEFINE_HASH(float, float)

DEFINE_COPY(int, int)
DEFINE_COPY(long, long)
DEFINE_COPY(float, float)
~~~

The function bodies are no longer duplicated.

But this information:

~~~text
int
long
float
~~~

is repeated again and again.

The first abstraction removed:

~~~text
duplicated code
~~~

and immediately revealed a second problem:

~~~text
duplicated facts
~~~

What the program really wants to say once is:

> I support `int`, `long`, and `float`.

So the next natural step is:

~~~c
#define TYPES(X)       \
    X(int, int)        \
    X(long, long)      \
    X(float, float)
~~~

and then:

~~~c
TYPES(DEFINE_COMPARE)
TYPES(DEFINE_HASH)
TYPES(DEFINE_COPY)
~~~

This still looks like an ordinary X-Macro technique, but something important has changed.

Initially the macro reused:

~~~text
a code template
~~~

Now it reuses:

~~~text
data
~~~

specifically:

~~~text
which types exist
~~~

At this point a macro is no longer just source replacement.

It has started to act as a very small:

~~~text
compile-time description
~~~

mechanism.

---

## 3. From Reusing Code to Reusing Facts

Once this pattern appears, it quickly spreads.

For an enum:

~~~c
#define STATES(X)             \
    X(READY,   "ready")       \
    X(RUNNING, "running")     \
    X(DONE,    "done")
~~~

the same facts can generate:

~~~text
enum values
strings
parse tables
debug output
~~~

Struct fields can use the same idea:

~~~c
#define USER_FIELDS(X) \
    X(int, id)         \
    X(double, score)
~~~

and generate:

~~~text
field declarations
field names
offsets
sizes
serialization mappings
~~~

Function signatures can also be maintained as facts:

~~~text
input type
output type
function name
~~~

Soon the project contains things like:

~~~text
TYPE_LIST
FIELD_LIST
ENUM_LIST
FUNCTION_LIST
SIGNATURE_LIST
~~~

They look unrelated, but they are converging on the same shape:

~~~text
a finite set of records
        ↓
consumed by different macros
        ↓
different generated results
~~~

The role of macros has changed again.

It is no longer merely:

> Copy this text in several places.

It is becoming:

> **Describe facts once, then generate program structures from those facts.**

---

## 4. The C Preprocessor Was Not Designed for This

The problem is that the C preprocessor was not originally designed for this kind of infrastructure.

It is excellent at:

~~~c
#define BUFFER_SIZE 1024
~~~

or:

~~~c
#define MAX(a, b) ...
~~~

But once we build reusable macro machinery, we repeatedly encounter rules that are unnatural compared with an ordinary language.

Token concatenation is a classic example.

This looks simple:

~~~c
#define CAT(a, b) a##b
~~~

Suppose:

~~~c
#define TYPE int
~~~

and then:

~~~c
CAT(TYPE, _value)
~~~

Without understanding macro argument expansion, the result can easily violate intuition.

So we usually need another layer:

~~~c
#define CAT_I(a, b) a##b
#define CAT(a, b) CAT_I(a, b)
~~~

just to:

> **expand the arguments before concatenating them.**

Something that would barely be worth mentioning in a normal language already requires special expansion knowledge in the preprocessor.

---

## 5. A Comma Can Change the Meaning of a “Type”

Macro arguments introduce another classic difficulty.

This is easy:

~~~c
MACRO(int)
~~~

But if the input contains a comma:

~~~text
(A, B)
~~~

the preprocessor naturally sees:

~~~text
two arguments
~~~

rather than:

~~~text
one structured value
~~~

So we start introducing:

~~~text
parentheses
tuples
UNPAREN
~~~

For example:

~~~c
#define UNPAREN(...) __VA_ARGS__
~~~

Then the next question appears:

> How do we know whether the input is parenthesized?

Now we invent machinery such as:

~~~text
PROBE
IS_PROBE
IS_PAREN
SECOND
~~~

This is where the story becomes revealing.

We started by wanting to:

> Write fewer duplicated functions.

Now we are studying:

> **how to recognize the structure of a token sequence during preprocessing.**

---

## 6. Even `for each` Has to Be Built by Hand

If the data is declared as:

~~~c
#define TYPES(X) \
    X(int)       \
    X(long)      \
    X(float)
~~~

iteration remains fairly direct.

But suppose the data comes from variadic arguments:

~~~c
FOR_EACH(M,
    int,
    long,
    float,
    double)
~~~

The C preprocessor has no real:

~~~text
for
foreach
iterator
~~~

So we have to build expansion manually.

A typical implementation has:

~~~c
#define FOR_EACH_1(...)
#define FOR_EACH_2(...)
#define FOR_EACH_3(...)
#define FOR_EACH_4(...)
~~~

plus:

~~~text
NARG
~~~

to count arguments.

Then:

~~~text
CAT(FOR_EACH_, N)
~~~

selects:

~~~text
FOR_EACH_4
~~~

A very ordinary requirement:

> Apply the same operation to four values.

has now expanded into:

~~~text
variadic arguments
argument counting
token concatenation
dispatch
expansion ordering
~~~

At this point the question is no longer:

> Can it be implemented?

Usually it can.

The better question is:

> **Has the complexity become too high for such ordinary reuse?**

---

## 7. Nesting Macros Is Even Harder

Even after building:

~~~text
FOR_EACH
~~~

we soon need:

~~~text
FOR_EACH
    ↓
another FOR_EACH inside
~~~

For example:

~~~text
iterate input types
    ↓
for each input type, iterate output types
~~~

Conceptually this is just a nested loop.

But the preprocessor has a special rule:

> While a macro is being expanded, that macro name is temporarily disabled from expanding again.

As a result:

~~~text
FOR_EACH(FOR_EACH(...))
~~~

does not necessarily behave like ordinary recursion or nested calls.

A common workaround is to define multiple expansion families:

~~~text
FOR_EACH_A
FOR_EACH_B
FOR_EACH_C
~~~

The outer level uses A, the next uses B, and the next uses C.

It is not elegant, but it is deterministic and easier to make portable across compilers.

This leads to an important realization:

> **Instead of trying to turn the preprocessor into a universal language, accept its boundaries and build reliable tools inside explicit limits.**

---

## 8. The Most Painful Part of Macros Is Often Not Writing Them, but Debugging Them

Complex macros have an even larger problem than syntax:

~~~text
error messages
~~~

In ordinary C:

~~~c
int x = "hello";
~~~

the compiler can usually point directly at the type mismatch.

With a complex macro, the source mistake might be:

~~~c
Traits(User,
    (equal, user_equal),
    (hash, user_hash)
);
~~~

while the compiler reports:

~~~text
expected ')' before ...
~~~

or:

~~~text
unknown identifier ...
~~~

The actual expansion chain may be:

~~~text
input declaration
   ↓
row unpack
   ↓
foreach
   ↓
tag dispatch
   ↓
token concat
   ↓
generated declaration
   ↓
C compiler error
~~~

The user made the mistake at layer one, but the compiler sees layer six.

So as macros grow more powerful, another design requirement becomes essential:

> We must care not only whether the macro works, but whether its failures remain understandable.

---

## 9. The Biggest Limitation Is Not Syntax — It Is That Macros Have No Types

All the previous problems are annoying, but they can usually be worked around.

The deeper limitation is:

> **The preprocessor does not know what a type is.**

To the C compiler:

~~~c
int
double
User
~~~

are different types.

To the preprocessor they are merely:

~~~text
token
token
token
~~~

It does not know that:

~~~text
int is an integer
double is floating point
User is a struct
~~~

and certainly does not know:

~~~text
sizeof(T)
alignment
copy semantics
destroy semantics
hashability
comparability
~~~

It does not know that:

~~~text
int -> double
~~~

describes a function signature.

Nor does it know that:

~~~text
Vec<int>
~~~

describes a Generic type parameterized by `int`.

So when ordinary macros pretend to “handle types,” they often simulate them as names:

~~~text
INT
DOUBLE
USER
~~~

and manually maintain mappings such as:

~~~text
INT -> int
INT -> integer
INT -> descriptor
INT -> hash
INT -> compare
~~~

We have returned to the original problem:

> **the same fact is being written in many places again.**

---

## 10. C11 `_Generic` Opens a Door

C11 introduced an important tool:

~~~c
_Generic
~~~

It is nowhere near a C++ template system, but it does provide a finite form of:

~~~text
type-directed selection
~~~

Conceptually:

~~~c
_Generic((value),
    int:    handle_int,
    double: handle_double)
~~~

If we already own a:

~~~text
finite type list
~~~

we can use that list to generate:

~~~text
type selection
descriptor lookup
callback signatures
~~~

In other words, macros can finally connect to:

~~~text
the C compiler's type system
~~~

in a meaningful way.

That is a major change.

---

## 11. Once Types Enter the Picture, Many Problems Become Structured

Suppose a type can describe not only its:

~~~text
name
~~~

but also:

~~~text
size
alignment
kind
traits
identity
~~~

Many things that previously depended on naming conventions become real type relations.

For example:

~~~text
HashMap<K,V>
~~~

can require:

~~~text
K supports hash
K supports equal
~~~

A sorted structure can require:

~~~text
K supports compare
~~~

A function can carry:

~~~text
input type
output type
~~~

rather than being only an address.

The system starts moving from:

~~~text
text generation
~~~

toward:

~~~text
type-aware generation
~~~

This was not the original grand plan.

It emerged naturally from repeatedly solving macro-reuse problems.

---

## 12. What the First Stage Actually Taught Us

Looking back, every new abstraction appeared not because:

> We wanted new syntax.

but because the previous layer exposed new duplication.

~~~text
duplicated code
    ↓
parameterized macro

duplicated macro calls
    ↓
shared list

duplicated list-consumption patterns
    ↓
generic foreach / repeat

duplicated row representation
    ↓
uniform schema

duplicated type knowledge
    ↓
type-aware description
~~~

The progression is:

~~~text
C code
  ↓
Macro reuse
  ↓
Macro data
  ↓
Structured rows
  ↓
Reusable preprocessor primitives
  ↓
Type-aware description
~~~

What drives the progression is never:

~~~text
"What other clever macro trick can we invent?"
~~~

It is:

> **How can we stop maintaining the same knowledge more than once?**

---

## 13. A Principle That Never Changed

After working through these problems, one principle becomes clear:

> **The value of macros is not that they become as powerful as possible. Their value is using the least complexity needed to collapse stable repetition into one source of truth.**

That is why the later design consistently prefers:

~~~text
finite
explicit
bounded
predictable
~~~

instead of:

~~~text
unbounded recursion
universal template language
macro interpreter
~~~

The original reason to use macros was:

~~~text
reduce complexity
~~~

If the macro system becomes harder to understand and debug than the C it replaces, it has defeated its purpose.

---

## 14. The Next Step: When Macros Become Type-Aware

At this point we have two important foundations.

First, we know how to let:

~~~text
a set of facts
~~~

be consumed repeatedly by different code generators.

Second, we can begin connecting:

~~~text
C types
~~~

with:

~~~text
compile-time descriptions
~~~

The next question is natural:

> **If we can describe types, can macros generate different code based on those types?**

Then:

> Can we describe a Generic?

And then:

> Given known types, can we derive another type?

We move from:

~~~text
Reuse
~~~

to:

~~~text
Generate
~~~

and then to:

~~~text
Derive
~~~

This is the point where scattered macro techniques start to become a genuine typed metaprogramming model.

## 15. Semantic Contract: What This Chapter Actually Establishes

What we have built is not a new runtime and not a new “template language.”

This chapter establishes a small set of semantic promises that later chapters will keep reusing.

### 15.1 After Preprocessing, It Is Still Ordinary C

Execution semantics do not change:

~~~text
facts / schema
      ↓
preprocessor
      ↓
ordinary C declarations / definitions
      ↓
ordinary C compiler
~~~

The macro layer may reduce duplicated knowledge, but it should not secretly own:

~~~text
object runtime
dynamic dispatcher
reflection VM
hidden scheduler
automatic ownership system
~~~

If an abstraction requires those facilities, we have entered a later layer and are no longer discussing simple Macro Reuse.

### 15.2 One Fact Should Have One Authoritative Source

When we write:

~~~text
int
long
float
~~~

what we really mean is:

> “The system currently supports this set of types.”

Compare, hash, copy, and destroy are consumers of that fact.

So the most important contract in this chapter is not a macro name. It is:

> **Stable knowledge should not be manually duplicated across multiple places.**

### 15.3 Generation Must Remain Finite, Explicit, and Checkable

This chapter does not attempt to build an infinitely recursive preprocessor language.

We accept a smaller goal:

~~~text
finite
explicit
bounded
predictable
~~~

That means:

- supported schemas are finite;
- expansion rules are explicit;
- the generated C can be inspected;
- failures should remain close to the declaration site where possible;
- debuggability is not sacrificed for “universality.”

These constraints become basic CMeta design disciplines later.

## 16. What Lean Should — and Should Not — Do in Chapter 1

This chapter introduces a methodological rule that matters throughout the book:

> **Not every correctness problem belongs in Lean.**

The questions at this stage are primarily:

- Did the preprocessor expand the schema as intended?
- Does the compiler accept the generated C?
- Do different compilers behave consistently?
- Are the generated symbols what we intended?
- Did the macro actually reduce duplicated knowledge?

Those are toolchain and engineering-evidence questions first.

We do not need to write a theorem merely to “formalize” the fact that:

~~~text
DEFINE_COMPARE(int)
~~~

will be preprocessed correctly by a particular compiler.

That is not the most valuable proof obligation here.

Lean becomes useful when the next chapter introduces semantic questions such as:

~~~text
Given a finite type set,
is a type mapping unique?

Given several input types,
is a derivation rule total / deterministic?

If two descriptors live in different Translation Units,
how do they denote the same semantic type?
~~~

The boundary is:

~~~text
Macro problem
    ↓
engineering evidence

Type relation
    ↓
semantic model
    ↓
Lean
~~~

That distinction matters.

**Lean is neither decoration nor a substitute for tests.**

## 17. Implementation Evidence: How Do We Know the Abstraction Has Not Secretly Become Heavy?

If this is a real Modern C engineering method rather than a showcase of macro tricks, it needs concrete evidence.

### 17.1 Preprocessor Evidence

For important macros, inspect the preprocessed output:

~~~text
macro/schema input
      ↓
compiler -E
      ↓
ordinary C
~~~

The reader should be able to confirm that the generated code is still C they would be willing to write and maintain by hand.

### 17.2 Compile-Pass / Compile-Fail

Both successful and unsuccessful cases should be tested:

~~~text
valid schema
    → compile

invalid schema / unsupported type
    → fail close to the declaration site
~~~

A professional typed C API should not only work when used correctly; it should also move errors earlier.

### 17.3 Cross-Compiler Evidence

The preprocessor is one of the areas in C where compiler-specific corner cases appear most often.

At minimum we should care about:

~~~text
GCC
Clang
MSVC / compatible preprocessing mode
~~~

The goal is not to prove that all compilers are identical. It is to make explicit:

> which syntax belongs to the contract we truly depend on.

### 17.4 Runtime Evidence

The ideal result of this chapter is almost boring:

> **there is no new runtime cost center.**

If both versions ultimately generate the same or equivalent ordinary C function, Macro Reuse provides value in the build/control plane, not in the hot path.

This is the first appearance of an idea that will recur throughout the book:

> **Know more before execution, do less during execution.**

---

## 18. What We Learned

The real lesson of Chapter 1 is not that macros can become complicated.

It is almost the opposite.

We learned this progression:

~~~text
Plain C
   ↓
observe stable repetition
   ↓
reuse code
   ↓
reuse facts
   ↓
make facts structured
   ↓
attach type knowledge
~~~

and several principles that will not change later:

1. **Plain C first**: do not abstract before real repetition exists.
2. **Code first, Meta later**: abstract stable knowledge, not accidental similarity.
3. **Single source of truth**: maintain each fact once.
4. **Finite / explicit / bounded**: do not turn the preprocessor into a second language.
5. **No hidden runtime**: the macro layer still lowers to ordinary C.
6. **Use the right evidence**: compiler/test evidence for toolchain questions; Lean only for semantic laws.

The next question is now unavoidable:

> **When those “facts” begin to include type relations, how do we move from textual reuse to actual typed computation?**

Chapter 2 continues from there: **how macros move from textual reuse into types, Traits, Generics, and finite type derivation.**
