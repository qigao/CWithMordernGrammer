# Chapter 1: Where CMeta Begins — The Pain of Writing C Macros

> **This chapter answers one question only:**
>
> When repetition in ordinary C stops being “a few similar lines” and becomes “the same stable fact maintained in several places,” how can we make that fact explicit without creating a new runtime?

---

## 1. Plain C: Repeated Code Is Not Automatically a Problem

Start with ordinary compare functions:

~~~c
int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}

int long_compare(const long *a, const long *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

If a project has only a few such functions, stop here.

Once the pattern is stable, a macro can remove mechanical repetition:

~~~c
#define DEFINE_COMPARE(T)                  \
    static int T##_compare(                \
        const T *a,                        \
        const T *b)                        \
    {                                      \
        return (*a > *b) - (*a < *b);      \
    }

DEFINE_COMPARE(int)
DEFINE_COMPARE(long)
DEFINE_COMPARE(float)
~~~

This is still ordinary C code generation.

---

## 2. The First Problem: Macro Invocations Start Repeating Too

As the project grows, compare, hash, copy, and destroy all need the same type set:

~~~c
DEFINE_COMPARE(int)
DEFINE_COMPARE(long)
DEFINE_COMPARE(float)

DEFINE_HASH(int)
DEFINE_HASH(long)
DEFINE_HASH(float)

DEFINE_COPY(int)
DEFINE_COPY(long)
DEFINE_COPY(float)
~~~

The repeated knowledge is no longer the function body. It is the fact that the system supports int, long, and float.

Write that fact once:

~~~c
#define BUILTIN_TYPES(X) \
    X(int)               \
    X(long)              \
    X(float)
~~~

Several consumers can expand the same fact set:

~~~c
#define GEN_COMPARE(T) DEFINE_COMPARE(T)
BUILTIN_TYPES(GEN_COMPARE)

#define GEN_HASH(T) DEFINE_HASH(T)
BUILTIN_TYPES(GEN_HASH)
~~~

The important transition is:

> **macros begin as code reuse, but their more valuable direction is fact reuse.**

---

## 3. The Preprocessor Boundary Appears Quickly

### 3.1 A Comma Breaks the “One Argument” Intuition

For example, PAIR(int, double) contains a comma that the preprocessor normally treats as an argument separator.

If a type-like expression contains commas, a protocol must protect and later unwrap it:

~~~c
#define UNPAREN(...) __VA_ARGS__
#define TYPE_ARG(x) UNPAREN x

TYPE_ARG((Pair, int, double))
~~~

This is evidence that the preprocessor does not understand type expressions.

### 3.2 for each Must Be Finite and Explicit

The preprocessor has no general loop.

A library usually provides bounded arities:

~~~c
#define FOR_EACH_1(M, a) \
    M(a)

#define FOR_EACH_2(M, a, b) \
    M(a) M(b)

#define FOR_EACH_3(M, a, b, c) \
    M(a) M(b) M(c)
~~~

NARG then selects one implementation.

Being finite is useful: the capability is bounded and testable.

### 3.3 Nested Macros Need an Expansion Discipline

For example:

~~~c
#define CAT_I(a, b) a##b
#define CAT(a, b) CAT_I(a, b)
~~~

The second layer lets arguments expand before token pasting.

If every subsystem reinvents these mechanisms, macro infrastructure becomes the new duplication.

---

## 4. The Largest Limitation Is Semantic: Macros Do Not Know Types

To the preprocessor, int, double, and User are all tokens.

It does not know:

- whether User is hashable;
- the element type of Vec<int>;
- whether two tokens denote the same semantic type;
- the input/output type of a function.

This establishes a boundary:

> **the preprocessor can generate structure, but it cannot be the semantic authority.**

Modern C needs a more explicit representation for type facts.

---

## 5. C11 _Generic Opens Compile-Time Type Selection

C11 provides _Generic:

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                  \
    long: print_long,                \
    double: print_double             \
)(x)
~~~

This lets C select from a finite set using the static type of an expression.

But _Generic only answers:

> given a known C expression, which existing expression/function should be selected?

It does not define semantic type identity, Generic constructors, field metadata, traits, FunctionDesc, or Multi-TU identity.

_Generic is a tool inside a semantic layer, not the semantic layer itself.

## 6. From Token Tables to a Finite Native Semantic IR

The stable native facts are:

| C fact | Semantic object |
|---|---|
| one type | TypeDesc / semantic identity |
| struct fields | Struct metadata |
| capability | Traits |
| native function | FunctionDesc |
| interface contract | InterfaceDesc |

Consider:

~~~c
typedef struct User {
    uint64_t id;
    const char *name;
} User;
~~~

If serializer, debugger, DataBind, and Mock all need the fields, they should not maintain separate copies.

One source can be:

~~~c
Struct(User,
    (uint64_t, id),
    (const char *, name)
);
~~~

The same rows can generate C declarations and metadata.

The rule is not “write all C as a DSL.” It is:

> **promote only stable facts that several independent consumers otherwise duplicate.**

---

## 7. The Semantic Layer Must Stay Finite, Explicit, and Bounded

Chapter 1 establishes three long-term constraints.

### Finite

Supported type families, macro arities, and relation rows form finite sets.

### Explicit

There is no hidden default; unsupported relations fail during compile/admission.

### Bounded

Macro expansion, generated object size, and relation tables have clear limits.

This moves errors into the build/control plane instead of runtime guesswork.

---

## 8. The Macro Layer Must Not Secretly Become a Runtime

The intended chain is a **build-time generation pipeline**, not runtime dataflow:

~~~text
facts / schema
      ↓ generate
preprocessor / generator
      ↓ emit
ordinary C declarations / metadata
      ↓ compile
ordinary C compiler
~~~

Macro/Meta should not quietly acquire an object runtime, dynamic dispatcher, hidden scheduler, or automatic ownership system.

If a capability requires those things, it belongs to a later Runtime/Execution layer.

---

## 9. The Lean Boundary in Chapter 1

Lean is not needed to prove that a specific compiler expands DEFINE_COMPARE(int).

Use preprocess output, compile-pass/fail tests, cross-compiler tests, and generated-symbol checks.

Lean becomes useful for semantic questions such as:

- is a finite type relation deterministic?
- does normalization preserve meaning?
- do two descriptors denote the same semantic type?
- does a rewrite preserve observable semantics?

> **proof does not replace toolchain evidence, and toolchain tests do not replace semantic proof.**

---

## 10. Engineering Evidence

### Preprocess

~~~bash
cc -E sample.c
~~~

Verify that the result is still C a human is willing to read, debug, and maintain.

### Compile-Pass / Compile-Fail

Valid declarations compile; unsupported relations fail near the declaration site.

### Cross-Compiler

Cover at least GCC, Clang, and MSVC-compatible preprocessing mode.

### Runtime

The ideal result is:

> **no new runtime cost center.**

If Meta and handwritten versions ultimately generate equivalent ordinary C, the value exists in the build/control plane, not the hot path.

---

## 11. What We Learned

This chapter did not invent a “C metaprogramming language.”

It made three moves:

1. use macros to remove mechanical code duplication;
2. notice that duplicated stable facts matter more;
3. constrain the next layer to a finite, explicit, bounded semantic model.

The next chapter continues that direction:

> **once type facts have one authoritative source, how can Generic, Struct, Traits, and finite type relations share one Native Semantic IR?**
