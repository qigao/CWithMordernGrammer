# Chapter 14: Finite, Explicit, On Demand — When to Stop Adding Meta

> **This chapter does not list abstract principles and then explain each one.**
>
> It asks one question:
>
> ~~~text
> Does this abstraction remove more stable duplicated knowledge
> than the long-term cost it introduces?
> ~~~
>
> If not, keep ordinary C.

---

## 1. Decision Tree: Ask Whether Abstraction Is Needed at All

~~~text
problem appears
    |
    v
Can ordinary C express it clearly?
    |
   yes
    |
    v
Is stable knowledge duplicated across modules/backends?
    |
   no -----------------> keep ordinary C
    |
   yes
    |
    v
Can the knowledge be finite/explicit/bounded?
    |
   no -----------------> keep local/manual design
    |
   yes
    |
    v
Does a shared IR remove real maintenance or correctness risk?
    |
   no -----------------> keep ordinary C
    |
   yes
    |
    v
introduce the smallest semantic object
~~~

Abstraction is not the default answer.

---

## 2. Case A: One Fixed Pipeline Does Not Need Graph

~~~c
size_t copy_even_squares(
    const int *xs,
    size_t n,
    long *out)
{
    size_t m = 0;

    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];

        if ((x & 1) != 0)
            continue;

        out[m++] = (long)x * x;
    }

    return m;
}
~~~

If there is one pipeline, one call site, no dynamic composition, no rewrite, and no alternate backend, then **Graph cost > shared knowledge removed**. Keep the loop.

Upgrade only when the system grows into shared operators, many pipelines, type propagation, optimizer passes, or multiple backends.

---

## 3. Case B: One Callback Does Not Need a Callable Object

~~~c
typedef void (*done_fn)(void *user);

void request_start(done_fn done, void *user);
~~~

If the callback is not stored across a complex lifetime, composed, reflected, or optimized, this API is enough. Do not immediately add a signature registry, capture object, effect metadata, and generic dispatcher.

Introduce FunctionDesc/Callable only when several consumers need shared function semantics.

---

## 4. Case C: One Internal Function Does Not Need an IDL

~~~c
static int
lookup_user(UserRepository *repo, uint64_t id, User *out);
~~~

If it is only directly called inside one binary and has no HTTP, RPC, Plugin, WASM, generated Mock, or external contract, do not add message/service/component/databindc.

IDL is justified by repeated logical contracts across boundaries, not by the mere existence of a function.

---

## 5. Case D: One Known Implementation Does Not Need Plugin

If there is one implementation, known at link time, never dynamically discovered, and never unloaded, direct linking is simpler:

~~~cmake
target_link_libraries(app PRIVATE image_codec)
~~~

Do not add loader, registry, manifest, lease, and quiescent unload without a real dynamic capability requirement.

Use PLUGIN only when dynamic discovery, replaceable implementation, cross-DSO capability, or safe unload is actually needed.

---

## 6. Cost Table

| Abstraction | Removes | Adds |
|---|---|---|
| Generic | repeated type-instantiation facts | generated API / diagnostics |
| FunctionDesc | repeated native function metadata | descriptor ABI / ownership rules |
| Graph | repeated composition/analysis logic | IR + optimizer + qualification |
| DataBind IDL | repeated logical contracts | compiler + versioning + codegen |
| Plugin | dynamic capability publication | loader/lease/unload ABI |
| WASM | portable component ABI | host/guest lowering + runtime boundary |
| Actor | concurrency admission/lifecycle duplication | mailbox/ref/generation protocol |

If the right column dominates the left, stop abstracting.

---

## 7. Hidden Runtime Budget

Every convenience feature must account for hidden cost.

For oversized lambda capture, avoid:

~~~text
capture too large
    ↓
secret malloc
    ↓
still reports success
~~~

Prefer an explicit contract:

~~~text
capture <= inline_capacity
    -> OK

capture > inline_capacity
    -> TOO_LARGE
~~~

or let the caller provide an explicit owner:

~~~c
owned_capture *cap = owned_capture_create(...);

callable_bind_owned(&fn, cap);
~~~

A prettier API does not make cost disappear.

---

## 8. Evidence Budget

Before a new abstraction enters core, list the new gates it creates:

~~~text
new generated syntax
    -> compile tests

new identity rule
    -> Multi-TU / DSO tests

new lifecycle
    -> sanitizer/stress

new rewrite
    -> semantic theorem

new performance claim
    -> benchmark

new projection backend
    -> installed integration
~~~

If maintaining those gates cannot be justified, the abstraction is probably not ready for core.

## 9. Counterexample Lab: Ten Designs That Look More Advanced but Are Actually Worse

These examples are not straw men.

They are common designs that often look more uniform, intelligent, or automatic early on.

Their problems appear only as the system grows.

### 25.1 Counterexample 1: One Similarity Appears, So We Immediately Invent a Meta DSL

Suppose there are only:

~~~c
int user_age(const User *u) {
    return u->age;
}

int order_count(const Order *o) {
    return o->count;
}
~~~

They look structurally similar, so we design:

~~~text
FieldGetter(Type, Field, ReturnType)
GenerateAccessor(...)
Reflect(...)
GenericInvoke(...)
~~~

Surface benefit:

~~~text
two fewer tiny functions
~~~

Actual cost:

~~~text
new macro vocabulary
new error messages
new naming convention
new compile-time dependency
new debugging path
~~~

And:

~~~text
User.age
Order.count
~~~

may only be accidentally similar.

#### Why It Is Wrong

The abstraction captures:

~~~text
current code shape
~~~

instead of:

~~~text
stable knowledge
~~~

This violates:

> **Code First, Meta Later.**

#### Smallest Correction

Keep ordinary C.

Only when we have:

~~~text
many stable field schemas
multiple consumers repeatedly reading the same field facts
serializer / binder / UI / query all need the same information
~~~

should:

~~~text
Field Metadata
~~~

become shared knowledge.

---

### 25.2 Counterexample 2: Pursue Infinite Type Inference to “Look Like Templates”

Suppose the original need is only `CommonType(int, long) = long` and `CommonType(int, double) = double`.

Soon we ask why a TypeFunction should not support arbitrary nesting, recursion, and partial specialization, and then try to emulate template partial specialization, SFINAE, recursive pattern matching, and higher-kinded generic with the preprocessor.

#### Why It Looks Reasonable

C++ Templates are powerful, so it is easy to redefine the goal as “C should be equally powerful.”

#### What Actually Goes Wrong

The C preprocessor was not designed for open recursive type computation.

The result tends to be error explosion, unpredictable compile time, compiler divergence, terrible debugging, unclear rule boundaries, and harder formal models.

#### Smallest Correction

Rewrite the problem as **finite admitted universe + finite relation rows + explicit unsupported case**. In other words, **TypeFunction = finite relation**, not a secret general-purpose compiler.

This is why No Default matters.

Unknown input fails.

---

### 25.3 Counterexample 3: Descriptor Pointer Is Type Identity

The simplest implementation:

~~~c
if (a == b) {
    /* same type */
}
~~~

works perfectly in one TU.

Tests may all be green.

Until TU A, TU B, shared library A/B, or a static archive duplicated into several DSOs appears. The same `Pair<int, long>` may then have several descriptor objects.

Then:

~~~text
pointer differs
    ↓
"type mismatch"
~~~

#### Why It Is Wrong

Address answers “where is this representation object?”, not “what semantic type is this?”

#### Smallest Correction

Use stable atom id, generic constructor identity, structural arguments, and pointer/const/application form for semantic identity. Two descriptors with different addresses but the same structure/meaning should compare equal.

This is not an abstraction bonus.

It is Multi-TU correctness.

---

### 25.4 Counterexample 4: Lambda Capture Exceeds Inline Bound, So We Secretly `malloc`

Suppose a C lambda uses a callable with `inline capture[32]`.

Then an 80-byte capture appears.

The most “convenient” behavior is:

~~~text
if too large:
    malloc(...)
    hide pointer inside callable
~~~

with no API change.

#### Why It Looks Reasonable

Now it appears that “any capture works.”

#### What Actually Goes Wrong

The API originally implied bounded value objects, copy-by-value, no hidden allocation, and predictable lifetime. It silently becomes “some callables allocate; copy may fail; destroy becomes mandatory; thread/lifetime semantics changed; ABI shape meaning changed,” and the call site does not know.

#### Smallest Correction

Three valid choices are A. compile/admission failure, B. an explicit heap-backed callable type, or C. caller-owned external context. The choice must be explicit.

> **Hidden convenience that changes ownership is not convenience. It is semantic drift.**

---

### 25.5 Counterexample 5: Actor / Executor Queue Automatically Grows Forever

Requirement:

~~~text
send should almost never fail
~~~

Implementation:

~~~text
queue full
    ↓
realloc bigger
    ↓
keep accepting
~~~

or:

~~~text
linked-list unbounded queue
~~~

#### Why It Looks Reasonable

Upper layers do not need to handle FULL.

The demo is smooth.

#### What Happens in Production

When:

~~~text
producer rate > consumer rate
~~~

there is no backpressure.

Only:

~~~text
memory rises
latency rises
cache locality collapses
events become stale
eventually OOM
~~~

An explicit:

~~~text
FULL
~~~

has been converted into a delayed global failure.

#### Smallest Correction

Use fixed capacity.

Return:

~~~text
FULL
~~~

and let higher layers choose:

~~~text
retry later
drop by explicit policy
backpressure upstream
fail operation
shed load
~~~

> **Boundedness turns resource pressure into information.**

---

### 25.6 Counterexample 6: Silent Sequential Fallback When Parallel Plan Is Unavailable

The user explicitly requests:

~~~text
parallel reduce
~~~

but input is too small, Executor is full, reducer contract fails, or Plan does not support it.

Framework decides:

~~~text
"No problem, I will run sequentially. The result is the same."
~~~

#### Why It Looks Reasonable

The feature seems more robust.

#### Why It Is Actually Dangerous

Even if output is equal:

~~~text
latency
CPU topology
resource usage
deadline behavior
load shedding
SLA
benchmark
~~~

all changed.

Worse, an admission bug that should be visible is hidden.

#### Smallest Correction

Return:

~~~text
UNSUPPORTED
FULL
INVALID_OPTIONS
INELIGIBLE
~~~

If application wants fallback:

~~~text
if parallel failed:
    explicitly choose sequential
~~~

it owns that policy.

> **Semantic equivalence does not imply operational equivalence.**

---

### 25.7 Counterexample 7: Everything Is Virtual

To “unify” the system, turn everything into:

~~~text
{ self, vtable }
~~~

including:

~~~text
Map
Filter
type operations
small value transform
inner-loop compare
Graph node execution
~~~

Every value performs:

~~~text
vtable lookup
indirect call
metadata check
dynamic dispatch
~~~

#### Why It Looks Elegant

One interface to rule them all.

New types do not change callers.

#### The Real Problem

We mixed:

~~~text
boundaries that truly need dynamic behavior
~~~

with:

~~~text
interior behavior already known at compile/construction time
~~~

So:

~~~text
optimizer knowledge cannot eliminate the layer
hot path remains dynamic forever
debugging stacks grow
cache/inlining opportunities shrink
~~~

#### Smallest Correction

Keep:

~~~text
Dynamic Boundary
    Publisher / Scheduler / plugin provider

Static Interior
    known Graph stage / Plan instruction / direct target
~~~

Dynamic behavior remains only where it is truly dynamic.

> **Interface is a boundary tool, not a universal object model.**

---

### 25.8 Counterexample 8: Treat Raw Parser Tokens as Business Stream Items

A JSON parser emits:

~~~text
OBJECT_BEGIN
KEY
STRING
ARRAY_BEGIN
...
~~~

and we already have CFlow Stream.

So it is tempting to write:

~~~text
Stream<Token>
    .filter(...)
    .map(...)
~~~

#### Why It Looks Reasonable

Both are “streams.”

#### The Real Problem

A token sequence is not a collection of independent business values.

It is a:

~~~text
grammar-preserving structural protocol
~~~

If business logic filters out:

~~~text
ARRAY_END
~~~

the grammar is broken.

And:

~~~text
field name
number
container boundary
~~~

still has not become a semantic object.

#### Smallest Correction

Use:

~~~text
parser syntax
    ↓
canonical grammar
    ↓
binding / validation
    ↓
complete semantic/native value
    ↓
business CFlow
~~~

> **Same shape “stream of items” does not mean same semantics.**

---

### 25.9 Counterexample 9: Use Lean to Prove ABI or Benchmark Claims

Once a team has Lean, another formalist temptation appears:

~~~text
Can we prove struct ABI stable?
Can we prove this version is 2x faster?
Can we prove Linux scheduler never starves us?
~~~

#### Why It Is Wrong

Those questions depend on:

~~~text
compiler ABI
linker/loader
platform
CPU
OS
allocator
benchmark workload
external environment
~~~

Unless the formal model includes those real facts precisely, the theorem proves:

~~~text
an abstract model
~~~

not the actual toolchain.

#### Smallest Correction

Use Lean for:

~~~text
semantic identity
rewrite preservation
state-machine invariant
bounded protocol relation
refinement
~~~

Use toolchain evidence for:

~~~text
ABI
link
install
compiler compatibility
~~~

Use benchmarks for:

~~~text
actual performance
~~~

Use stress/sanitizers for:

~~~text
memory/race bugs
~~~

> **Using proof at the wrong layer is another form of hidden assumption.**

---

### 25.10 Counterexample 10: Push Domain Semantics into Core Because “Upper Layers Need It”

RPC needs:

~~~text
retry
deadline
service discovery
~~~

so we put:

~~~text
retry policy
~~~

inside Executor.

Workflow needs:

~~~text
compensation
~~~

so compensation goes into Machine core.

JSON needs:

~~~text
field names
~~~

so JSON syntax goes into CMeta.

#### Why It Is Wrong

Core loses:

~~~text
single semantic ownership
~~~

A primitive begins serving too many domains and accumulates:

~~~text
vague universal parameters
~~~

#### Smallest Correction

Ask:

~~~text
Is this meaning unique to the domain?
Does it repeat stably across several independent domains?
Is Core still complete without it?
~~~

If it is domain-specific:

~~~text
keep it in the upper layer
~~~

> **Reuse does not require ownership transfer.**

## 10. “Ordinary C Is Better” Is Not Failure; It Is a Successful Design Decision

A Modern C book that leaves readers thinking:

~~~text
every problem should use CMeta/CFlow
~~~

has taught the wrong lesson.

Many situations are clearly better as ordinary C.

### 26.1 One Fixed Pipeline

If we only have:

~~~c
for (...) {
    if (...) {
        ...
    }
}
~~~

with no dynamic composition, Graph reuse, analysis, or optimization:

> write the loop.

### 26.2 A Small State Machine

If there are:

~~~text
3 states
4 events
one file
no dynamic binding
no concurrency
~~~

a switch may be better than Machine IR.

### 26.3 One Callback

If there is no need for:

~~~text
capture
signature registry
Graph
semantic optimization
~~~

use:

~~~c
void (*fn)(void *);
~~~

directly.

### 26.4 One Fixed-Struct Parser

One format, one object, no generic binding:

> write parser-to-struct code directly.

### 26.5 A Simple Synchronous Program

If we do not need:

~~~text
WAIT
Demand
Scheduler
Executor
~~~

do not add an async model merely to look “modern.”

#### Decision Rule

If an abstraction removes none of:

~~~text
real duplicated knowledge
real error boundaries
real runtime-decision duplication
~~~

then it may be only another layer.

## 11. Decision Tree: Should a New Capability Enter Meta / Core?

Use this sequence:

~~~text
Q1. Is Plain C already clear, short, and stable?
    YES → keep Plain C
    NO  ↓

Q2. Is the repetition stable knowledge or only code shape?
    code shape only → do not abstract yet
    stable knowledge ↓

Q3. Do multiple independent consumers need the same fact?
    NO → keep it module-local
    YES ↓

Q4. Is the knowledge finite and explicitly describable?
    NO → may be runtime/domain feature
    YES ↓

Q5. Can ownership / failure / capacity be stated clearly?
    NO → do not enter Core
    YES ↓

Q6. Which existing semantic owner already owns this meaning?
    existing owner → extend/reuse owner
    none ↓

Q7. Does the same meaning repeat stably across domains?
    NO → upper-layer feature
    YES ↓

Q8. Can most complexity be consumed before execution?
    NO → explicitly classify as Runtime Feature
    YES ↓

Q9. Is there a correct evidence strategy?
    NO → design is incomplete
    YES ↓

Q10. Does adding it make the whole system easier to understand?
    NO → remove the abstraction
    YES → only then consider Core
~~~

The last question is the most important.

## 12. Anti-Meta Budget: Every New Core Primitive Has a Long-Term Cost

Treat every Core feature as spending a maintenance budget.

Once a primitive enters:

~~~text
CMeta
CFlow kernel
public ABI
formal model
generated manifest
~~~

it carries long-term obligations:

~~~text
documentation
compiler compatibility
ABI
Multi-TU
tests
formal maintenance
debugging
migration
downstream compatibility
~~~

So the standard cannot be merely:

~~~text
Is it easy to implement?
~~~

It should be:

> **Is this worth explaining, testing, and preserving for the next five years?**

This naturally slows Core growth.

That is a feature, not a problem.

## 13. Counterexample Review Checklist

When reviewing a new Meta/Runtime abstraction, ask:

~~~text
[ ] Is there a Plain C baseline?
[ ] What duplicated knowledge does this remove?
[ ] Why is a module-local helper insufficient?
[ ] Why must this enter Core?
[ ] Does type identity survive Multi-TU?
[ ] Is ownership explicit?
[ ] Is there hidden allocation?
[ ] Are resources bounded?
[ ] Are FULL/CLOSED/STALE preserved as information?
[ ] Is there silent fallback?
[ ] Does dynamic dispatch enter an unnecessary hot path?
[ ] Does failure happen as early as possible?
[ ] Is the theorem proving the right layer of problem?
[ ] Do ABI/toolchain claims have a real consumer test?
[ ] Do performance claims have fresh measurement?
[ ] Can the abstraction disappear from the hot path?
~~~

If many questions cannot be answered:

> shrink the abstraction before improving it further.

## 14. What We Learned

Chapter 14 establishes:

> **restraint is itself a systems capability.**

The ten disciplines now have concrete failure modes:

~~~text
Finite
    prevents the preprocessor from becoming an unbounded language

Explicit
    prevents ownership/policy from changing invisibly

Bounded
    prevents backpressure from becoming OOM

Fail-fast
    prevents error distance from growing

No Silent Fallback
    prevents operational semantics from changing invisibly

Static When Possible
    prevents known interior work from retaining dynamic cost

No Hidden Runtime
    prevents simple-looking APIs from hiding complex ownership

Cross-Compiler Semantics First
    prevents Core from depending on accidental compiler tricks

Semantic Identity
    prevents address coincidence from becoming meaning

Module Owns Meaning
    prevents Core from becoming a landfill of domain features
~~~

But the most important rule remains:

~~~text
Ordinary C First
~~~

not because ordinary C is somehow “purer,” but because:

> **abstraction must justify itself by removing real complexity.**

A mature Modern C system therefore needs two capabilities:

~~~text
knowing when to construct a Typed / Verified abstraction

and

knowing when to write one ordinary C function
~~~

The final chapter no longer lists features.

It keeps one reusable method:

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
~~~

and asks:

> **What is the Modern C described by this book?**
