# Chapter 13: From Foundational Capabilities to Modern C — Serialization, RPC, Plugin, Workflow, and More

> **Chapter path**
>
> This chapter does not treat Serialization, RPC, Plugin, Workflow, ECS, and Query as a feature list of “what else can we build?”
>
> Instead, we choose two deep cases that already have real implementation boundaries:
>
> ~~~text
> Case A
> Concrete Format
>      ↓
> CSerde Canonical Tokens
>      ↓
> CBind + CMeta Semantic Shape
>      ↓
> Native C Value
>      ↓
> optional CFlow composition
>
> Case B
> CMeta Method Semantics + CSerde Params/Result
>      ↓
> JSON-RPC Envelope
>      ↓
> CHTTP
>      ↓
> CNet
>      ↓
> NativeIO
> ~~~
>
> Both cases answer the same questions:
>
> **Which primitives are reused? Who owns semantic truth? Who owns runtime? Where are resources bounded? Where does failure happen early? What evidence exists?**
>
> Plugin, Event Bus, Workflow, ECS, Query, Parser, and Protocol remain on the map, but as extensions rather than excuses to create new core frameworks.

After the previous chapter, the CMeta/CFlow boundaries are fairly clear.

CMeta provides:

```text

Interface

Finite Relation
Semantic Identity
```

CFlow adds:

```text

```

A traditional framework mindset now tempts us to ask:

```text
What else can we build?

CStream?
CRx?

```

and then keep adding large modules.

But the previous chapters point in the opposite direction.

We increasingly find that:

> **the valuable question is not how many frameworks we can add, but whether the existing primitives compose well enough to solve other problems.**

So this chapter is not a roadmap of future features.

It asks:

> Once C has a finite Type, Callable, Graph, and execution substrate, which problems that normally require repeated conventions and duplicated infrastructure can be built naturally on top?

## 2. Deep Case A: Serialization / Data Binding

Serialization is an excellent test of whether a Meta system has real boundaries.

A common bad design is:

~~~text
JSON parser
    owns JSON syntax
    +
    owns native struct reflection
    +
    owns allocation policy
    +
    owns container binding
    +
    owns validation
    +
    owns application conversion
~~~

and then we copy similar machinery for:

~~~text
YAML
XML
CSV
binary protocol
database row
IPC message
~~~

That recreates:

~~~text
Knowledge Duplication
~~~

The right question is:

> **Who owns format syntax, canonical data events, native semantic shape, and native storage lifecycle?**

The edition Salts snapshot already has a clean layered answer.

---

## 2.1 Plain C Baseline: Hand-Written Parser → Struct Is Not Wrong

Suppose:

~~~c
typedef struct User {
    int id;
    char name[64];
} User;
~~~

A small program with one fixed format and one fixed struct can simply:

~~~text
parse "id"
    ↓
atoi
    ↓
user.id

parse "name"
    ↓
copy with bound
    ↓
user.name
~~~

If:

~~~text
only one format exists
only one struct exists
schema is stable
there is no general binding requirement
~~~

then this is the best solution.

A Data Binding abstraction becomes worthwhile only after stable repetition appears:

~~~text
multiple formats need the same User semantic shape
multiple native types repeat field mapping
ownership / rollback / limits keep recurring
parser and native layout are tightly coupled
~~~

---

## 2.2 First Layer: Concrete Parser Owns Syntax Only

A concrete parser should answer:

~~~text
this is object begin
this is a field name
this is a signed integer
this is a string slice
this is array end
~~~

It should not answer:

~~~text
this field writes to User.name offset
this string allocates tstr
this enum belongs to this business domain
~~~

So JSON/YAML/XML parsers can first project into a:

~~~text
CSerde canonical token protocol
~~~

instead of mutating native objects directly.

That separates:

~~~text
syntax
~~~

from:

~~~text
semantic/native binding
~~~

The write direction mirrors the same layering:

~~~text
Native C Value
    ↓
semantic writer/binding
    ↓
CSerde canonical events
    ↓
concrete serializer
    ↓
JSON/YAML/...
~~~

---

## 2.3 Second Layer: CSerde Owns Format-Neutral Token Truth

The edition architecture positions CSerde around:

~~~text
canonical token
reader/writer contract
view lifetime semantics
~~~

It does not depend on:

~~~text
CMeta
CFlow
concrete parser
~~~

That matters.

CSerde itself should not know:

~~~text
User

Actor
Graph
JSON
YAML
~~~

It defines only:

~~~text
canonical value/event grammar
single-pass reader
writer protocol
slice stability/lifetime
status
~~~

Concrete parsers may change while downstream binding remains unchanged.

## 2.4 Third Layer: CMeta Provides Native Semantic Shape

CBind should not invent a second native type system.

It consumes semantic shapes such as:

~~~text
cmeta_data_desc
~~~

A descriptor can tell the binding layer about:

~~~text
kind
storage type
struct shape
enum shape
variant shape
buffer provider
fixed/native operations
stable identity
ABI/version information
~~~

So:

~~~text
native type meaning
~~~

still has one authority.

This continues Chapter 12's principle:

> **Data Binding should not create another type-identity universe merely because it needs schema information.**

## 2.5 Fourth Layer: CBind Is a Format-Neutral Decode Kernel

Current CBind is positioned clearly as:

~~~text
CSerde Reader
    +
CMeta-described native storage
    ↓
CBind
    ↓
native C value
~~~

Its production target depends only on:

~~~text
Salts::CMeta
Salts::CSerde
~~~

not on:

~~~text
CFlow
CSTL
SaltsUtils concrete parsers
application runtime
~~~

This is a strong example of module ownership.

### STRING / BYTES

CBind does not know concrete storage classes such as:

~~~text
tstr
vstr
application buffer class
~~~

It works through a CMeta buffer adapter:

~~~text
owned
borrowed
custom
~~~

and follows:

~~~text
STRING only accepts STRING token
BYTES only accepts BYTES token
owned adapter copies
borrowed adapter only accepts stable view
max_buffer_bytes is hard bound
~~~

### ENUM

Enum must go through the full enum provider contract:

~~~text
declared text/symbol/integer
    → admitted

undeclared value / float coercion
    → rejected
~~~

not “best effort conversion.”

### VARIANT

Variant uses a canonical representation:

~~~text
ARRAY_BEGIN
tag
payload
ARRAY_END
~~~

and `select/restore_zero` owns active-payload lifecycle.

A malformed provider cannot leave a half-active union.

## 2.6 Failure Atomicity: On Failure, the Native Graph Returns to Semantic Zero

Decode may fail because of:

~~~text
bad token
wrong field type
buffer bound
container bound
provider allocation/copy
enum value
variant case
depth
item count
~~~

If failure leaves:

~~~text
half the fields written
some owned buffers allocated
variant engaged but payload incomplete
~~~

then C callers cannot safely destroy or retry.

The CBind contract therefore requires:

~~~text
destination starts in semantic zero
      ↓
decode
      ↓
success:
    complete semantic object

failure:
    restore complete root semantic graph to zero
~~~

while:

~~~text
reader is not rewound
~~~

This distinction matters.

> **Rollback belongs to target-object ownership, not to pretending the input stream never advanced.**

That is a very C-like transactional boundary.

---

## 2.7 Boundedness: Serialization Must Not Grow Without Limit Either

Context explicitly carries:

~~~text
scratch size
max depth
max container items
max buffer bytes
~~~

so:

~~~text
deep malicious input
huge string
unbounded array
~~~

does not get a special exception because “serializers often allocate dynamically.”

Again:

~~~text
Bounded resource
    is semantic contract
~~~

not a performance hint.

---

## 2.8 Only After Binding Should We Enter CFlow

A dangerous anti-pattern is:

~~~text
Stream<cserde_token>
    → arbitrary business filter/map
~~~

Why?

Tokens are:

~~~text
structural transport grammar
~~~

not:

~~~text
business semantic values
~~~

If business code filters raw tokens such as:

~~~text
OBJECT_BEGIN
FIELD
ARRAY_END
~~~

it can destroy the grammar itself.

A stronger boundary is:

~~~text
format syntax
    ↓
CSerde token grammar
    ↓
CBind + CMeta
    ↓
complete native semantic value
    ↓
optional CFlow Stream<T> / Graph / Machine
~~~

CFlow composition starts from:

~~~text
complete semantic/native value
~~~

not raw parser tokens.

Equality here should be:


not arbitrary `memcmp` over padding/object bytes.

## 3.1 Layer the RPC Stack by Ownership First

Current CRPC documentation presents:

~~~text

+
CSerde params/result
      ↓
JSON-RPC envelope + deadline
      ↓
CHTTP POST + HTTP limits
      ↓
CNet connection
      ↓
NativeIO terminal completion
~~~

Each layer owns one meaning.

### CMeta

Optionally describes:

~~~text
local callable signature
effects
properties
~~~

### CSerde

Describes:

~~~text
params/result canonical data events
~~~

### CRPC

Owns:

~~~text
JSON-RPC 2.0 envelope
method/id
remote error
notification/batch semantics
RPC deadline
local request handle
~~~

### CHTTP

Owns:

~~~text
HTTP request/response
headers/body limits
H1/H2
connection pool integration
server routing/middleware
~~~

### CNet

Owns:

~~~text
connection/session/TLS transport progress
~~~

### NativeIO

Owns:

~~~text
native operation progress/completion
~~~

RPC does not need to become a:

~~~text
socket runtime
~~~

This is an advanced application of **Module Owns Meaning**.

## 3.2 Method Identity and Callable Metadata Must Remain Separate

An RPC method on the wire is identified by:

~~~text
service/name
or
wire method name
~~~

Locally, we may additionally bind a:

~~~text
cmeta_callable
~~~

describing:

~~~text
signature
effects
properties
~~~

But:

> **local callable semantics are not wire schema.**

Current CRPC copies/binds callable metadata during admission/registration, while request/response views consume stable snapshots.

CRPC does not:

~~~text
use CMeta to guess JSON wire schema
automatically invoke the callable at runtime
~~~

This boundary matters.

Otherwise CMeta metadata drifts from semantic description into an implicit RPC code-execution framework.

---

## 3.3 Params/Result Reuse CSerde Instead of a Dedicated JSON AST API

RPC params encoder writes:

~~~text
exactly one Array or Map root
~~~

through:

~~~text
cserde_writer
~~~

Result/error data is read through:

~~~text
single-pass cserde_reader
~~~

RPC protocol owns:

~~~text
JSON-RPC envelope shape
~~~

while semantic payload continues to use the canonical value protocol.

This lets future:

~~~text
local test provider
non-JSON internal binding
schema validator
native binder
~~~

reuse the same data semantics without being tied to one JSON DOM.

## 3.4 Blocking and Async APIs Share Protocol but Differ in Progress Ownership

The ordinary business path is:

~~~text
crpc_client_init
    ↓
crpc_request_reply
    ↓
owning crpc_response
    ↓
crpc_response_destroy
~~~

The caller does not need:

~~~text
poller
executor
worker thread
~~~

The advanced caller-driven path is:

~~~text
crpc_async_client_init
    ↓
submit
    ↓
generation-checked request handle
    ↓
poll / cancel
    ↓
exactly-once terminal callback
    ↓
stop
    ↓
destroy
~~~

These are not two RPC semantic systems.

They differ only in progress ownership.

---

## 3.5 JSON-RPC ID and Local Request Handle Are Two Different Identities

This is another useful identity example.

~~~text
request_id
    = JSON-RPC wire identity

crpc_request {slot, generation}
    = local cancellation/lifetime capability
~~~

They must not be conflated.

Why generation?

Because:

~~~text
slot reused
    ↓
old handle must not cancel new request
~~~

So:

~~~text
slot + generation
~~~

protects local lifetime from stale handles.

This is the same pattern as Actor STALE and Graph version/certificate:

> **representation slots may be reused, but semantic lifetime identity must distinguish generations.**

---

## 3.6 Deadline Does Not Mean “Timeout, Therefore Free Everything”

When an RPC deadline expires:

~~~text
request cancellation
~~~

is a control request to lower layers.

Until:

~~~text
CHTTP
CNet
NativeIO
~~~

produce a real terminal completion, the runtime may still need:

~~~text
payload
parser
callback state
request handle
TLS/profile dependency
~~~

to remain alive.

Therefore:

~~~text
deadline reached
    ≠
all underlying work already quiescent
~~~

This is the same principle as Reactive cancel and Actor destroy:

> **Cancellation is a protocol, not an immediate memory-reclamation event.**

---

## 3.7 No Automatic Retry: RPC Especially Must Not Replay Silently

Current CRPC specifies:

~~~text
disconnect after accepted send
    → original error path
    → no automatic replay
~~~

Why?

Because methods may have side effects:

~~~text
charge card
create order
send message
modify state
~~~

The transport cannot know:

~~~text
whether the server already executed the request
~~~

So transport retry is not:

~~~text
"a small reliability optimization"
~~~

It is application semantic policy.

Only a higher layer that understands:

~~~text
idempotency key
deduplication
transaction semantics
retry budget
~~~

is qualified to retry.

This is a concrete case of No Silent Fallback / Module Owns Meaning.

## 3.8 Server Registry Must Also Be Bounded and Pre-Start

Current server lifecycle is:

~~~text
init
    ↓
bounded method registry
    ↓
register target + wire method
    ↓
start
~~~

Register after start returns:

~~~text
BUSY
~~~

Duplicate key returns:

~~~text
ALREADY
~~~

Registry full returns:

~~~text
ENOBUFS
~~~

The method table is therefore not:

~~~text
runtime unordered_map that grows forever
~~~

It is a bounded control-plane artifact.

Likewise:

~~~text
JSON depth
batch items
method bytes
HTTP headers/body
network resources
~~~

have hard bounds.

## 3.9 Exactly-Once Completion Is Another Core RPC Invariant

Async client:

~~~text
submit accepted
    ↓
eventually exactly one terminal callback
~~~

Immediate admission failure:

~~~text
no callback
~~~

Server handler:

~~~text
normal call
    ↓
exactly one response_result or response_error
~~~

Second completion:

~~~text
EALREADY
~~~

Notification:

~~~text
handler runs
but response bytes suppressed
~~~

These are protocol semantics, not conveniences.

An RPC toolkit that cannot state how many terminal completions exist is difficult to compose safely with Actor, Executor, or Workflow.

A valid JSON-RPC error object is:

## 4. Engineering Cases C–E: Async I/O, CSTL, and Testing

The two deep cases show that CMeta/CFlow can support cross-layer application capability.

The next three shorter cases ask:

> **Can the same design discipline improve ordinary foundation libraries too, rather than only large frameworks?**

### 4.1 Async File / Network: Reactive Owns Waiting Semantics, Executor Only Delivers

Chapters 8–9 established:

~~~text
I/O request / readiness
    owns completion truth
        ↓
WAIT / wake
    transports readiness
        ↓
Subscription / Executor
    owns resumption and execution admission
~~~

Reactive source outcomes in the edition snapshot are the finite five states:

~~~text
CFLOW_STEP_VALUE
CFLOW_STEP_VALUE_AND_DONE
CFLOW_STEP_WAIT
CFLOW_STEP_DONE
CFLOW_STEP_ERROR
~~~

An external file/socket driver does not need to understand Graph and should not mutate Graph execution state directly.

It only calls the defined wake boundary on completion/readiness; `cflow_subscription_wake()` returns control to Subscription / Scheduler.

Asynchronous file/network integration therefore does not require a new:

~~~text
async operator system
async type system
async graph
async thread ownership model
~~~

The same typed Graph simply gains a source with time.

The RPC stack composes the same principle downward:

~~~text
CRPC
  ↓
CHTTP
  ↓
CNet
  ↓
NativeIO terminal completion
~~~

“Asynchronous capability” is therefore reuse of WAIT/Wake, Executor, ownership, and completion contracts — not another Core framework.

### 4.2 CSTL: Generic Generates Typed Contracts; Algorithms Remain Ordinary C

Containers are the most direct engineering proof of the Generic design from Part I.

If every container family owns its own declaration macro:

~~~c
DECLARE_VEC(IntVec, int);
DECLARE_LIST(IntList, int);
DECLARE_HASHMAP(IntLongHashMap, int, long);
~~~

the problem is not that those macros cannot work.

It is that every family redefines “how to declare a typed application.”

The edition CSTL snapshot uses the same CMeta Generic entry point:

~~~c
#include <cstl/typed.h>

typed(Vec, IntVec, int);
typed(List, IntList, int);
typed(HashMap, IntLongHashMap, int, long);
typed(Map, IntLongMap, int, long);
typed(BTree, IntTree, int, long);
~~~

Usage remains ordinary C:

~~~c
IntList values = {0};
IntLongMap index = {0};

IntList_init(&values, 100u);
IntList_push_back(&values, 10);
IntList_push_back(&values, 20);

IntLongMap_init(&index, 100u);
IntLongMap_put(&index, 7, 70L);

IntLongMap_destroy(&index);
IntList_destroy(&values);
~~~

The key is implementation boundary.

The edition snapshot leaves:

~~~text
typed wrapper / descriptor / Range traits
    in a thin generated/static-inline surface

vector growth / hashing / tree balancing / allocation
    in compiled CSTL C implementation
~~~

So:

> **finite Meta unifies contracts; it does not turn container algorithms into macros.**

This is the core method of the book: as Meta matures, runtime C becomes more ordinary, not less.

CSTL can also compose directly into Graph/Stream without a second collection pipeline.

The snapshot README uses:

~~~c
typed(filter, value, bool, keep_even, (int value)) {
    return value % 2 == 0;
}

cflow_stream pipeline = {0};

stream(&values, &pipeline)
    ->filter(&pipeline, keep_even)
    ->distinct(&pipeline, 64u)
    ->sorted(&pipeline, 64u)
    ->skip(&pipeline, 1u)
    ->take(&pipeline, 10u);
~~~

This code composes three ownership boundaries:

~~~text
CSTL
    owns container storage / Range / collector

CMeta callable
    owns predicate signature and declared contract

CFlow
    owns Graph operator semantics and evaluation state
~~~

Adding a typed container does not require reimplementing Filter/Map. Adding a Graph operator does not require reimplementing Vec/List/Set.

### 4.3 TinyTest / TinyMock: Testing Infrastructure Reuses the Same Finite Typed Design

Testing frameworks repeat type dispatch too:

~~~text
check_int_equal
check_long_equal
check_double_equal
check_string_equal
check_pointer_equal
...
~~~

The edition TinyTest snapshot collapses this into strict-C11 generic assertions:

~~~c
#include "tinytest.h"

spec("strncmp") {
    it("should return 0 when strings are equal") {
        check(strncmp("foo", "foo", 12) == 0);
    }
}

check_equal(actual, expected);
check_not_equal(actual, expected);
check_greater(actual, expected);
check_within(actual, expected, margin);
~~~

A custom C value only needs to register the equality fact it requires:

~~~c
typedef struct Point {
    int x, y;
} Point;

static bool point_equal(const Point *actual, const Point *expected)
{
    return actual->x == expected->x && actual->y == expected->y;
}

#define TTEST_USER_EQUAL_TRAIT_LIST , (POINT, Point, point_equal)
#include "tinytest.h"

check_equal((Point){1, 2}, (Point){1, 2});
~~~

Production code is deliberately not required to depend on CMeta.

TinyTest reuses the same **finite trait-map design**:

~~~text
known value kinds
    ↓
_Generic admission
    ↓
typed comparator
    ↓
compiled test runtime
~~~

The reusable thing is not a macro name. It is the design method.

TinyMock extends the same strict-C11 trait map; runtime state, comparison, formatting, scripting, and verification live in the compiled TinyTest library, while headers retain only the wrapper generation that must occur at the call site.

A real mock usage remains small:

~~~c
#include "tinymock.h"

TINYMOCk_MOCK(int, add, int, int)

spec("calculator") {
    it("uses the expected dependency call") {
        mock_add_reset();

        mock_add_expect(
            TINYMOCk_ARG(2),
            TINYMOCk_ARG(3),
            TINYMOCk_RETURN(5));

        check_equal(add(2, 3), 5);

        mock_add_verify();
    }
}
~~~

There is no dynamic method table, scripting language, or runtime code generation. Function wrappers are generated in the test Translation Unit, while expectation queues and verification state remain ordinary compiled C runtime.

Resources are explicitly bounded, for example:

~~~c
#define TINYMOCk_MAX_ARGS 6
#define TINYMOCk_MAX_EXPECTATIONS 32
#define TINYMOCk_MAX_CALLS 32
#define TINYMOCk_MAX_SCRIPTS 32
~~~

Again, the same rule appears:

> **finite, explicit, call-site-required logic stays in headers; everything else returns to ordinary compiled C.**

CSTL and TinyTest can compose too. The snapshot provides `<cstl/tinytest.h>`:

~~~c
#include <cstl/typed.h>

typed(Vec, IntVec, int);

#include <cstl/tinytest.h>

CSTL_TINYTEST_DEFINE_SEQUENCE_EQUAL(IntVec, int)

check_cstl_equal(IntVec, actual, expected);
~~~

The comparator bridge borrows the container rather than copying an owning storage handle.

Testing is therefore not a separate story from CMeta/CSTL. It shows that the same typed identity / trait contract can be consumed safely across library boundaries.

## 5. The Shared Structure of All Five Cases

Serialization/Binding, RPC, Async I/O, CSTL, and Testing look very different.

Remove the domain details and the same method remains:

~~~text
1. Start from an existing Plain C problem
2. Separate semantic owners
3. Give stable knowledge one source of truth
4. Perform typed admission at boundaries
5. Make resource capacity explicitly bounded
6. Make ownership / lifetime explicit
7. Keep dynamic behavior only where required
8. Never hide failure through silent fallback
9. Formalize reusable semantic laws
10. Use real runtime/toolchain tests for evidence outside proof scope
~~~

So:

> **an advanced application is not “one more feature in Core”; it is a test of whether the primitive architecture actually composes.**

## 6. Extension Map: What Other Domains Should Reuse Without Entering Core

The following directions are worth exploring, but should default to upper-layer composition.

### 6.1 Plugin

Reuse:

~~~text
Semantic Type Identity
Interface
Capability
ABI version
Admission
Explicit Lifecycle
~~~

A new Core primitive belongs only after:

~~~text
the same stable contract repeats across multiple plugin domains
~~~

### 6.2 Event Bus / Command Bus

Reuse:

~~~text
Typed Event
Bounded Mailbox
Publisher/Subscriber
Executor
Actor refs
~~~

Bus-specific routing, fanout, retention, and delivery guarantees remain domain policy.

### 6.3 Workflow

Compose:

~~~text
Graph
Machine/Statechart
Actor
Timer
Executor
Persistence adapter
~~~

Retry / compensation / durability / lease remain explicit.

Workflow should not get:

~~~text
its own hidden thread runtime
its own type universe
~~~

### 6.4 ECS / Query

Reuse:

~~~text
Type identity
Traits
Range
Predicate
Typed Graph
Plan/Direct lowering
~~~

Component storage/layout/query planning remains ECS/domain implementation.

### 6.5 Parser / Protocol

Parser owns syntax/protocol grammar.

If output enters business dataflow:

~~~text
parser
    ↓
complete semantic event/value
    ↓
CFlow
~~~

Do not force:

~~~text
raw lexer token
~~~

to become a business Stream item merely for “uniformity.”

### 6.6 Device / UI / Service Runtime

Reuse:

~~~text
Typed Event
Machine/Statechart
Actor
Executor
Scheduler
Reactive
~~~

but device drivers, UI rendering, service discovery, and other domain meaning stay outside the CFlow kernel.

## 7. Application Admission Checklist

Before adding a new “advanced application,” answer ten questions:

~~~text
1. What is the Plain C version?
2. Which knowledge is truly repeated?
3. Which existing primitive already owns this semantic?
4. Are we creating a second Type/Identity system?
5. Are we creating a second Scheduler/Executor/Runtime?
6. Are ownership/capacity/cancel/terminal explicit?
7. Which errors cause callers to take different actions?
8. Which laws are worth proving in Lean?
9. Which facts can only be established by toolchain/runtime tests?
10. Can this feature stay in a higher layer instead of entering Core?
~~~

If the answer to 10 is:

~~~text
yes
~~~

then usually:

> **keep it in the upper layer first.**

Core stays stable by being:

~~~text
small
slow-changing
highly reused
explicitly bounded
~~~

not by accumulating features.

## 8. What We Learned

Chapter 13 does not prove:

~~~text
CMeta/CFlow can do everything
~~~

It proves:

> **a small set of well-bounded primitives can remove large amounts of duplicated foundational knowledge from advanced applications.**

Deep Case A shows:

~~~text
Concrete Format
    ↓
CSerde
    ↓
CBind + CMeta
    ↓
Native Value
    ↓
CFlow when needed
~~~

where:

~~~text
syntax
token grammar
semantic shape
native lifecycle
execution
~~~

each have one owner.

Deep Case B shows:

~~~text
CMeta/CSerde
    ↓
CRPC
    ↓
CHTTP
    ↓
CNet
    ↓
NativeIO
~~~

where RPC does not reinvent:

~~~text
type system
serializer
socket runtime
connection pool
retry policy
scheduler
~~~

but composes existing capabilities at the correct boundaries.

Engineering Cases C–E further show:

~~~text
Async I/O
    reuses WAIT/Wake + Executor + completion ownership

CSTL
    reuses typed(...) / Traits while algorithms remain compiled C

TinyTest/TinyMock
    reuse finite trait-map / _Generic admission while runtime remains compiled C
~~~

Together they demonstrate:

> **the value of finite Meta is not to unify every library into one framework, but to let different libraries share the same contract-design discipline while keeping the correct runtime owner for each domain.**

That is what mature Modern C infrastructure looks like:

~~~text
higher-level behavior increases

but

core primitives do not multiply at the same rate
~~~

The next chapter asks the inverse question:

> **When is this composition still not worth it? When are an ordinary C function pointer, a switch, or a for-loop simply better?**

That is the question of when to stop Meta.
