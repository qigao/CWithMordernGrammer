# Chapter 12: Engineering Boundaries — ABI, Multi-TU, Semantic Identity, and an Installable C Library

> **Chapter path**
>
> The previous eleven chapters answered “how do we design?” and “how do we prove?” This chapter asks a more practical question:
>
> **Do these capabilities still hold once they leave the source tree?**
>
> ~~~text
> One-TU prototype
>      ↓
> Multi-TU
>      ↓
> Static / Shared Library
>      ↓
> Install / Export
>      ↓
> External Consumer
>      ↓
> Cross-Compiler / Cross-Platform
>      ↓
> Stable semantic + ABI contract
> ~~~
>
> This chapter does not formalize ABI into something it is not. Lean can help define semantic identity; linker behavior, symbol visibility, package exports, SOVERSION, installed headers, and external-consumer behavior still require real toolchain evidence.

The previous chapters have built a fairly complete system:

```text
Macro
 ↓
Type
 ↓
Traits
 ↓
Generic
 ↓
Callable
 ↓
Graph
 ↓
Stream / Reactive
 ↓
Executor
 ↓
Machine / Actor
 ↓
Optimization
 ↓
Lean Proof
```

If we stop at those abstractions, the system is already interesting.

But a real C foundation library faces another test:

> **Can these designs survive outside a single-file demo and inside a real engineering environment?**

Real C engineering means:

```text
dozens or hundreds of .c files
multiple static / shared libraries
independently installed public headers
GCC / Clang / MSVC
Linux / Windows / macOS
Debug / Release
independently compiled translation units
```

Many designs that look perfectly sound in one source file suddenly expose problems here.

For example:

```text
Can Type Descriptor address be used as type identity?
Are header-generated objects the same across TUs?
Are Generic type names stable?
Should metadata live in headers or .c files?
Who owns generated headers?
Does Lean enter the ordinary consumer build?
Which module actually owns an abstraction?
```

These questions do not decide:

```text
how powerful CMeta is
```

They decide:

> **whether it can truly be a Library.**

---

## 1. A Single Translation Unit Hides Many Problems

Suppose everything lives in:

```text
main.c
```

Then:

```c
static const cmeta_type_desc user_type = { ... };
```

has one address everywhere:

```text
&user_type
```

It is easy to write:

```c
if (a == b) {
    /* same type */
}
```

In one TU:

```text
descriptor pointer equality
```

seems to work as:

```text
type equality
```

But split the code into:

```text
a.c
b.c
```

and the assumption breaks.

If a header contains:

```c
static const cmeta_type_desc int_vec_type = { ... };
```

then:

```text
a.c
```

has:

```text
int_vec_type @ 0x1000
```

while:

```text
b.c
```

has another:

```text
int_vec_type @ 0x9000
```

Both describe:

```text
the same Vec<int>
```

but:

```text
0x1000 != 0x9000
```

If:

```text
pointer equality
=
type equality
```

the type system fails immediately across Translation Units.

---

## 2. Address Is a Representation Location, Not Semantic Identity

This exposes a fundamental fact:

> **memory address is not semantic type identity.**

The same problem appears elsewhere too.

The same string may exist at two addresses in different modules.

The same schema may be instantiated independently by two shared libraries.

So a type must answer:

```text
"What are you?"
```

rather than:

```text
"Where are you stored right now?"
```

Therefore:

```text
Type Descriptor
```

and:

```text
Type Identity
```

must be separate.

---

## 3. Semantic Type Identity

For atomic types we may have:

```text
Atom(int)
Atom(double)
Atom(User)
```

For Pointer:

```text
Pointer(int)
Pointer(User)
```

For Generic:

```text
Generic(
    constructor = Vec,
    args = [int]
)
```

or:

```text
Generic(
    constructor = Map,
    args = [String, User]
)
```

The identity of:

```text
Vec<int>
```

is therefore not:

```text
descriptor address
```

but:

```text
constructor = Vec
argument[0] = int
```

So even if:

```text
TU A
```

and:

```text
TU B
```

each produce independent descriptors, equal:

```text
semantic identity
```

still means:

```text
same type
```

---

## 4. Semantic Identity Matters Especially for Generic Types

A simple:

```text
int
```

can still be represented with a global numeric type id.

The harder cases are:

```text
Vec<int>
Vec<double>
Map<int, User>
Option<Vec<int>>
```

If every application manually registers global integers such as:

```text
TYPE_VEC_INT = 1001
TYPE_VEC_DOUBLE = 1002
...
```

we recreate:

```text
registration explosion
```

A more natural identity is structural.

For example:

```text
Option<Vec<int>>
```

can be:

```text
Generic Option
    ↓
Generic Vec
    ↓
Atom int
```

a:

```text
Type Identity Tree
```

---

## 5. Identity and Descriptor Have Different Responsibilities

Separate them explicitly.

A Descriptor may contain:

```text
name
size
alignment
traits
runtime metadata
```

Identity contains:

```text
semantic equality
generic structure
stable relation
```

So:

```text
Descriptor
    mainly answers "how do I operate on this type?"

Identity
    mainly answers "is this semantically that type?"
```

A descriptor may point to identity.

Identity must not collapse to descriptor address.

---

## 6. This Is Part of ABI Design Too

ABI is often understood as:

```text
function calling convention
struct layout
symbol name
```

All are important.

But a library with runtime metadata also has:

```text
Semantic ABI
```

For example, do two modules agree about:

```text
Vec<int>
```

?

Do they agree about:

```text
Callable<int,long>
```

?

Do they assign the same bit to:

```text
Trait HASH
```

?

If these semantic structures are unstable, the linker may succeed while:

```text
the libraries still cannot interoperate correctly
```

ABI therefore includes more than:

```text
binary layout
```

It also includes:

```text
semantic contract
```

---

## 7. Header / Source Boundaries Must Be Reconsidered

Macro systems naturally drift toward:

```text
everything in header
```

because macros expand at the call site.

That does not mean:

```text
every runtime object
every function body
every registry
```

must also live in headers.

Declarations such as:

```text
Struct(...)
Enum(...)
typed(...)
```

may need header visibility.

But:

```text
registry storage
complex helper implementation
runtime lookup
large tables
```

can live in:

```text
.c
```

files.

This reduces:

```text
duplicate code
compile time
object file bloat
```

---

## 8. From Engineering Principles to Qualification

The first sections establish the core engineering problem: a single Translation Unit hides identity and ABI bugs; addresses are not semantic identity; descriptor, generic relation, and public representation need clear semantic authority; macro use must not turn into “everything header-only.”

The rest of the chapter therefore tests these principles at real boundaries: structural type identity, callable identity, static/shared images, versioned provider ABI, compile-time configuration, generated-artifact ownership, CMake install/export, independent consumers, Multi-TU, cross-compiler behavior, and ABI gates.

Where the current snapshot has real tests or package contracts, we identify the evidence. Where release/platform qualification is not yet complete, we describe the gate that should exist rather than claiming the guarantee already exists.

---

## 9. Case Study: Why Descriptor Address Cannot Be Type Identity

In a single Translation Unit the tempting implementation is:

~~~c
if (a_type == b_type) {
    /* same type */
}
~~~

If every descriptor comes from one global object, this may appear correct for a long time.

But once we have:

~~~text
header-local generated descriptors
static archive embedded into multiple DSOs
plugin/shared-library boundary
independent translation units
~~~

the same semantic type may have:

~~~text
descriptor object A
descriptor object B
~~~

with different addresses but identical meaning.

Therefore:

~~~text
pointer equality
    ≠
semantic type equality
~~~

This is Multi-TU/DSO correctness, not abstract purity.

### 9.1 Current CMeta Explicitly Separates Identity from Descriptor

The current type descriptor contains:

~~~text
name
size
align
kind
pointee
traits
identity
~~~

while `cmeta_type_identity` can express:

~~~text
ATOM(stable id)
POINTER(base identity)
CONST(base identity)
APPLY(generic constructor, arguments...)
~~~

Generic constructor itself also has:

~~~text
stable_id
display_name
min/max arity
category
~~~

So:

~~~text
Pair<int, long>
~~~

has structural semantic identity:

~~~text
APPLY(
    constructor = "cmeta.Pair",
    args = ["cmeta.int", "cmeta.long"]
)
~~~

rather than:

~~~text
address of one Pair descriptor
~~~

### 9.2 Structural Identity Has a Real Multi-TU Test

The current test does not compare two pointers created in one source file.

A peer Translation Unit returns an independently constructed identity:

~~~text
local Pair<A,B>
peer  Pair<A,B>
~~~

and validates:

~~~text
local identity address != peer identity address
local constructor address != peer constructor address

but

cmeta_type_identity_equal(local, peer) == true
~~~

This is the right kind of evidence for this chapter:

> **make two truly independent compilation units produce different representations, then verify semantic equality.**

### 9.3 Custom Trait Descriptor Must Also Stay Semantically Consistent Across TUs

Current CMeta tests also cover:

~~~text
custom owned_int descriptor in TU A
peer descriptor in TU B
~~~

Again, the goal is not descriptor pointer equality.

It is:

~~~text
same type semantics
same trait contract
cross-TU behavior remains valid
~~~

Otherwise Traits would be only a header-demo mechanism.

## 10. Callable Identity: Function Address Is Not One Universal Answer Either

Callable is more complex than Type because it may include:

~~~text
canonical raw target
adapter
generator
capture
effects
properties
signature
~~~

So Callable identity must first ask:

> Which dispatch representation is authoritative?

The current implementation distinguishes:

~~~text
CANONICAL_RAW
ADAPTER
~~~

and specifies:

~~~text
canonical-raw identity
    uses authoritative raw target across translation units

adapter identity
    uses adapter/generator pointers + capture bytes
~~~

### 10.1 Why Canonical Raw Works Across TUs

Suppose two Translation Units produce different wrappers/adapters:

~~~text
wrapper A address != wrapper B address
~~~

but both resolve to the same:

~~~text
authoritative raw C function
~~~

Semantic callable identity should not fail because wrappers differ.

Current tests cover:

~~~text
canonical callable identity across translation units by raw target
~~~

This is then consumed by:

~~~text
Graph structural equality
Optimizer duplicate detection
AOT Graph/Stage matching
Certificate checking
~~~

Callable identity is therefore not a local helper.

It is part of compiler/control-plane correctness.

### 10.2 Capturing Callable Must Include Capture in Identity

For:

~~~text
bind(multiply, 10)
bind(multiply, 20)
~~~

raw/adapter code may be identical, while captures differ.

They are not the same callable.

So the rule is not:

~~~text
always compare pointer
~~~

nor:

~~~text
never compare pointer
~~~

It is:

> **define equality according to the semantic authority of the representation.**

## 11. Static Library / Shared Library: Duplicate Globals Must Not Become Semantic Accidents

The current CMeta CMake setup contains an important engineering choice.

For the static CMeta archive:

~~~text
C_VISIBILITY_PRESET hidden
~~~

The reason is not merely “export fewer symbols.”

The comment explicitly notes that:

~~~text
a static CMeta archive may be embedded by Core
and multiple bridge DSOs

keep each image's immutable descriptors/helpers local

type compatibility is semantic,
not address-based
~~~

This is a mature ABI principle.

If semantic correctness depends on:

~~~text
one process-wide unique descriptor address
~~~

then embedding one static archive into two DSOs is inherently fragile.

The current direction is:

~~~text
duplicate representation objects may exist
      ↓
semantic identity still agrees
~~~

Symbol visibility becomes an encapsulation/optimization issue, not the source of type semantics.

## 12. Public Struct: Visible Does Not Mean Mutable or Stable-bytes ABI

A common C-library mistake is:

~~~text
struct is in public header
    ↓
every field is caller contract
~~~

That is false.

Chapter 7 already kept Graph as concrete IR for introspection, while Subscription / Actor live owners use opaque handles.

Public fields should be understood in three categories.

### 12.1 Stable Contract Fields

Examples:

~~~text
configuration rows
status/result structs
documented method pointers
semantic enum values
~~~

Callers may initialize/read them according to documentation.

### 12.2 Read-Only Introspection

Examples:

~~~text
Graph
Node
Edge
Subgraph
Plan input/output type
stats
~~~

Visibility exists for:

~~~text
diagnostics
verification
advanced tooling
~~~

not to let callers bypass builder mutation.

### 12.3 Internal Carrier

For example:

~~~text
void *impl
~~~

Even when visible in a public struct, it has no additional semantic meaning.

Callers must not:

~~~text
dereference
serialize
compare as identity
copy a live owner
use sizeof/offsetof as persistence protocol
~~~

The ABI philosophy should state:

> **C visibility is not semantic ownership.**

---

## 13. Versioned Provider ABI: Extensible Structs Need Admission Boundaries

A dangerous pattern for extensible provider/vtable APIs is:

~~~text
assume caller and library always share exactly the same struct layout
~~~

Current CMeta data descriptor/provider uses fields such as:

~~~text
struct_size
abi_version
~~~

A checked façade can first validate:

~~~text
provider ABI version
minimum struct prefix size
storage type identity
ownership/layout contract
required operations
~~~

before using optional appended fields.

This pattern works for:

~~~text
descriptor
provider ops
plugin ABI
extension interface
~~~

but must obey:

1. old prefix meaning must not silently change;
2. appended fields need version/size admission;
3. optional capability and required capability remain distinct;
4. current field presence must not imply future ABI guarantees;
5. public enum/status numeric values are ABI too.

## 14. CFlow SOVERSION: ABI Version Should Be a Real Library Artifact

The current CFlow library snapshot has:

~~~text
library version = 4.1.0
SOVERSION = 4
~~~

Windows shared builds also encode ABI major in the output name.

This matters.

A library exposing:

~~~text
public structs
enum values
function signatures
calling conventions
symbol names
ownership contracts
~~~

should not hide ABI breaks only in Git history.

It needs at least:

~~~text
library ABI major
package version
release compatibility policy
~~~

Of course:

> **SOVERSION does not automatically make an ABI stable.**

It merely gives incompatible boundaries a way to be expressed.

Real stability still comes from public API discipline and qualification.

## 15. Compile-Time Configuration Is Also Part of ABI

CMeta's finite signature universe and CFlow configured limits can enter the public compilation surface.

For example, CFlow exports Machine/Statechart limits as PUBLIC compile definitions:

~~~text
CFLOW_MACHINE_MAX_STATES
CFLOW_MACHINE_MAX_EVENTS
CFLOW_MACHINE_MAX_GUARDS
CFLOW_MACHINE_MAX_ACTIONS
CFLOW_MACHINE_MAX_TRANSITIONS
...
~~~

Consumer compilation must therefore see configuration consistent with the library contract.

Likewise, CMeta user relation/type lists are shared compile-time configuration.

The documentation explicitly requires:

> affected translation units must see consistent callable ABI/configuration.

Multi-TU correctness includes more than:

~~~text
same struct declaration
~~~

It includes:

~~~text
same finite signature universe
same compile-time configuration
same public feature/limit contract
~~~

If different TUs use different relation universes while exchanging callables/descriptors, a semantic bug can become an ABI bug.

## 16. Header / Source Boundary: Which Meta Must Stay at the Call Site?

A Modern C meta library should not become:

~~~text
everything header-only
~~~

nor:

~~~text
everything hidden in .c
~~~

The right boundary depends on where the necessary information exists.

### 16.1 What Must Remain in Headers / at the Call Site

Typical examples:

~~~text
_Generic selection
compile-time type assertion
finite macro specialization
typed wrapper generation
call-site C type inspection
~~~

because only the compiler at the call site knows:

~~~text
actual static C type
~~~

### 16.2 What Belongs in the Compiled C Library

Examples:

~~~text
container algorithms
Graph mutation/validation
Subscription runtime
Executor
Machine/Actor runtime
type identity comparison
optimizer
plan compiler
certificate checker
~~~

These do not need to be copied into every Translation Unit merely because the project uses Meta.

Therefore:

> **header-only typed façade does not imply header-only implementation.**

This matters for code size, ABI, compile time, and debugging.

## 17. Generated Artifact Ownership: A Fact Cannot Be Maintained by Lean and by Humans at the Same Time

Chapter 6 introduced:

~~~text
builtin_signature_manifest.h
builtin_operator_policy.h
machine_schema.h
~~~

These C headers are generated from formal sources/generators.

The engineering rule must be strict:

~~~text
formal model
    = authoritative source

generated header
    = checked-in build artifact

manual edit generated header
    = forbidden
~~~

Ordinary consumer builds:

~~~text
do not require Lean
~~~

CI / semantic development uses:

~~~text
generator --check
~~~

to verify no artifact drift.

This simultaneously gives:

~~~text
reproducible package
ordinary C consumer
single source of truth
reviewable generated diff
~~~

## 18. Install / Export: Linking in the Source Tree Is Not Enough

The edition Salts snapshot uses a normal CMake package/export boundary:

~~~text
SaltsConfig.cmake
SaltsConfigVersion.cmake
SaltsTargets.cmake
namespace Salts::
~~~

CMeta / CFlow export as:

~~~text
Salts::CMeta
Salts::CFlow
~~~

and install:

~~~text
public headers
library/archive/runtime artifact
package config
target export
~~~

A consumer should use:

~~~cmake
find_package(Salts CONFIG REQUIRED)

target_link_libraries(app PRIVATE
    Salts::CMeta
    Salts::CFlow)
~~~

This matters far more than:

~~~text
add_subdirectory(path/to/salts)
include_directories(source/tree)
link random .a file
~~~

because the install boundary exposes:

~~~text
missing public dependency
wrong include interface
private header leak
missing transitive target
wrong compile definition export
bad symbol visibility
source-tree-only path
~~~

### 18.1 CFlow Public Dependencies Must Be Exported Through Target Contract

Current CFlow link contract includes:

~~~text
PUBLIC
    Salts::CMeta
    Salts::NativeIO
    Salts::Platform

PRIVATE
    Salts::Concurrency
~~~

This is not CMake aesthetics.

It says:

> which dependencies are exported contract for external consumers of CFlow public headers/symbols, and which are implementation details.

If a PRIVATE dependency leaks into public ABI without export, source-tree builds may succeed while installed consumer linking fails.

### 18.2 Public Header Install Must Exclude Private Headers

Current CFlow install includes:

~~~text
install include/cflow/*.h
~~~

while explicitly excluding:

~~~text
plan_internal.h
relation_exec.h
~~~

This boundary matters:

> **a header existing in the repository does not make it part of the SDK.**

If a public header includes a private one accidentally, installed builds expose the mistake quickly.

## 19. Installed Consumer Qualification: The Gate Closest to a Real User

This book recommends installed-consumer testing as a formal gate rather than a manual pre-release smoke test.

A strong flow is:

~~~text
clean source checkout
    ↓
configure/build/test Salts
    ↓
install into empty prefix
    ↓
new independent consumer source tree
    ↓
find_package(Salts CONFIG REQUIRED)
    ↓
link only exported Salts::* targets
    ↓
include only installed headers
    ↓
build
    ↓
run
~~~

The consumer should cover at least:

~~~text
CMeta type/traits/callable
CFlow Graph/Stream
Multi-TU use
static build
shared build where supported
C and C++ header compatibility
~~~

Rules:

~~~text
no source-tree include path
no build-tree target
no undeclared private library
no generated source file copied manually
~~~

Only then can we claim:

> **the installable library is not just documentation; a user can consume a real SDK contract.**

## 20. Multi-TU Qualification Should Intentionally Create Different Representations

A weak Multi-TU test only proves:

~~~text
foo.c calls bar.c
~~~

That is not enough for Meta identity.

A strong test deliberately makes two TUs own independent representations.

### 20.1 Type Identity Test

~~~text
TU A:
    independently constructs Pair<A,B> identity

TU B:
    independently constructs Pair<A,B> identity

assert:
    addresses differ
    constructors may differ
    semantic equality true
~~~

The current CMeta implementation already has such a peer test.

### 20.2 Callable Identity Test

~~~text
TU A:
    canonical callable wrapper A

TU B:
    canonical callable wrapper B

assert:
    wrapper representation can differ
    authoritative raw target identity agrees
~~~

Current tests cover this too.

### 20.3 Generated Configuration Test

Also test:

~~~text
shared configuration header
    included consistently in TU A/TU B

callable signature ABI
    agrees across both
~~~

and add negative compile/link tests where possible:

~~~text
intentionally inconsistent configuration
    → fail fast
~~~

If the toolchain cannot diagnose reliably, document the configuration as explicitly unsupported instead of guessing at runtime.

## 21. Cross-Compiler: Core Semantics Must Not Depend on Accidental Extensions

CMeta can rely on:

~~~text
C11 _Generic
preprocessor
_Static_assert
standard alignment/type rules
~~~

and configure MSVC's conforming preprocessor mode where required.

But the book keeps one principle:

> **compiler extensions may optimize an implementation, but must not be the only basis of the semantic model.**

Extensions such as:

~~~text
GNU statement expression
typeof extension
compiler-specific section trick
~~~

may be optional fast paths.

Core type relations, callable semantics, and ABI contracts should still be expressible using the official mechanisms of supported target compilers.

Cross-compiler CI is not merely:

~~~text
"the syntax compiles everywhere"
~~~

It should validate:

~~~text
same declared semantics
same ownership/error contract
same installed API shape
~~~

across target compiler families.

## 22. ABI Qualification: Do Not Only Compare `sizeof(struct)`

ABI tests have at least four layers.

### 22.1 Compile ABI

~~~text
public headers compile as C11
public headers compile from supported C++ mode
macros do not depend on include accident
generated headers self-consistent
~~~

The current CFlow implementation already has public/header C++ compile tests; this category of gate should keep expanding.

### 22.2 Link ABI

~~~text
public symbol exists
calling convention matches
transitive dependency exported
static/shared consumer links
~~~

This is where installed consumers matter.

### 22.3 Semantic ABI

Even if function signatures stay identical, changes such as:

~~~text
FULL suddenly starts dropping
CLOSED becomes retryable
Actor stale ref becomes INVALID_ARGUMENT
Graph mutation stops changing version
~~~

are breaking behavior.

Therefore:

> **status meaning, ownership, lifecycle, ordering, and fallback are part of semantic ABI.**

### 22.4 Data ABI

For structs explicitly promised across binary boundaries:

~~~text
prefix fields
version
struct_size
enum values
alignment
ownership of pointed data
~~~

must be versioned intentionally.

Opaque owners such as:

~~~text
void *impl
~~~

exist precisely to keep internal layout out of ABI.

## 23. Fail Fast Across Boundaries: The Later the Error, the More Expensive It Is

The fail-fast principle appears across engineering layers:

~~~text
compile-time
    ↓
build-time
    ↓
install/package-time
    ↓
link-time
    ↓
admission-time
    ↓
execution-time
~~~

Rule:

> **if the same error can be found earlier, do not postpone it to a later boundary.**

Examples:

~~~text
unsupported TypeFunction row
    → compile-time

invalid Machine schema
    → build-time

generated manifest drift
    → CI/generator check

missing public link dependency
    → installed consumer link

wrong Event payload
    → admission

I/O failure
    → execution
~~~

Turning every error into:

~~~text
runtime error string
~~~

is not “a simpler API.”

It only transfers diagnostic cost to the user.

## 24. What We Learned

Chapter 12 brings all earlier “advanced” capability back into ordinary C engineering reality.

A mature Modern C abstraction requires all of these to hold:

~~~text
semantic identity
    does not depend on representation address

Multi-TU
    sees compatible finite configuration

public ABI
    separates stable/read-only/internal fields

generated artifacts
    have one authority

ordinary build
    does not require Lean

static/shared libraries
    do not rely on duplicate-global coincidence

install/export
    publishes real dependency contracts

external consumer
    builds only from installed SDK

cross-compiler
    preserves core semantics

status/ownership/lifecycle
    are treated as semantic ABI
~~~

The edition Salts snapshot already contains substantial engineering evidence:

~~~text
structural type identity
cross-TU identity tests
cross-TU callable tests
CMake install/export
Salts::* imported targets
CFlow SOVERSION
public/private install headers
generated-header CI checks
public-header compile checks
~~~

Mature qualification should continue to treat:

~~~text
independent installed consumer
static/shared matrix
negative ABI/config tests
platform/toolchain matrix
release compatibility
~~~

as formal gates.

Lean's role is also clear here.

It can help define:

~~~text
semantic identity
finite schema
generated manifest
protocol invariants
~~~

but:

~~~text
linker
loader
symbol visibility
CMake package export
compiler ABI
shared-library resolution
~~~

must be validated with real toolchains.

This is not a weakness of formal methods.

It is:

> **the right question should be answered with the right evidence.**

The next chapter stops adding foundational mechanisms.

It asks instead:

> **Once Type, Callable, Graph, Reactive, Machine, Actor, Lean-backed proofs, and a stable library boundary exist, how can these primitives compose into real applications such as Serialization, RPC, Workflow, CSTL, and testing infrastructure?**
