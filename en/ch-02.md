# Chapter 2: From Macros to Generic — Collapse Repeated Type Contracts into One Definition

> **This chapter solves one C problem only:**
>
> The same “type fact” gets written again and again across typedefs, macros, containers, comparison functions, descriptors, dispatch, serialization, and callback boundaries.
>
> Look at the code first. Discuss abstractions second.

Chapter 1 showed that macros are very useful at first:

~~~c
#define DECLARE_BUFFER(T, Name) \
    typedef struct Name {       \
        T *data;                \
        size_t size;            \
        size_t capacity;        \
    } Name
~~~

They can collapse a repeated declaration into one line.

The real problem appears as the project grows. We no longer have only one Buffer. We now have families such as List, Vec, Pair, Option, Result, HashMap, Callback, Range, and Collector: APIs with the same shape but different types.

At that point, what repeats is no longer just a few lines of C. What repeats is:

~~~text
what is this type called?
what is its element type?
which operations belong to it?
which capabilities does it support?
how is it recognized by another module?
how is its wrapper generated?
~~~

These are **contracts**.

The goal of this chapter is not to create more sophisticated macros. It is to pull these contracts back into a small, unified, finite set of definitions.

---

## 1. Plain C: The First Type Is Usually Easy to Write

Suppose we need a dynamic array of integers.

The most direct C is perfectly fine:

~~~c
typedef struct IntVec {
    int *data;
    size_t size;
    size_t capacity;
} IntVec;

bool IntVec_init(IntVec *v, size_t capacity);
bool IntVec_push_back(IntVec *v, int value);
int *IntVec_at(IntVec *v, size_t index);
void IntVec_destroy(IntVec *v);
~~~

If the program needs only this one type, stopping here is the correct answer.

Then the project also needs:

~~~c
typedef struct DoubleVec {
    double *data;
    size_t size;
    size_t capacity;
} DoubleVec;

bool DoubleVec_init(DoubleVec *v, size_t capacity);
bool DoubleVec_push_back(DoubleVec *v, double value);
double *DoubleVec_at(DoubleVec *v, size_t index);
void DoubleVec_destroy(DoubleVec *v);
~~~

Later:

~~~c
typedef struct User {
    int id;
    double score;
} User;

typedef struct UserVec {
    User *data;
    size_t size;
    size_t capacity;
} UserVec;

bool UserVec_init(UserVec *v, size_t capacity);
bool UserVec_push_back(UserVec *v, User value);
User *UserVec_at(UserVec *v, size_t index);
void UserVec_destroy(UserVec *v);
~~~

The duplicated part is not really the push_back algorithm.

That algorithm can exist only once.

What repeats is:

~~~text
IntVec binds int
DoubleVec binds double
UserVec binds User

and, for each binding:
type
wrapper
function names
descriptor
traits
range adapter
collector adapter
~~~

Once these repeated contracts spread across a codebase, maintaining them quickly costs more than maintaining the algorithm itself.

---

## 2. The First Reaction: Write “Smarter Macros”

The most natural next step is usually:

~~~c
#define DECLARE_VEC(Name, T)            \
    typedef struct Name {               \
        T *data;                        \
        size_t size;                    \
        size_t capacity;                \
    } Name;                             \
    bool Name##_init(Name *, size_t);   \
    bool Name##_push_back(Name *, T);   \
    T *Name##_at(Name *, size_t);       \
    void Name##_destroy(Name *)

DECLARE_VEC(IntVec, int);
DECLARE_VEC(DoubleVec, double);
DECLARE_VEC(UserVec, User);
~~~

This really does reduce repetition.

But soon the project contains another group of macros:

~~~c
#define DECLARE_OPTION(Name, T) ...
#define DECLARE_PAIR(Name, K, V) ...
#define DECLARE_HASHMAP(Name, K, V) ...
#define DECLARE_RESULT(Name, T, E) ...
~~~

Then each library introduces its own entry point:

~~~c
LIST_OF(int, IntList);
VEC_OF(User, UserVec);
PAIR_OF(int, User, UserById);
OPTION_OF(User, MaybeUser);
~~~

Superficially, the project is now “generic.”

But the user has to remember:

~~~text
which macro corresponds to each Generic kind
what the argument order is
where the generated name goes
which header registers which family
~~~

The macros themselves become another duplicated interface.

What needs to be unified is not macro-expansion machinery. It is:

> **the Generic declaration entry point.**

---

## 3. The First Value of Generic: One Entry Point for Different Macro Families

The public entry point in this CMeta design is:

~~~c
typed(kind, generated_name, type_arguments...);
~~~

For CMeta value kinds:

~~~c
#include <cmeta/meta.h>

typedef struct User {
    int id;
} User;

typed(Option, MaybeUser, User);
typed(Pair, UserScore, User, double);
typed(Tuple, Point3, double, double, double);
~~~

CSTL uses the same entry point for its container kinds:

~~~c
#include <cstl/typed.h>

typed(List, IntList, int);
typed(Vec, IntVec, int);
typed(HashMap, IntValuesById, int, int);
~~~

The user no longer chooses among `DECLARE_LIST`, `DECLARE_VEC`, `DECLARE_HASHMAP`, `DECLARE_OPTION`, and `DECLARE_PAIR`; the user writes only `typed(kind, name, ...)`.

This is not mainly about prettier syntax.

It solves a more practical problem:

> **the whole project has one Generic declaration protocol.**

---

## 4. What `typed(...)` Actually Does Is Small

The real generic routing core is short:

~~~c
#define CMETA_TYPED_GENERIC_I(kind, ...) \
    CMETA_PP_CAT(CMETA_TYPED_, kind)(__VA_ARGS__)

#define CMETA_TYPED_GENERIC(kind, ...) \
    CMETA_TYPED_GENERIC_I(kind, __VA_ARGS__)

#define CMETA_TYPED_ROUTE_1(kind, ...) \
    CMETA_TYPED_GENERIC(kind, __VA_ARGS__)

#define CMETA_TYPED_ROUTE_0(kind, ...) \
    CMETA_TYPED_FALLBACK(kind, __VA_ARGS__)

#define typed(kind, ...) \
    CMETA_TYPED_ROUTE(kind, __VA_ARGS__)
~~~

A library only has to register a finite set of Generic kinds.

So:

~~~c
typed(Vec, IntVec, int);
~~~

eventually routes to the implementation for that kind, `CMETA_TYPED_Vec(IntVec, int)`.

The actual container algorithm can still be ordinary compiled C.

In other words:

~~~text
Generic declaration
        ↓
generate typed wrapper / metadata
        ↓
call ordinary C algorithm
~~~

not “copy a complete runtime implementation for every `T`.” That is the fundamental difference between finite Generic and “templating the whole program.”

---

## 5. Before and After: The Repetition Is in the Type Contract, Not the Container Algorithm

Without Generic, call sites may look like this:

~~~c
IntVec ints = {0};
UserVec users = {0};

IntVec_init(&ints, 64);
UserVec_init(&users, 64);

IntVec_push_back(&ints, 7);

User u = {.id = 42};
UserVec_push_back(&users, u);

IntVec_destroy(&ints);
UserVec_destroy(&users);
~~~

There is nothing wrong with this code.

The problem is that in order to get these APIs, we often maintain two independent declaration contracts.

With one finite Generic declaration:

~~~c
#include <cstl/typed.h>

typed(Vec, IntVec, int);
typed(Vec, UserVec, User);

int main(void)
{
    IntVec ints = {0};
    UserVec users = {0};

    IntVec_init(&ints, 64u);
    UserVec_init(&users, 64u);

    IntVec_push_back(&ints, 7);

    User u = {.id = 42};
    UserVec_push_back(&users, u);

    IntVec_destroy(&ints);
    UserVec_destroy(&users);
}
~~~

The call side still uses concrete, ordinary, debuggable C names:

~~~text
IntVec_init
IntVec_push_back
UserVec_push_back
~~~

Generic is mostly a declaration-time mechanism.

It does not require the runtime to become a “dynamic template system.”

---

## 6. The Generated Target Should Still Look Like Ordinary C

For:

~~~c
typed(Vec, IntVec, int);
~~~

the generated result can be understood **conceptually** as:

~~~c
typedef struct IntVec {
    cstl_vec raw;
} IntVec;

static inline bool
IntVec_push_back(IntVec *self, int value)
{
    return cstl_vec_push_back(&self->raw, &value);
}
~~~

This is not a byte-for-byte expansion from the current source snapshot. The design must preserve three parts: **a concrete C type, a concrete typed wrapper, and a shared ordinary C implementation**.

That is why later chapters do not keep repeating “the macro eventually generates C.”

That is only the basic mechanism.

The more important question is:

> **Once we have a unified, finite, typed Generic declaration, which previously scattered contracts can become one definition?**

---

## 7. The Second Kind of Repetition: Struct Definition and Metadata Definition Drift Apart

Consider a common engineering pattern:

~~~c
typedef struct User {
    int id;
    double score;
} User;

typedef struct FieldInfo {
    const char *name;
    size_t offset;
    size_t size;
} FieldInfo;

static const FieldInfo user_fields[] = {
    {"id",    offsetof(User, id),    sizeof(int)},
    {"score", offsetof(User, score), sizeof(double)},
};
~~~

Here `id`, `score`, `int`, and `double` are written twice.

Add a serializer, binding layer, or debug printer and the same facts may be written a third or fourth time.

A typical bug looks like this:

~~~c
typedef struct User {
    long id;
    double score;
} User;

/* forgotten */
static const FieldInfo user_fields[] = {
    {"id", offsetof(User, id), sizeof(int)},
};
~~~

The problem is not that C cannot express a struct.

The problem is:

> **the same field fact is maintained independently by several systems.**

---

## 8. `Struct(...)`: Write Structure Facts Once

CMeta's application DSL can express those facts directly:

~~~c
Struct(User,
    (int, id),
    (double, score)
);
~~~

The same row data can then generate the C struct declaration, field metadata, field count, field lookup, and descriptor-facing structure information.

Normal call-side code still uses:

~~~c
User user = {
    .id = 7,
    .score = 98.5
};

printf("%d %.1f\n", user.id, user.score);
~~~

The value of Meta here is not merely “one fewer typedef.” It is that **User fields have one authoritative source**.

When later layers such as Data Binding, debug tooling, or RPC schema adapters need structural information, they do not need to invent separate `UserSchema`, `UserJsonFields`, or `UserDbColumns`.

This is the recurring theme of Part I:

> **finite Meta first removes duplicated knowledge.**

---

## 9. The Third Kind of Repetition: Capabilities and Function Slots Drift Too

Ordinary C can easily produce:

~~~c
typedef struct UserOps {
    bool (*equal)(const User *, const User *);
    uint64_t (*hash)(const User *);
    void (*destroy)(User *);
} UserOps;

enum {
    USER_CAN_EQUAL   = 1u << 0,
    USER_CAN_HASH    = 1u << 1,
    USER_CAN_DESTROY = 1u << 2
};

static const UserOps user_ops = {
    .equal = user_equal,
    .hash = user_hash,
    .destroy = user_destroy
};
~~~

The capability flags and function slots are maintaining the same facts: User supports equal, hash, and destroy. If one side is not updated, the contract can become false.

---

## 10. `Traits(...)`: Generate Capabilities and Function Slots from the Same Row

The current CMeta Traits form is:

~~~c
Traits(User,
    (equal, user_equal),
    (hash, user_hash),
    (destroy, user_destroy)
);
~~~

The implementation derives both **trait flags** and **function slots** from the same tagged rows.

So the one fact `(equal, user_equal)` determines both that `CMETA_TRAIT_EQUAL` is present and that `traits.equal = user_equal`. We no longer get “flag says HASH but hash function slot is NULL.”

This is exactly the kind of C problem Meta is good at solving:

> **two declarations that must change together should come from one source of truth.**

---

## 11. `_Generic` Is Useful, but It Is Not a Complete Generic Design

C11 already has:

~~~c
_Generic
~~~

For example:

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                    \
    double: print_double               \
)(x)
~~~

It can perform compile-time selection.

But it can only select among expressions/functions that already exist. It does not automatically solve:

- how a Generic kind is instantiated;
- how different libraries share one generic declaration syntax;
- where descriptors come from;
- how traits are associated with generated types;
- how a Generic application gets an identity.

So `_Generic` is a tool, whereas `typed(kind, ...)`

is an engineering-level Generic protocol.

They operate at different layers.

---

## 12. A Finite Type Universe: Handle Only Types We Explicitly Support

CMeta does not try to “reflect arbitrary C types.”

It maintains a finite known/callable type universe.

Call sites can use:

~~~c
const cmeta_type_desc *desc = CMETA_TYPEOF(int);
~~~

rather than:

~~~text
parse a runtime string "int"
~~~

For an unregistered type, the system does not guess.

This fits C well:

~~~text
supported type set
    is finite

unsupported type
    fails explicitly
~~~

Finiteness is not a weakness.

It keeps:

~~~text
dispatch
descriptor
signature family
generic relation
ABI
compile diagnostics
~~~

under control.

---

## 13. Generic Identity: A Descriptor Address Is Not “the Type Itself”

If the same Generic type can generate header-local metadata in different Translation Units:

~~~text
TU A: descriptor A for Pair<int,double>
TU B: descriptor B for Pair<int,double>
~~~

their addresses may legitimately differ.

So we cannot write:

~~~c
if (a_desc == b_desc) {
    /* same semantic type */
}
~~~

We must compare semantic identity.

This is a key transition from “macro demo” to real C library:

> **the address of a generated object is a representation detail, not semantic type identity.**

The ABI/Multi-TU chapter will return to this issue later.

---

## 14. The Fourth Kind of Repetition: Type Relations Become Repeated `if` / `_Generic` Logic

Suppose we want a small common-arithmetic relation:

~~~text
int + int       -> int
int + double    -> double
double + int    -> double
double + double -> double
~~~

Ordinary C can write:

~~~c
enum TypeId {
    TYPE_INT,
    TYPE_DOUBLE
};

enum TypeId common_type(enum TypeId a, enum TypeId b)
{
    if (a == TYPE_INT && b == TYPE_INT)
        return TYPE_INT;

    if (a == TYPE_INT && b == TYPE_DOUBLE)
        return TYPE_DOUBLE;

    if (a == TYPE_DOUBLE && b == TYPE_INT)
        return TYPE_DOUBLE;

    if (a == TYPE_DOUBLE && b == TYPE_DOUBLE)
        return TYPE_DOUBLE;

    abort();
}
~~~

If compile-time code needs the same relation, we write another `_Generic` or macro table.

The relation is duplicated across:

~~~text
compile-time relation
runtime/admission relation
documentation
tests
~~~

---

## 15. `TypeFunction(...)`: Write a Finite Type Relation as Data

CMeta can declare:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);

typedef TypeEval(CommonArithmetic, int, double) result_type;
~~~

The important thing is the row:

~~~text
(int, double, double)
~~~

It is an explicit relation.

There is no hidden inference.

There is no default branch.

There is no “best effort conversion.”

If:

~~~text
(long, User, ???)
~~~

does not exist, the relation should fail at the correct boundary.

---

## 16. `ValueFunction` / `Predicate`: The Same Method Expresses Capabilities

For example:

~~~c
ValueFunction(TypeRank,
    (int, 1),
    (double, 2)
);

enum {
    int_rank = ValueEval(TypeRank, int),
    double_rank = ValueEval(TypeRank, double)
};
~~~

Or:

~~~c
Predicate(Hashable,
    (int, 1),
    (double, 1),
    (opaque, 0)
);

Require(Hashable, int);
~~~

For a finite C system, this already covers many relations that would otherwise be scattered across:

~~~text
#ifdef
_Static_assert
_Generic
macro specialization
manual lookup table
~~~

---

## 17. Why “No Default” Is Often an Advantage

Suppose:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double)
);
~~~

and then:

~~~c
typedef TypeEval(CommonArithmetic, User, double) bad_type;
~~~

CMeta does not:

~~~text
fallback to void *
fallback to int
try best conversion
~~~

A missing row is itself a fact:

> **this relation is undefined.**

In systems programming, fail-fast behavior is often safer than an intelligent default.

A default can turn:

~~~text
a design omission
~~~

into:

~~~text
runtime behavior
~~~

## 18. A Complete Before / After: Several Generic Families

Suppose an application needs:

~~~text
List<int>
Vec<int>
Option<int>
Pair<int,double>
~~~

If each library has its own macro grammar, we may get:

~~~c
DECLARE_LIST(IntList, int);
DECLARE_VEC(IntVec, int);
DECLARE_OPTION(MaybeInt, int);
DECLARE_PAIR(IntDouble, int, double);
~~~

Different projects may even use different argument orders:

~~~c
MAKE_LIST(int, IntList);
VEC_DECLARE(IntVec, int);
OPTION_OF(int, MaybeInt);
PAIR_OF(int, double, IntDouble);
~~~

A maintainer now has to remember four small “languages.”

After unification:

~~~c
#include <cmeta/meta.h>
#include <cstl/typed.h>

typed(List, IntList, int);
typed(Vec, IntVec, int);
typed(Option, MaybeInt, int);
typed(Pair, IntDouble, int, double);
~~~

The value is not a few fewer characters.

It is:

~~~text
all finite generic declarations
share one grammar
~~~

Adding a new library Generic kind no longer requires teaching users another top-level macro language.

---

## 19. The CMeta Boundary: Generic Should Not Own Algorithms

This is an easy place to go too far.

If:

~~~c
typed(Vec, IntVec, int);
~~~

causes:

~~~text
a complete vec algorithm to be copied
a complete allocator policy to be copied
a complete sort/search implementation to be copied
~~~

then Generic quickly becomes a code-bloat generator.

A better boundary is:

~~~text
typed declaration
    owns:
        type-safe surface
        names
        metadata
        adapters

ordinary C library
    owns:
        allocation
        growth
        search
        sort
        storage algorithm
~~~

This keeps Generic as an interface/code-generation layer rather than another runtime.

---

## 20. What This Solves: CSTL Is the Most Direct Engineering Example

Traditional C container APIs often choose between two approaches.

The first is fully erased:

~~~c
vec_push(&v, &value, sizeof(value));
~~~

Its strength is algorithm reuse.

Its weakness is that:

~~~text
sizeof
cast
element type
operation naming
~~~

are maintained by the caller.

The second copies a container implementation per type.

Its strength is typed call sites.

Its weakness is duplicated code and contracts.

Finite Generic combines the two:

~~~c
typed(Vec, UserVec, User);

UserVec users = {0};

UserVec_init(&users, 64u);
UserVec_push_back(&users, (User){.id = 7});
User *u = UserVec_at(&users, 0u);
UserVec_destroy(&users);
~~~

The typed wrapper preserves static type information.

The underlying algorithm remains a shared ordinary-C implementation.

This is what this book means by:

> **improve C with finite Meta rather than escaping from C.**

---

## 21. The More Important Result: Higher Layers Can Trust That a Type Fact Exists Once

When CFlow later sees:

~~~text
Map<int, double>
~~~

it should not create another universe such as:

~~~text
FlowTypeInt
FlowTypeDouble
~~~

When CBind sees `User`, it should not create `BindUserSchema`.

When RPC sees request/response types, it should not create a third type universe.

This is where the deeper value of CMeta appears:

> **higher-level systems can reuse the same finite type / trait / generic / identity contract.**

That directly affects the design complexity of Graph, Stream, State Machine, Actor, Serialization, and RPC.

## 22. How to Validate This Chapter: C / Toolchain Evidence

The engineering evidence for this chapter is deliberately ordinary.

### Compile Success

~~~c
typed(Option, MaybeInt, int);
typed(Pair, IntDouble, int, double);
~~~

should generate valid C on supported compilers.

### Compile Failure

Wrong kind, wrong arity, missing relation, and duplicate trait tags should:

~~~text
fail early
~~~

rather than fall into runtime guessing.

### Multi-TU

Two Translation Units may contain different representation objects, while semantic type identity must still agree.

### Installed Consumer

A user who includes only installed headers and links exported targets should be able to use the same Generic API.

These are C/toolchain questions.

## 23. From Generic to Callable: The Next Repeated Contract Is Behavior

At this point we have unified facts for:

~~~text
data type
container application
traits
finite relation
descriptor
~~~

The next problem is harder.

An ordinary C callback may be only:

~~~c
int (*fn)(int);
~~~

or:

~~~c
void (*fn)(void *);
~~~

But a higher-level execution system may need to know:

~~~text
input type
output type
capture/context
ownership
effects
properties
dispatch authority
~~~

If those facts are also maintained separately as:

~~~text
function pointer
manual enum
manual context struct
manual flags
~~~

we are back at the opening problem of this chapter:

> **the same behavior contract is written several times.**

So the next chapter is not about writing more macros.

It asks:

> **How can a function itself become a finite, typed, composable C value?**

That is the starting point for Callable, Lambda, and Bind.

---

## 24. What We Learned

The most important lesson in this chapter is not a macro trick.

It is four engineering conclusions.

First:

> **macros become hard to maintain not because there are too few macros, but because different macro families begin to maintain the same contract.**

Second:

> **the first value of Generic is a unified declaration protocol, not imitation of C++ templates.**

Third:

> **Struct, Traits, typed, and TypeFunction should all collapse “the same fact written many times” into one source of truth.**

Fourth:

> **the resulting API, data layout, and algorithms should remain ordinary C wherever possible.**

The chapter can be compressed into:

~~~text
duplicated C declarations
        ↓
duplicated macro families
        ↓
one finite Generic protocol
        ↓
single-source type/trait/relation facts
        ↓
ordinary typed C API
~~~

That is the real problem CMeta begins to solve.
