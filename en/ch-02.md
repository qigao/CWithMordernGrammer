# Chapter 2: From Macros to Generic — Collapse Repeated Type Contracts into One Definition

> Chapter 1 removed repeated code shape. This chapter asks the next question: when the same type fact is consumed by containers, Struct metadata, Traits, TypeFunction, and later compilers, how can it be written once?

---

## 1. From Plain C to One Generic Entry Point

Ordinary C often defines several concrete types for one algorithm family:

~~~c
typedef struct IntVec {
    int *data;
    size_t size;
    size_t capacity;
} IntVec;

typedef struct DoubleVec {
    double *data;
    size_t size;
    size_t capacity;
} DoubleVec;
~~~

As the library grows to List, Option, Pair, and HashMap, several declaration grammars appear.

The goal is not to emulate templates. It is to unify the declaration entry point:

~~~c
typed(Vec, IntVec, int);
typed(Vec, DoubleVec, double);
typed(Option, MaybeUser, User);
~~~

One declaration fixes at least three facts:

- Generic kind: Vec / Option;
- concrete C name: IntVec / MaybeUser;
- element/application type: int / User.

Call sites still use ordinary concrete C names such as IntVec_init, IntVec_push_back, and MaybeUser_has_value.

Generic mostly belongs to the declaration/build plane; it does not require a dynamic hot-path runtime.

## 2. Struct: Give Field Facts One Source of Truth

Plain C:

~~~c
typedef struct User {
    uint64_t id;
    const char *name;
    double score;
} User;
~~~

If DataBind, debug tooling, Mock, and schema tooling all need field information, a second handwritten metadata table will drift.

Write field facts as rows:

~~~c
Struct(User,
    (uint64_t, id),
    (const char *, name),
    (double, score)
);
~~~

The same rows can generate:

- the C struct declaration;
- field count;
- field descriptors;
- field lookup;
- descriptor-facing structural information.

The point is not fewer typedefs. It is:

> User fields have one authoritative source.

If a field disappears, all generated artifacts that depend on it should change together instead of relying on a developer to update five separate tables.

## 3. Traits: Generate Capability and Function Slots from One Fact

A fragile design maintains capability flags and function pointers separately:

~~~c
traits.flags =
    TRAIT_EQUAL |
    TRAIT_HASH |
    TRAIT_DESTROY;

traits.equal = user_equal;
traits.hash = user_hash;
traits.destroy = user_destroy;
~~~

The same fact is written twice.

A better input is tagged rows:

~~~c
Traits(User,
    (equal, user_equal),
    (hash, user_hash),
    (destroy, user_destroy)
);
~~~

The generator derives:

~~~c
flags |= TRAIT_EQUAL;
traits.equal = user_equal;
~~~

and the other rows.

That removes internal drift such as “flag says HASH but hash slot is NULL.”

Traits remain a finite capability set; they do not need to become a dynamic object model.

## 4. Finite Type Universe and Generic Identity

A type descriptor may look like:

~~~c
typedef struct cmeta_type_desc {
    uint64_t semantic_id;
    const char *name;
    size_t size;
    size_t align;
    uint32_t kind;
} cmeta_type_desc;
~~~

The important rule is semantic identity, not pointer equality.

Different Translation Units may each construct a Pair<int,double> descriptor:

~~~text
TU A descriptor address != TU B descriptor address
~~~

If the Generic constructor and arguments are the same, they should denote the same semantic type.

Generic application identity can be modeled as:

~~~text
identity(Vec<int>)
    =
GenericConstructorId(Vec)
+
identity(int)
~~~

and for Pair:

~~~text
identity(Pair<int,double>)
    =
GenericConstructorId(Pair)
+
identity(int)
+
identity(double)
~~~

This lets Multi-TU, DSO, Plugin, and generated code compare meaning instead of betting on one unique descriptor address.

Keep the admitted universe finite:

> the supported type set is finite; unsupported types fail explicitly.

Finiteness keeps dispatch, diagnostics, ABI, and proof boundaries controllable.

## 5. TypeFunction: Make Finite Type Relations Data

Many C systems need finite relations such as CommonArithmetic:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

One row:

~~~text
(int, double, double)
~~~

means:

~~~text
CommonArithmetic(int, double) = double
~~~

This is not a secret compiler and does not perform best-effort conversion.

If there is no row such as:

~~~text
(long, User, ???)
~~~

then the relation does not exist and should fail explicitly at compile/admission.

The rule is:

~~~text
lookup(Relation, args)
    = exactly one row
        -> result

lookup(Relation, args)
    = no row
        -> UNSUPPORTED

lookup(Relation, args)
    = multiple rows
        -> INVALID_DEFINITION
~~~

This is easier to inspect and formalize than scattered _Generic, #ifdef, or manual lookup tables.

## 6. From Several Generic Families to an Engineering Boundary

Generic should not copy a complete runtime algorithm for every T.

The desired shape is:

~~~text
typed(Vec, IntVec, int)
      ↓
concrete C wrapper
      ↓
shared ordinary C implementation
~~~

A wrapper may handle size, cast, and descriptor only:

~~~c
static inline bool
IntVec_push_back(IntVec *v, int value)
{
    return vec_push_back_raw(
        &v->raw,
        &value,
        sizeof(value),
        CMetaType(int));
}
~~~

The real growth, allocation, and move algorithms remain shared.

This prevents Generic from turning into a code-bloat generator.

The engineering boundary stays explicit:

- declarations/type wrappers may be generated;
- shared algorithms should be compiled once where practical;
- ownership and allocator policy stay explicit;
- unsupported Generic kind/arity fails;
- Generic does not introduce hidden allocation or dynamic dispatch.

## 7. Evidence: C / Toolchain Qualification

This layer primarily needs toolchain evidence, not Lean standing in for the compiler.

### 7.1 Compile-Pass

Valid Generic declarations must compile independently.

### 7.2 Compile-Fail

Wrong kind, wrong arity, missing TypeFunction row, and duplicate Trait tag must fail early.

### 7.3 Multi-TU

Two Translation Units may each obtain a descriptor for the same semantic type:

~~~c
const cmeta_type_desc *a = pair_type_from_tu_a();
const cmeta_type_desc *b = pair_type_from_tu_b();

assert(a != b);
assert(cmeta_type_equal(a, b));
~~~

### 7.4 Cross-Compiler

Cover at least GCC, Clang, and MSVC-compatible mode, especially variadic-macro behavior, _Generic, alignment/layout assumptions, and generated public headers.

### 7.5 Code Size / Performance

Compare handwritten and generated wrappers; verify that Generic instantiation does not duplicate large algorithms unnecessarily.

## 8. From Generic to Callable

At this point data types, container applications, Traits, finite relations, and descriptors share one native semantic source.

One class of stable facts is still duplicated:

- function input/output type;
- parameter direction;
- capture/context;
- ownership;
- effects;
- semantic properties;
- dispatch authority.

If those remain scattered across a function pointer, manual enum, context struct, and flags, we recreate the problem this chapter just solved.

The next chapter applies the same method to behavior:

~~~text
ordinary function pointer
      ↓
FunctionDesc
      ↓
admitted executable shape
      ↓
Callable / exact adapter
~~~

## 9. What We Learned

The chapter's real progression is:

~~~text
repeated type facts
      ↓
single-source rows
      ↓
generated ordinary C
      ↓
shared native semantic identity
~~~

The pieces are:

| Problem | Object |
|---|---|
| Generic application | typed(kind, ...) |
| Struct fields | Struct rows |
| capability | Traits rows |
| finite relation | TypeFunction |
| cross-TU meaning | semantic type identity |

All of them still serve ordinary C.

The next chapter continues the same rule: **define the stable semantics of a native function once.**
