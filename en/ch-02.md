# Chapter 2: From Macros to Generics — Collapsing Repeated Type Contracts into One Definition

> **This chapter solves one C problem only:**
>
> The same “type fact” gets written repeatedly across typedefs, macros, containers, comparison functions, descriptors, dispatch, serialization, and callback boundaries.
>
> Start with code. Discuss abstraction afterward.

Chapter 1 showed why macros are initially so useful:

~~~c
#define DECLARE_BUFFER(T, Name) \
    typedef struct Name {       \
        T *data;                \
        size_t size;            \
        size_t capacity;        \
    } Name
~~~

A repeated declaration collapses into one line.

The real problem appears when the project grows. We no longer have one Buffer. We have List, Vec, Pair, Option, Result, HashMap, Callback, Range, Collector, and other families of APIs that are structurally similar but parameterized by different types.

At that point the duplication is no longer a few lines of C. What repeats is:

~~~text
what this type is called
what its element type is
which operations belong to it
which capabilities it supports
how other modules identify it
how the corresponding wrappers are generated
~~~

Those are **contracts**.

The goal of this chapter is not to invent more clever macros. It is to collapse these contracts into a small, uniform, finite set of definitions.

---

## 1. Plain C: The First Type Is Usually Easy to Write

Suppose we need a dynamic array of integers.

Straightforward C is perfectly fine:

~~~c
typedef struct IntVec {
    int *data;
    size_t size;
    size_t capacity;
} IntVec;

bool IntVec_init(IntVec *v, size_t capacity);
bool IntVec_push_back(IntVec *v, int value);
int *IntVec_at(IntVec *v, size_t index);
void IntVec_destroy(IntVec *v);
~~~

If this is the only type the program needs, stopping here is the correct design.

Then the project also needs:

~~~c
typedef struct DoubleVec {
    double *data;
    size_t size;
    size_t capacity;
} DoubleVec;

bool DoubleVec_init(DoubleVec *v, size_t capacity);
bool DoubleVec_push_back(DoubleVec *v, double value);
double *DoubleVec_at(DoubleVec *v, size_t index);
void DoubleVec_destroy(DoubleVec *v);
~~~

Later:

~~~c
typedef struct User {
    int id;
    double score;
} User;

typedef struct UserVec {
    User *data;
    size_t size;
    size_t capacity;
} UserVec;

bool UserVec_init(UserVec *v, size_t capacity);
bool UserVec_push_back(UserVec *v, User value);
User *UserVec_at(UserVec *v, size_t index);
void UserVec_destroy(UserVec *v);
~~~

What is really duplicated here is not the `push_back` algorithm.

The algorithm can exist once.

What repeats is:

~~~text
IntVec is bound to int
DoubleVec is bound to double
UserVec is bound to User

and all the contracts derived from those bindings:
type
wrapper
function names
descriptor
traits
range adapter
collector adapter
~~~

Once those facts are scattered, maintaining them often costs more than maintaining the underlying algorithm.

---

## 2. The First Reaction: Write “Smarter Macros”

The obvious next step is something like:

~~~c
#define DECLARE_VEC(Name, T)            \
    typedef struct Name {               \
        T *data;                        \
        size_t size;                    \
        size_t capacity;                \
    } Name;                             \
    bool Name##_init(Name *, size_t);   \
    bool Name##_push_back(Name *, T);   \
    T *Name##_at(Name *, size_t);       \
    void Name##_destroy(Name *)

DECLARE_VEC(IntVec, int);
DECLARE_VEC(DoubleVec, double);
DECLARE_VEC(UserVec, User);
~~~

This absolutely reduces duplication.

But another set of macros soon appears:

~~~c
#define DECLARE_OPTION(Name, T) ...
#define DECLARE_PAIR(Name, K, V) ...
#define DECLARE_HASHMAP(Name, K, V) ...
#define DECLARE_RESULT(Name, T, E) ...
~~~

Then every library invents its own entry point:

~~~c
LIST_OF(int, IntList);
VEC_OF(User, UserVec);
PAIR_OF(int, User, UserById);
OPTION_OF(User, MaybeUser);
~~~

The project now looks “generic,” but callers must still remember:

~~~text
which macro belongs to each Generic kind
what the argument order is
where the generated name appears
which header registers which family
~~~

The macros themselves have become another repeated interface.

The thing that needs unification is not macro-expansion technique. It is:

> **the Generic declaration entry point.**

---

## 3. The First Value of a Generic Protocol: One Entry Point for Different Macro Families

The public entry point in this CMeta edition is:

~~~c
typed(kind, generated_name, type_arguments...);
~~~

For CMeta value kinds:

~~~c
#include <cmeta/meta.h>

typedef struct User {
    int id;
} User;

typed(Option, MaybeUser, User);
typed(Pair, UserScore, User, double);
typed(Tuple, Point3, double, double, double);
~~~

CSTL uses the same entry point for container kinds:

~~~c
#include <cstl/typed.h>

typed(List, IntList, int);
typed(Vec, IntVec, int);
typed(HashMap, IntValuesById, int, int);
~~~

Callers no longer choose among:

~~~text
DECLARE_LIST
DECLARE_VEC
DECLARE_HASHMAP
DECLARE_OPTION
DECLARE_PAIR
~~~

They write:

~~~text
typed(kind, name, ...)
~~~

This is not primarily a syntax improvement.

It solves a more practical problem:

> **the entire codebase now has one Generic declaration protocol.**

---

## 4. What `typed(...)` Actually Does Is Small

The real generic-routing core in this CMeta edition is short:

~~~c
#define CMETA_TYPED_GENERIC_I(kind, ...) \
    CMETA_PP_CAT(CMETA_TYPED_, kind)(__VA_ARGS__)

#define CMETA_TYPED_GENERIC(kind, ...) \
    CMETA_TYPED_GENERIC_I(kind, __VA_ARGS__)

#define CMETA_TYPED_ROUTE_1(kind, ...) \
    CMETA_TYPED_GENERIC(kind, __VA_ARGS__)

#define CMETA_TYPED_ROUTE_0(kind, ...) \
    CMETA_TYPED_FALLBACK(kind, __VA_ARGS__)

#define typed(kind, ...) \
    CMETA_TYPED_ROUTE(kind, __VA_ARGS__)
~~~

A library registers only a finite set of generic kinds.

So:

~~~c
typed(Vec, IntVec, int);
~~~

eventually routes to the implementation associated with that kind:

~~~text
CMETA_TYPED_Vec(IntVec, int)
~~~

The actual container algorithm can remain ordinary compiled C.

The shape is:

~~~text
Generic declaration
        ↓
generate typed wrapper / metadata
        ↓
call ordinary C algorithm
~~~

not:

~~~text
duplicate the whole runtime implementation for every T
~~~

That is the fundamental difference between a finite Generic protocol and templating the entire program.

---

## 5. Before and After: The Duplication Is in the Type Contract, Not the Container Algorithm

Without a Generic protocol, callers may use code like:

~~~c
IntVec ints = {0};
UserVec users = {0};

IntVec_init(&ints, 64);
UserVec_init(&users, 64);

IntVec_push_back(&ints, 7);

User u = {.id = 42};
UserVec_push_back(&users, u);

IntVec_destroy(&ints);
UserVec_destroy(&users);
~~~

There is nothing wrong with these calls.

The problem is that getting these APIs often means manually maintaining two declaration contracts.

With a finite Generic declaration:

~~~c
#include <cstl/typed.h>

typed(Vec, IntVec, int);
typed(Vec, UserVec, User);

int main(void)
{
    IntVec ints = {0};
    UserVec users = {0};

    IntVec_init(&ints, 64u);
    UserVec_init(&users, 64u);

    IntVec_push_back(&ints, 7);

    User u = {.id = 42};
    UserVec_push_back(&users, u);

    IntVec_destroy(&ints);
    UserVec_destroy(&users);
}
~~~

The call site still uses concrete, debuggable C names:

~~~text
IntVec_init
IntVec_push_back
UserVec_push_back
~~~

The Generic layer lives primarily at declaration time.

It does not require the runtime to become a “dynamic template system.”

---

## 6. The Generated Target Should Still Look Like Ordinary C

For:

~~~c
typed(Vec, IntVec, int);
~~~

the generated result can be understood **conceptually** as something like:

~~~c
typedef struct IntVec {
    cstl_vec raw;
} IntVec;

static inline bool
IntVec_push_back(IntVec *self, int value)
{
    return cstl_vec_push_back(&self->raw, &value);
}
~~~

This is not a byte-for-byte expansion from the edition source. It is the shape the design is required to preserve:

~~~text
concrete C type
+
concrete typed wrapper
+
shared ordinary C implementation
~~~

For that reason, the rest of this book will not keep repeating “the macro eventually generates C.”

That is only the mechanism.

The more important question is:

> **Once we have one uniform, finite, typed Generic declaration, which previously scattered contracts can become single-source definitions?**

---

## 7. A Second Kind of Duplication: Struct Definitions and Metadata Drift Apart

Consider a common engineering pattern:

~~~c
typedef struct User {
    int id;
    double score;
} User;

typedef struct FieldInfo {
    const char *name;
    size_t offset;
    size_t size;
} FieldInfo;

static const FieldInfo user_fields[] = {
    {"id",    offsetof(User, id),    sizeof(int)},
    {"score", offsetof(User, score), sizeof(double)},
};
~~~

The facts:

~~~text
id
score
int
double
~~~

have all been written twice.

Add serialization, binding, or debug printing and they may be written a third or fourth time.

The resulting bugs are ordinary:

~~~c
typedef struct User {
    long id;
    double score;
} User;

/* forgotten */
static const FieldInfo user_fields[] = {
    {"id", offsetof(User, id), sizeof(int)},
};
~~~

The problem is not that C cannot describe a struct.

It is:

> **the same field fact is maintained independently by several systems.**

---

## 8. `Struct(...)`: Write Structure Facts Once

CMeta's application DSL can express the facts directly:

~~~c
Struct(User,
    (int, id),
    (double, score)
);
~~~

The same row data can then generate:

~~~text
C struct declaration
field metadata
field count
field lookup
descriptor-facing structure information
~~~

Callers still use ordinary C directly:

~~~c
User user = {
    .id = 7,
    .score = 98.5
};

printf("%d %.1f\n", user.id, user.score);
~~~

The value of Meta here is not merely “fewer typedef lines.”

It is that:

~~~text
User fields
~~~

have one authoritative source.

Later, when Data Binding, debug tooling, RPC schema adapters, and other higher layers need structural information, they do not need to invent separate:

~~~text
UserSchema
UserJsonFields
UserDbColumns
~~~

This is the recurring theme of Part I:

> **Finite Meta first removes knowledge duplication.**

---

## 9. A Third Kind of Duplication: Capabilities and Function Slots Drift Too

Ordinary C can easily contain:

~~~c
typedef struct UserOps {
    bool (*equal)(const User *, const User *);
    uint64_t (*hash)(const User *);
    void (*destroy)(User *);
} UserOps;

enum {
    USER_CAN_EQUAL   = 1u << 0,
    USER_CAN_HASH    = 1u << 1,
    USER_CAN_DESTROY = 1u << 2
};

static const UserOps user_ops = {
    .equal = user_equal,
    .hash = user_hash,
    .destroy = user_destroy
};
~~~

Capability flags and function slots are maintaining the same facts:

~~~text
User supports equal
User supports hash
User supports destroy
~~~

If one side is not updated, the contract can lie.

---

## 10. `Traits(...)`: Generate Capability and Function Slots from the Same Row

The Traits form in this CMeta edition is:

~~~c
Traits(User,
    (equal, user_equal),
    (hash, user_hash),
    (destroy, user_destroy)
);
~~~

The same tagged rows generate:

~~~text
trait flags
+
function slots
~~~

So the one fact:

~~~text
(equal, user_equal)
~~~

determines both:

~~~text
CMETA_TRAIT_EQUAL is present
traits.equal = user_equal
~~~

The inconsistent state:

~~~text
flag says HASH
but hash function slot is NULL
~~~

is no longer created by maintaining two declarations manually.

This is exactly the kind of C problem Meta is good at:

> **Declarations that must evolve together should be generated from the same fact source.**

---

## 11. `_Generic` Is Useful, but It Is Not a Complete Generic Design

C11 already has:

~~~c
_Generic
~~~

For example:

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                    \
    double: print_double               \
)(x)
~~~

It performs compile-time selection.

But it selects among:

~~~text
expressions/functions that already exist
~~~

It does not answer:

~~~text
how a Generic kind is instantiated
how different libraries share one generic declaration syntax
where the descriptor comes from
how traits are connected to the generated type
how a Generic application gets an identity
~~~

So:

~~~text
_Generic
~~~

is a language tool.

And:

~~~text
typed(kind, ...)
~~~

is an engineering-level Generic protocol.

They live at different layers.

---

## 12. A Finite Type Universe: Handle Only Types We Explicitly Support

CMeta does not attempt to “reflect arbitrary C types.”

It maintains a finite known/callable type universe.

Callers can write:

~~~c
const cmeta_type_desc *desc = CMETA_TYPEOF(int);
~~~

instead of:

~~~text
parsing a runtime string "int"
~~~

For unregistered types, the system does not guess.

This is a good fit for C:

~~~text
supported type set
    is finite

unsupported type
    fails explicitly
~~~

Finiteness is not a defect here.

It keeps:

~~~text
dispatch
descriptor
signature family
generic relation
ABI
compile diagnostics
~~~

under control.

---

## 13. Generic Identity: A Descriptor Address Is Not “the Type Itself”

If the same generic type can generate header-local metadata in multiple Translation Units:

~~~text
TU A: descriptor A for Pair<int,double>
TU B: descriptor B for Pair<int,double>
~~~

the addresses may differ.

So this is wrong as a semantic test:

~~~c
if (a_desc == b_desc) {
    /* same semantic type */
}
~~~

Semantic identity must be compared instead.

This is an important transition from a “macro demo” to a real C library:

> **The address of a generated representation object is not semantic type identity.**

The ABI/Multi-TU chapter will return to this boundary.

## 14. A Fourth Kind of Duplication: Type Relations Become Many `if` / `_Generic` Tables

Suppose we define a small common-arithmetic relation:

~~~text
int + int       -> int
int + double    -> double
double + int    -> double
double + double -> double
~~~

Ordinary C can write:

~~~c
enum TypeId {
    TYPE_INT,
    TYPE_DOUBLE
};

enum TypeId common_type(enum TypeId a, enum TypeId b)
{
    if (a == TYPE_INT && b == TYPE_INT)
        return TYPE_INT;

    if (a == TYPE_INT && b == TYPE_DOUBLE)
        return TYPE_DOUBLE;

    if (a == TYPE_DOUBLE && b == TYPE_INT)
        return TYPE_DOUBLE;

    if (a == TYPE_DOUBLE && b == TYPE_DOUBLE)
        return TYPE_DOUBLE;

    abort();
}
~~~

If compile-time logic needs the same relation, another `_Generic` or macro table appears.

The same relation is now repeated in:

~~~text
compile-time relation
runtime/admission relation
documentation
tests
~~~

---

## 15. `TypeFunction(...)`: Express a Finite Type Relation as Data

CMeta can declare the relation directly:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);

typedef TypeEval(CommonArithmetic, int, double) result_type;
~~~

The important thing is the row:

~~~text
(int, double, double)
~~~

It is an explicit relation.

There is no hidden derivation.

There is no default branch.

There is no “best effort conversion.”

If:

~~~text
(long, User, ???)
~~~

does not exist, it should fail at the appropriate boundary.

---

## 16. `ValueFunction` and `Predicate`: The Same Method Can Express Capability Relations

For example:

~~~c
ValueFunction(TypeRank,
    (int, 1),
    (double, 2)
);

enum {
    int_rank = ValueEval(TypeRank, int),
    double_rank = ValueEval(TypeRank, double)
};
~~~

or:

~~~c
Predicate(Hashable,
    (int, 1),
    (double, 1),
    (opaque, 0)
);

Require(Hashable, int);
~~~

For a finite C system, this already covers many relations that would otherwise be distributed across:

~~~text
#ifdef
_Static_assert
_Generic
macro specialization
manual lookup table
~~~

---

## 17. Why “No Default” Is Often an Advantage

Suppose:

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double)
);
~~~

and then:

~~~c
typedef TypeEval(CommonArithmetic, User, double) bad_type;
~~~

CMeta does not:

~~~text
fall back to void *
fall back to int
try the best conversion
~~~

The missing row is itself the fact:

> **This relation is undefined.**

In systems programming, fail-fast behavior is often safer than a “smart default.”

A default turns:

~~~text
design omission
~~~

into:

~~~text
runtime behavior
~~~

## 18. A Complete Before / After: Multiple Generic Families

Suppose an application needs:

~~~text
List<int>
Vec<int>
Option<int>
Pair<int,double>
~~~

If every library has its own macro grammar:

~~~c
DECLARE_LIST(IntList, int);
DECLARE_VEC(IntVec, int);
DECLARE_OPTION(MaybeInt, int);
DECLARE_PAIR(IntDouble, int, double);
~~~

and different projects may even use different argument ordering:

~~~c
MAKE_LIST(int, IntList);
VEC_DECLARE(IntVec, int);
OPTION_OF(int, MaybeInt);
PAIR_OF(int, double, IntDouble);
~~~

the maintainer has to remember four little “languages.”

With one protocol:

~~~c
#include <cmeta/meta.h>
#include <cstl/typed.h>

typed(List, IntList, int);
typed(Vec, IntVec, int);
typed(Option, MaybeInt, int);
typed(Pair, IntDouble, int, double);
~~~

The value is not a few fewer characters.

It is:

~~~text
all finite generic declarations
share one grammar
~~~

Adding another library Generic kind no longer means teaching callers another top-level macro language.

---

## 19. CMeta's Boundary: A Generic Should Not Own the Algorithm

This is an easy place to go wrong.

If:

~~~c
typed(Vec, IntVec, int);
~~~

causes the system to:

~~~text
copy a full vector algorithm
copy allocator logic
copy sort/search implementations
~~~

then the Generic layer becomes a code-bloat generator.

A better boundary is:

~~~text
typed declaration
    owns:
        type-safe surface
        names
        metadata
        adapters

ordinary C library
    owns:
        allocation
        growth
        search
        sort
        storage algorithm
~~~

This keeps Generic as an interface/code-generation layer instead of another runtime.

## 20. What Does This Solve? CSTL Is the Most Direct Engineering Example

Traditional C container APIs often choose between two extremes.

The first is complete erasure:

~~~c
vec_push(&v, &value, sizeof(value));
~~~

The advantage is algorithm reuse.

The disadvantage is that:

~~~text
sizeof
cast
element type
operation naming
~~~

are all manually maintained by callers.

The second approach duplicates a container implementation for each type.

That gives typed calls, but duplicates code and contracts.

A finite Generic protocol can combine the advantages:

~~~c
typed(Vec, UserVec, User);

UserVec users = {0};

UserVec_init(&users, 64u);
UserVec_push_back(&users, (User){.id = 7});
User *u = UserVec_at(&users, 0u);
UserVec_destroy(&users);
~~~

The typed wrapper preserves static type information.

The underlying algorithm remains shared ordinary C.

This is what this book means by:

> **Improve C with finite Meta instead of escaping from C.**

---

## 21. The More Important Result: Higher Layers Can Trust That “Type Facts Exist Once”

When CFlow later sees:

~~~text
Map<int, double>
~~~

it should not create another universe called:

~~~text
FlowTypeInt
FlowTypeDouble
~~~

When CBind sees `User`, it should not create another `BindUserSchema`.

When RPC sees request and response types, it should not create a third type universe.

This is where the deeper value of CMeta becomes visible:

> **Higher-level systems can reuse the same finite type / trait / generic / identity contract.**

That directly reduces the design complexity of Graph, Stream, State Machine, Actor, Serialization, and RPC.

## 22. How to Verify This Chapter: C and Toolchain Evidence

The engineering evidence here is deliberately plain.

### Compile Success

~~~c
typed(Option, MaybeInt, int);
typed(Pair, IntDouble, int, double);
~~~

should generate valid C on supported compilers.

### Compile Failure

Wrong kinds, wrong arity, missing relations, and duplicate trait tags should:

~~~text
fail early
~~~

rather than becoming runtime guesses.

### Multi-TU

Two Translation Units may contain different representation objects while still sharing the same semantic type identity.

### Installed Consumer

A consumer that sees only installed headers and exported link targets should be able to use the same Generic API.

These are C/toolchain questions.

## 23. From Generic to Callable: The Next Repeated Contract Is Behavior

At this point:

~~~text
data type
container application
traits
finite relation
descriptor
~~~

can all share one source of truth.

The next problem is harder.

A normal C callback may expose only:

~~~c
int (*fn)(int);
~~~

or:

~~~c
void (*fn)(void *);
~~~

A higher-level execution system may need to know all of this at once:

~~~text
input type
output type
capture/context
ownership
effects
properties
dispatch authority
~~~

If those are again maintained independently as:

~~~text
function pointer
manual enum
manual context struct
manual flags
~~~

we have returned to the beginning of this chapter:

> **The same behavior contract is being written repeatedly.**

So the next chapter is not about “more macros.”

It asks:

> **How can a function become a finite, typed, composable C value?**

That is the starting point for Callable, Lambda, and Bind.

---

## 24. What We Learned

The most important lesson in this chapter is not a macro trick.

It is four engineering conclusions.

First:

> **Macros become hard to maintain not because there are too few of them, but because different macro families begin maintaining the same contract.**

Second:

> **The first value of Generic is a uniform declaration protocol, not imitation of C++ templates.**

Third:

> **Struct, Traits, typed, and TypeFunction should all collapse “write the same fact many times” into one source of truth.**

Fourth:

> **The final API, data layout, and algorithms should remain as ordinary C as possible.**

The chapter can be summarized as:

~~~text
duplicated C declarations
        ↓
duplicated macro families
        ↓
one finite Generic protocol
        ↓
single-source type/trait/relation facts
        ↓
ordinary typed C API
~~~

That is where CMeta starts solving a real engineering problem.
