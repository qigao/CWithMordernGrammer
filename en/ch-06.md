# Chapter 6: Trusted Graph Semantics — From Semantic Law to Verified Rewrite, Certificate, and Refinement

> **Chapter path**
>
> Chapters 4–5 preserved a LINQ-like pipeline as a typed Graph.
>
> Now a question appears that only Graph can ask:
>
> **If an optimizer rewrites one Graph into another, how do we know they still represent the same computation?**
>
> Start with the smallest C example:
>
> ~~~c
> static int clamp_0_100(int x)
> {
>     if (x < 0) return 0;
>     if (x > 100) return 100;
>     return x;
> }
>
> int original(int x)
> {
>     return clamp_0_100(clamp_0_100(x));
> }
>
> int rewritten(int x)
> {
>     return clamp_0_100(x);
> }
> ~~~
>
> For this concrete function we would like to rewrite:
>
> ~~~text
> Map(clamp_0_100)
>        ↓
> Map(clamp_0_100)
> ~~~
>
> into:
>
> ~~~text
> Map(clamp_0_100)
> ~~~
>
> But the optimizer cannot trust the rewrite merely because metadata contains `IDEMPOTENT`.
>
> The real requirement is a semantic condition:
>
> ~~~text
> forall x, clamp(clamp(x)) = clamp(x)
> ~~~
>
> This is the first place in the book where Lean becomes genuinely irreplaceable:
> **not to help Generic generate C, and not to replace tests, but to prove which program transformations are allowed.**
>
> This chapter focuses only on trusted Graph/LINQ transformation:
>
> ~~~text
> C metadata claim
>     ↓ admission
> Semantic Law
>     ↓ Lean theorem
> Verified Rewrite Rule
>     ↓ concrete optimizer application
> Proof Trace / Certificate
>     ↓
> C differential tests
> ~~~

## 1. Why Testing Alone Cannot Completely Solve the Problem

Tests remain essential.

For example:

~~~c
assert(run(original, input1) == run(optimized, input1));
assert(run(original, input2) == run(optimized, input2));
assert(run(original, input3) == run(optimized, input3));
~~~

If a result differs, the optimizer is clearly wrong.

But even if:

~~~text
1000 tests all agree
~~~

we have shown only:

~~~text
no difference was found for these 1000 inputs
~~~

not:

~~~text
for every possible input
the original and optimized programs have the same semantics
~~~

This matters especially when a rewrite depends on a mathematical property of a function.

For:

~~~text
f(f(x))
~~~

when may we replace it with:

~~~text
f(x)
~~~

Tests may find counterexamples.

The real rule is:

~~~text
∀x, f(f(x)) = f(x)
~~~

which is naturally a mathematical proposition.

---

## 2. A Metadata Claim Is Not a Proof

Earlier chapters allowed a Callable to carry:

~~~text
Effects
Properties
~~~

such as:

~~~text
PURE
DETERMINISTIC
TOTAL
IDEMPOTENT
ASSOCIATIVE
~~~

This metadata is useful.

An optimizer can use it to identify candidates quickly:

~~~text
if callable.properties contains IDEMPOTENT
    candidate for duplicate-map elimination
~~~

But the boundary must be strict:

> **metadata is a declaration, not a proof.**

A programmer may incorrectly write:

~~~text
increment
    IDEMPOTENT
~~~

even though:

~~~text
increment(increment(1))
=
3
~~~

and:

~~~text
increment(1)
=
2
~~~

so:

~~~text
3 != 2
~~~

An `IDEMPOTENT` bit therefore means only:

~~~text
the program claims that this function has the property
~~~

not:

~~~text
the property is mathematically true
~~~

The current formal rewrite design makes the same distinction: CMeta property metadata is not enough for a proof; a separate `IdempotentLaw` is required.

---

## 3. Semantic Law Is the Real Mathematical Condition

Idempotence means:

~~~text
∀x, f(f(x)) = f(x)
~~~

Associativity means:

~~~text
∀a b c,

f(f(a,b),c)
=
f(a,f(b,c))
~~~

An identity law may be:

~~~text
∀x,

f(identity, x) = x
~~~

These are not flags.

They are:

~~~text
Laws
~~~

So semantic information should be separated into three layers:

~~~text
Metadata

what the program claims


Semantic Law

what the property mathematically means


Proof

why a transformation preserves semantics under those laws
~~~

The three layers must not be collapsed into one another.

---

## 4. Lean Should Prove Rules First, Not Every Program Execution

A tempting extreme is:

> If we use Lean, should the whole C runtime move into Lean and every execution carry a proof?

That would make the engineering system far too heavy.

A more useful boundary is:

~~~text
Lean
    proves general rules

C
    applies those rules to concrete programs
~~~

For example, Lean proves:

~~~text
for any f satisfying IdempotentLaw

Map(f) ; Map(f)

and

Map(f)

have the same observable result
~~~

This is a:

~~~text
General Rewrite Theorem
~~~

The C optimizer then sees a specific callable such as:

~~~text
normalize_user
~~~

and, when the corresponding admission conditions hold, applies the rule.

The division of responsibility is:

~~~mermaid
flowchart LR
    A["Semantic Law"]
    B["Lean Theorem"]
    C["Validated Rewrite Rule"]
    D["C Optimizer"]
    E["Concrete Rewrite Instance"]

    A --> B --> C --> D --> E
~~~

Formal reasoning and production runtime remain separate.

---

## 5. Observable Semantics Must Be Defined First

To prove two Graphs equivalent, we first need to answer:

> **What does “equivalent” mean?**

Two internal execution traces may differ.

The real question is:

~~~text
what can the user observe?
~~~

For a Stream, the observable result may contain:

~~~text
Values
Terminal Status
Error
~~~

Define a `StreamResult`, then prove:

~~~text
run(GraphA, input)
=
run(GraphB, input)
~~~

not by requiring every internal state transition to be identical, but by requiring:

~~~text
the final observable behavior to agree
~~~

The current Lean rewrite formalization proves preservation over the full observable `StreamResult`.

---

## 6. This Is the Basic Shape of Compiler Correctness

Traditional compiler optimization does not require:

~~~text
the machine instructions before and after optimization to be identical
~~~

or optimization would be impossible.

It requires the source and optimized program to have the same:

~~~text
Observable Semantics
~~~

CFlow rewrite proof follows the same pattern:

~~~text
Program Transformation
        ↓
Semantic Preservation
~~~

A CFlow optimizer can therefore evolve from ordinary graph-rewrite code toward:

~~~text
verified transformation
~~~

## 7. A Complete Rewrite Rule Has Four Layers

Consider:

~~~text
Duplicate Idempotent Map Elimination
~~~

### 7.1 Graph Pattern

~~~text
Map(f)
 ↓
Map(f)
~~~

This is the:

~~~text
syntactic candidate
~~~

### 7.2 Metadata Admission

Require:

~~~text
same callable identity
compatible types
IDEMPOTENT property
other required effects/properties
~~~

This is the:

~~~text
C-side fast check
~~~

### 7.3 Semantic Law

The real premise is:

~~~text
∀x, f(f(x)) = f(x)
~~~

This is the:

~~~text
mathematical assumption
~~~

### 7.4 Preservation Theorem

Prove:

~~~text
run(Map(f);Map(f))
=
run(Map(f))
~~~

This is the:

~~~text
formal guarantee
~~~

So:

~~~text
Pattern
+
Admission
+
Law
+
Theorem
~~~

together define one trusted rewrite.

---

## 8. This Prevents Dangerous Property-Driven Optimization

If an optimizer only does:

~~~c
if (props & CMETA_PROP_IDEMPOTENT)
    remove_duplicate_map();
~~~

then correctness ultimately depends on one bit never being wrong.

That is fragile.

A stronger engineering model is:

~~~text
Property
    filters candidates

Verified Rule
    defines which transformation is valid

Certificate / Trace
    records the concrete application
~~~

Even if a user callback's mathematical property cannot itself be proved, at least:

~~~text
the optimizer rule
~~~

has been formally justified.

That creates a useful trust boundary.

## 9. Formalization Is Useful Beyond Optimizer Rules

Lean can also validate simpler finite structures:

~~~text
Type Universe
Signature Universe
Operator Policy
Machine Schema
~~~

These share useful properties:

~~~text
finite
structured
explicit relations
~~~

They are good candidates for an authoritative Lean model followed by generated C artifacts.

The current CMeta built-in finite signature universe has a Lean model and generates a checked `builtin_signature_manifest.h`; ordinary C builds do not run Lean.

## 10. Manifest Generation Solves the “Two Sources of Truth” Problem

Suppose a C header maintains:

~~~text
admitted callback signatures
~~~

while Lean separately maintains:

~~~text
admitted callback signatures
~~~

Eventually:

~~~text
C version != Lean version
~~~

which recreates the problem from Chapter 1:

> **one fact is maintained twice.**

A better architecture is:

~~~text
Authoritative Formal Definition
        ↓
Generate
        ↓
C Manifest
~~~

rather than:

~~~text
Lean manually mirrors C
~~~

The earliest project principle remains intact:

~~~text
One Fact
    ↓
Many Uses
~~~

## 12. Ordinary C Builds Should Not Depend on Lean

Even when Lean is valuable, users should not need to:

~~~text
install Lean
compile theorems
generate manifests
~~~

just to run:

~~~text
cmake ..
make
~~~

That would make an otherwise simple C library unnecessarily hard to consume.

A better pipeline is:

~~~text
Development / Verification Pipeline

Lean model
   ↓
prove / generate
   ↓
checked generated headers
   ↓
commit
~~~

Ordinary users see only:

~~~text
C headers
C sources
~~~

So the normal build remains:

~~~text
C Compiler
~~~

Formal tooling improves development trust without contaminating the consumer build path.

## 13. Operator Policy Fits the Same Model

Graph has operators such as:

~~~text
Map
Filter
Reduce
FlatMap
~~~

Not every CMeta Signature is valid for every operator.

For example, `Filter` requires:

~~~text
T -> bool
~~~

while `Map` may accept:

~~~text
T -> U
~~~

So two different universes exist:

~~~text
CMeta
    defines the global finite Signature Universe

CFlow
    defines which Signatures each Operator admits
~~~

This separates:

~~~text
global capability
~~~

from:

~~~text
local policy
~~~

The current CFlow implementation uses per-operator admitted relations for its built-in operator policy, validates them in Lean, and generates `builtin_operator_policy.h`.

---

## 14. This Clarifies the CMeta / CFlow Responsibility Boundary

CMeta may say:

~~~text
the system contains:

int -> long
User -> bool
long × long -> long
~~~

It should not decide:

~~~text
which signature is valid for Filter
~~~

because that belongs to:

~~~text
CFlow Operator Semantics
~~~

So:

~~~text
CMeta
    owns relation universe

CFlow
    owns operator admission policy
~~~

Lean can verify both layers separately:

~~~text
Is the Universe itself valid?

Does the Policy refer only to relations that exist in the Universe?
~~~

This is a clean modular formal boundary.

## 15. Part II Refinement: Prove Rules, Then Bind Concrete Graph Artifacts

Lean proves finite semantic rules; the real optimizer / plan compiler is still C.

So three things must be connected:

~~~text
theorem
    says a rewrite class preserves observation under premises

optimizer instance
    records which nodes of this source Graph used which rule

execution artifact
    proves later Plan / Direct stages still bind to the admitted Graph snapshot
~~~

That is the practical meaning of refinement in Part II.

We do not require Lean to prove the entire C runtime. Proofs, traces, certificates, and differential tests each own a clear responsibility.

---

## 16. Certificate Is a Lighter Refinement Bridge

Not every system needs:

~~~text
a complete machine-checked C refinement proof
~~~

A practical alternative is a:

~~~text
Plan Certificate
~~~

recording:

~~~text
Graph Version
Fingerprint
Instruction
Callable
Input Type
Output Type
Effects
Properties
~~~

A:

~~~text
C-side checker
~~~

then verifies:

~~~text
does this Plan still correspond to the normalized Graph?
~~~

The current `certificate.h` provides this kind of runtime-checkable plan certificate.

The resulting layered guarantee is:

~~~text
Lean
    proves general rules

Generator
    generates finite manifests

C Checker
    validates concrete artifacts

Runtime
    executes approved artifacts
~~~

## 17. Why Certificate Is Better Than “Trust the Compiler”

Suppose the:

~~~text
Plan Compiler
~~~

has a bug and converts:

~~~text
Map<int,long>
~~~

into:

~~~text
double handler
~~~

If execution blindly trusts the Plan, memory corruption may follow.

If the Plan must pass:

~~~text
Certificate Check
~~~

admission can detect:

~~~text
input/output type mismatch
callable mismatch
instruction mismatch
~~~

This does not prove every implementation bug impossible.

It adds an:

~~~text
independent validation boundary
~~~

which is extremely valuable in systems software.

## 18. Proof Trace and Certificate Answer Different Questions

They are easy to confuse.

**Proof Trace** answers:

~~~text
Why was this Graph transformation performed?
~~~

For example:

~~~text
Rule = IdempotentMapElimination
~~~

It records:

~~~text
Optimization History
~~~

**Certificate** answers:

~~~text
Does the final Plan still correspond to the approved Graph?
~~~

It records:

~~~text
Artifact Consistency
~~~

So:

~~~text
Trace
    explains transformation

Certificate
    validates execution artifact
~~~

Together they make the Control Plane auditable.

## 20. From the Trust Chain to an Evidence Matrix

At this point the chapter's core trust chain is established: Metadata Claim declares candidate facts, Semantic Law states the mathematical condition, Lean proves finite rules, the C optimizer records a concrete rewrite, and Plan/Certificate binds execution artifacts back to approved IR.

The publication version does not repeat broad arguments about why formalization matters or whether Lean replaces testing. The rest of the chapter checks exactly what each kind of evidence can and cannot establish.

The boundary remains strict: a Lean theorem does not automatically prove an arbitrary C implementation refines the model; it does not prove ABI correctness, memory safety, OS liveness, or benchmark numbers; and ordinary C consumers still do not depend on Lean.

---

## 21. Trusted Boundary Matrix: What Does Each Kind of Evidence Prove?

The most dangerous mistake is no longer “having no proof.”

It is:

> **using one kind of evidence to claim something that kind of evidence cannot establish.**

| Evidence | Primarily answers | Cannot prove by itself |
|---|---|---|
| Metadata claim | what property/capability an implementation declares | that the declaration is mathematically true |
| Compile-time check | whether C types/macros/declarations satisfy the current compiler contract | runtime semantic equivalence |
| Lean theorem | whether a relation holds under a formal model/premises | that arbitrary C automatically refines that model |
| Generated manifest | how validated finite facts enter an ordinary C build | all C runtime behavior is correct |
| Optimizer proof trace | which known rules were applied in this concrete rewrite | that the rule itself is correct |
| Certificate / witness | whether an execution artifact binds to a specific approved IR | that OS/runtime can never fail |
| Differential test | whether real implementation paths agree on covered observations | a mathematical proof for all inputs |
| ABI/install test | whether an external consumer crosses a real package/link boundary | semantic law |
| Sanitizer/stress | whether memory/concurrency defects appear in covered scenarios | absence of all bugs |
| Benchmark | cost on a specified workload/platform | semantic correctness |

This matrix is one of the book's most important anti-overclaim rules.

## 22. Case Study A: Idempotent Map — From Property Claim to Verified Rewrite

Chapter 7 continues using:

~~~text
Map(clamp)
Map(clamp)
~~~

with the desired rewrite:

~~~text
Map(clamp)
~~~

This example walks the full trust chain.

### 22.1 Claim

C metadata may declare:

~~~text
IDEMPOTENT
~~~

It means only:

> admission declares this callable a candidate for the idempotent rule.

A handwritten claim is not a proof.

### 22.2 Semantic Law

The real premise is:

~~~text
forall x,
clamp (clamp x) = clamp x
~~~

### 22.3 Rule Theorem

The current formal Rewrite proof includes:

~~~text
map_idempotent_elimination
~~~

Its direct premise is not a bare property bit but:

~~~text
IdempotentEndomapPremises Γ ty
~~~

which includes the trusted/modeled callable meaning and the actual idempotent law.

More generally:

~~~text
certified_rewrite_preserves_observations
~~~

proves observation preservation for finite compositions of certified rewrites.

These theorems answer:

> If callable meaning and the corresponding semantic law are part of the theorem premises, does removing a duplicate Map preserve observable stream semantics?

The theorem proves the rule.

It does not re-prove a concrete C function at every runtime invocation.

### 22.4 Concrete Rewrite Instance

The current C optimizer can emit a stable rule id:

~~~text
IDEMPOTENT_MAP_ELIMINATION
~~~

and record in the proof trace:

~~~text
source subgraph
retained node/callable
removed node/callable
~~~

The Trace answers:

> At which source coordinate did this optimized Graph apply which rule?

So:

~~~text
Lean theorem
    = proof of rule

C trace
    = record of rule instance
~~~

### 22.5 Trace Checker / AOT Matcher

A later checker can validate:

~~~text
trace bound to exact source Graph/version
trace bound to exact optimized Graph/version
rule id supported
source/target coordinates match
final optimized structure matches expected Stage IR
~~~

The trusted path becomes:

~~~text
Semantic Law
    ↓
Lean rule theorem
    ↓
C optimizer applies rule
    ↓
Proof Trace
    ↓
Trace/IR checker
~~~

That is much stronger than:

~~~text
property bit set
    ↓
optimizer deletes node
~~~

Part III's Reactive, Machine, and Actor models reuse the same proof discipline:

~~~text
define observable/state semantics first
prove finite laws
validate refinement with C implementation + race/sanitizer tests
~~~

but those stateful protocols are outside the LINQ/Graph thread of this chapter.

## 23. Manifest: How Lean Enters Ordinary C Without Entering the Ordinary C Build

If formalization requires every application consumer to install Lean, the engineering boundary has failed.

The current Salts snapshot uses checked-in generated artifacts.

### 23.1 Builtin Signature Manifest

Lean validates the finite built-in type/signature relation and generates:

~~~text
cmeta/include/cmeta/generated/
    builtin_signature_manifest.h
~~~

An ordinary C/C++ build:

~~~text
includes checked-in header
does not run Lean
~~~

Only CI / semantic development workflows run:

~~~text
cmeta-signature-gen --check
~~~

to ensure:

~~~text
formal source
    ↔
checked-in C artifact
~~~

has not drifted.

### 23.2 Builtin Operator Policy

Similarly, the finite CFlow operator-policy relation is checked by the formal package and generates:

~~~text
cflow/include/cflow/generated/
    builtin_operator_policy.h
~~~

The C optimizer/runtime consumes an ordinary C table/header instead of invoking a theorem prover in the hot path.

### 23.3 Generator Is Part of the Trusted Bridge

We must be honest here.

A correct theorem plus an incorrect generator may still create a wrong C header.

So the trusted bridge includes at least:

~~~text
formal definitions/theorems
generator mapping
generated-artifact check
C consumer interpretation
~~~

Generated headers should therefore be:

- simple;
- readable;
- diff-friendly;
- reproducible/checkable in CI;
- never hand-edited into a second source of truth.

## 24. Certificate and Proof Trace: Two Different Runtime Bridges

### 24.1 Proof Trace

Answers:

> Why did the optimized Graph change from the source Graph to this structure?

It records:

~~~text
rewrite rule id
source coordinate
retained/removed node
callable coordinate
source/output Graph binding
~~~

Trace is a:

~~~text
Transformation Witness
~~~

### 24.2 Certificate

Answers:

> Does this Plan / execution path still correspond to the approved normalized/optimized semantic program?

It records:

~~~text
Graph version/fingerprint
certified opcode rows
types
callables
effects/properties
execution path
ordering
required capabilities
~~~

Certificate is an:

~~~text
Execution Artifact Witness
~~~

So the chain is:

~~~text
Source Graph
    ↓
Optimizer
    ↓
Proof Trace
    ↓
Optimized Graph
    ↓
Plan Compile
    ↓
Certificate
    ↓
Execution
~~~

Future stronger assurance can independently improve:

~~~text
trace checker
certificate checker
artifact identity
generator provenance
~~~

without converting the whole runtime into a theorem prover.

## 25. Formal Trusted Base and Execution Trusted Base Must Be Separate

“Trusted computing base” means different things at different layers.

### 25.1 Formal Proof Trusted Base

At minimum:

~~~text
formal definitions
theorem statements/premises
Lean checker/kernel/toolchain assumptions
semantic model itself
~~~

A theorem is correct only relative to its model and premises.

If observable semantics is specified incorrectly:

~~~text
the proof may be perfectly valid
while proving the wrong thing
~~~

Specification review matters as much as theorem proof.

### 25.2 Bridge Trusted Base

Includes:

~~~text
generators
rule-id mapping
trace construction/checking
certificate construction/checking
type/callable identity mapping
~~~

These connect the formal world to C artifacts.

### 25.3 Execution Trusted Base

Includes:

~~~text
C compiler/linker
C implementation
allocator/thread primitives
OS/runtime
hardware
borrowed callback/user code
~~~

Only parts that are actually formalized/refined inherit theorem guarantees.

Other parts need:

~~~text
tests
sanitizers
ABI qualification
stress
platform CI
benchmark
~~~

### 25.4 External Liveness Assumptions

Statements such as:

~~~text
OS eventually schedules worker
socket eventually becomes ready
device eventually completes
user callback eventually returns
~~~

are usually environment assumptions, not CMeta/CFlow theorems.

The book must label them explicitly so a safety proof is not overstated as “the system can never get stuck.”

## 26. How Proof, Test, and Runtime Checks Work Together

A mature feature should not ask:

~~~text
proof or test?
~~~

It should ask:

> **At which layers does this claim require evidence?**

For idempotent rewrite:

~~~text
Semantic law
    → Lean theorem

Concrete optimizer event
    → proof trace

Graph/optimized binding
    → trace checker

Plan binding
    → certificate

C implementation regression
    → differential tests

memory/lifetime
    → sanitizer

performance benefit
    → benchmark
~~~

For Reactive demand:

~~~text
demand mathematical invariant
    → Lean

runtime state mapping
    → conformance tests

wake/cancel race
    → stress/readiness tests

scheduler capacity behavior
    → bounded protocol tests

latency/throughput
    → benchmark
~~~

A professional verification stack is therefore:

~~~text
Formal proof
+
Generated facts
+
Runtime admission
+
Differential testing
+
Memory/concurrency testing
+
ABI/platform qualification
+
Measurement
~~~

not one of these pretending to replace all others.

## 27. What We Learned

This chapter establishes the book's trust method, not merely “a Lean chapter.”

The evidence chain is:

~~~text
Claim
    ↓
Semantic Definition
    ↓
Proof Obligation
    ↓
Lean Theorem
    ↓
Generated/Registered Rule
    ↓
Concrete Trace
    ↓
Artifact Certificate
    ↓
C Runtime
    ↓
Differential / Sanitizer / ABI Evidence
    ↓

~~~

Not every feature needs every layer.

The rule is:

> **use the kind of evidence that matches the layer of the claim.**

Real examples show different roles:

~~~text
Optimizer:
    theorem licenses transformation

Reactive:
    theorem shapes execution state machine

Machine:
    theorem constrains build/commit semantics
~~~

Manifest generation shows:

~~~text
formal knowledge
    → checked-in ordinary C artifact
~~~

Lean therefore becomes:

> **a design and verification tool in the Modern C control/trust plane, not a new runtime dependency.**
