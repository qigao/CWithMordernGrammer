# Chapter 6: Trusted Graph Semantics — From Observable Semantics to Verified Rewrite

> **Formal proof is not decoration for an “advanced” Graph.**
>
> It enters when one concrete question appears:
>
> ~~~text
> optimizer wants to replace program P with Q
> ~~~
>
> We must answer:
>
> ~~~text
> for every admitted input,
> are the observable results of P and Q equal?
> ~~~

---

## 1. Property Claim Is Not Rewrite Authority

Suppose metadata says:

~~~text
clamp.properties |= IDEMPOTENT
~~~

and the optimizer wants to eliminate two **sequential** Map nodes.

Write the data flow explicitly:

~~~text
input x
  |
  v
Map(clamp)
  |
  | y = clamp(x)
  v
Map(clamp)
  |
  | z = clamp(y)
  v
output z
~~~

The classification is:

~~~text
Graph level:
    two Map nodes execute in sequence
    = sequential composition

Per-element expansion:
    y = clamp(x)
    z = clamp(y)
      = clamp(clamp(x))
    = nested function application

Recursion:
    no.
    The implementation of clamp() does not call clamp() itself.
~~~

For two different functions:

~~~text
Map(f) -> Map(g)

on one element x means:

g(f(x))

therefore:

Map(g) after Map(f)
    = Map(g ∘ f)
~~~

Here f = g = clamp:

~~~text
Map(clamp) -> Map(clamp)
    = Map(clamp ∘ clamp)
~~~

The optimizer wants to replace it with one Map(clamp).

The metadata bit is not enough.

The actual law is:

~~~text
∀x, clamp(clamp(x)) = clamp(x)

equivalently:

clamp ∘ clamp = clamp
~~~

Therefore:

~~~text
property bit
    = admission claim

semantic theorem
    = rewrite authority
~~~

## 2. Define Observable Semantics First

For a pure data-flow pipeline, a simplified evaluator may be:

~~~text
eval(Source(xs)) = xs

eval(Filter(p, s)) =
    [x in eval(s) | p(x)]

eval(Map(f, s)) =
    [f(x) | x in eval(s)]

eval(Reduce(r, z, s)) =
    foldl(r, z, eval(s))
~~~

This is specification semantics, not runtime implementation.

Without an observation model, rewrite preservation is undefined.

---

## 3. Rewrite Judgment

Write optimizer authorization as:

~~~text
Γ ⊢ P ~> Q
~~~

with:

~~~text
Γ ⊢ admitted(P)
Γ ⊢ rewrite_preconditions(P,Q)
Γ ⊢ ∀input, observe(eval(P,input))
             = observe(eval(Q,input))
────────────────────────────────────────
Γ ⊢ P ~> Q : sound
~~~

For an idempotent map, fix the notation first:

~~~text
Map(f); Map(f)
~~~

The semicolon means **execute the left Map and then the right Map in the pipeline**. It does not mean recursion.

For one input x:

~~~text
x
 -> first Map(f)
 -> f(x)
 -> second Map(f)
 -> f(f(x))
~~~

The rewrite rule is therefore:

~~~text
IDEMPOTENT(f)
∧ theorem ∀x, f(f(x)) = f(x)
────────────────────────────────
Map(f); Map(f)  ~>  Map(f)
~~~

Metadata selects candidates.

The theorem authorizes the transformation.

---

## 4. Lean Theorem Must Bind to a Concrete Transformation

Conceptually:

~~~text
theorem map_idempotent_preserves_eval
    (hf : ∀ x, f (f x) = f x) :
    eval (Map f (Map f s))
    =
    eval (Map f s)
~~~

C optimizer does not run Lean at runtime.

The chain is:

~~~text
Lean source
    ↓ proof
approved rule manifest
    ↓
C optimizer matcher
    ↓
rewrite
~~~

Normal C builds need no theorem prover.

## 5. Proof Trace and Certificate

A rewrite records:

~~~text
rule_id
input graph fingerprint
output graph fingerprint
required property ids
proof/certificate version
~~~

For example:

~~~c
typedef struct rewrite_trace {
    uint32_t rule_id;
    uint64_t before_hash;
    uint64_t after_hash;
    uint32_t certificate_version;
} rewrite_trace;
~~~

Trace answers which rewrite happened.

Certificate answers whether a concrete artifact satisfies an approved refinement relation.

They are different objects.

---

## 6. Trusted Boundary

| Claim | Evidence |
|---|---|
| property declared | C metadata / generator |
| rewrite law valid | Lean theorem |
| optimizer used approved rule | trace / matcher test |
| generated C matches plan | differential/refinement test |
| ABI works | compile/link/install |
| faster | benchmark |

Do not use a theorem to prove ABI, a unit test to prove universal semantic equivalence, or a benchmark to prove correctness.

## 7. Failure Cases

### Claim but no theorem

~~~text
IDEMPOTENT bit present
proof rule unavailable
    ↓
NO_REWRITE
~~~

### Stale certificate

~~~text
graph fingerprint changed
certificate fingerprint old
    ↓
REJECT_CERTIFICATE
~~~

### Undefined observation model

If a transformation may change encounter order, error timing, side effects, or allocation observations and semantics do not say whether they are observable:

~~~text
rewrite not admitted
~~~

Do not let a PURE bit substitute for missing semantics.

The remainder of the chapter walks the complete trusted chain through the concrete Idempotent Map case.

## 8. Case Study A: Idempotent Map — From Property Claim to Verified Rewrite

Chapter 7 continues with this **sequential composition**:

~~~text
x
 |
 v
Map(clamp)
 |
 | y = clamp(x)
 v
Map(clamp)
 |
 | z = clamp(y) = clamp(clamp(x))
 v
z
~~~

This is not recursion. The two Graph nodes each invoke the same ordinary C function once.

If the idempotence law holds:

~~~text
∀x, clamp(clamp(x)) = clamp(x)
~~~

the graph may be rewritten to:

~~~text
x
 |
 v
Map(clamp)
 |
 | z = clamp(x)
 v
z
~~~

This example walks the full trust chain.

### 22.1 Claim

C metadata may declare:

~~~text
IDEMPOTENT
~~~

It means only:

> admission declares this callable a candidate for the idempotent rule.

A handwritten claim is not a proof.

### 22.2 Semantic Law

The real premise is:

~~~text
forall x,
clamp (clamp x) = clamp x
~~~

### 22.3 Rule Theorem

The current formal Rewrite proof includes:

~~~text
map_idempotent_elimination
~~~

Its direct premise is not a bare property bit but:

~~~text
IdempotentEndomapPremises Γ ty
~~~

which includes the trusted/modeled callable meaning and the actual idempotent law.

More generally:

~~~text
certified_rewrite_preserves_observations
~~~

proves observation preservation for finite compositions of certified rewrites.

These theorems answer:

> If callable meaning and the corresponding semantic law are part of the theorem premises, does removing a duplicate Map preserve observable stream semantics?

The theorem proves the rule.

It does not re-prove a concrete C function at every runtime invocation.

### 22.4 Concrete Rewrite Instance

The current C optimizer can emit a stable rule id:

~~~text
IDEMPOTENT_MAP_ELIMINATION
~~~

and record in the proof trace:

~~~text
source subgraph
retained node/callable
removed node/callable
~~~

The Trace answers:

> At which source coordinate did this optimized Graph apply which rule?

So:

~~~text
Lean theorem
    = proof of rule

C trace
    = record of rule instance
~~~

### 22.5 Trace Checker / AOT Matcher

A later checker can validate:

~~~text
trace bound to exact source Graph/version
trace bound to exact optimized Graph/version
rule id supported
source/target coordinates match
final optimized structure matches expected Stage IR
~~~

The trusted path becomes:

~~~text
Semantic Law
    ↓
Lean rule theorem
    ↓
C optimizer applies rule
    ↓
Proof Trace
    ↓
Trace/IR checker
~~~

That is much stronger than:

~~~text
property bit set
    ↓
optimizer deletes node
~~~

Part III's Reactive, Machine, and Actor models reuse the same proof discipline:

~~~text
define observable/state semantics first
prove finite laws
validate refinement with C implementation + race/sanitizer tests
~~~

but those stateful protocols are outside the LINQ/Graph thread of this chapter.

## 9. Manifest: How Lean Enters Ordinary C Without Entering the Ordinary C Build

If formalization requires every application consumer to install Lean, the engineering boundary has failed.

The current Salts snapshot uses checked-in generated artifacts.

### 23.1 Builtin Signature Manifest

Lean validates the finite built-in type/signature relation and generates:

~~~text
cmeta/include/cmeta/generated/
    builtin_signature_manifest.h
~~~

An ordinary C/C++ build:

~~~text
includes checked-in header
does not run Lean
~~~

Only CI / semantic development workflows run:

~~~text
cmeta-signature-gen --check
~~~

to ensure:

~~~text
formal source
    ↔
checked-in C artifact
~~~

has not drifted.

### 23.2 Builtin Operator Policy

Similarly, the finite CFlow operator-policy relation is checked by the formal package and generates:

~~~text
cflow/include/cflow/generated/
    builtin_operator_policy.h
~~~

The C optimizer/runtime consumes an ordinary C table/header instead of invoking a theorem prover in the hot path.

### 23.3 Generator Is Part of the Trusted Bridge

We must be honest here.

A correct theorem plus an incorrect generator may still create a wrong C header.

So the trusted bridge includes at least:

~~~text
formal definitions/theorems
generator mapping
generated-artifact check
C consumer interpretation
~~~

Generated headers should therefore be:

- simple;
- readable;
- diff-friendly;
- reproducible/checkable in CI;
- never hand-edited into a second source of truth.

## 10. Certificate and Proof Trace: Two Different Runtime Bridges

### 24.1 Proof Trace

Answers:

> Why did the optimized Graph change from the source Graph to this structure?

It records:

~~~text
rewrite rule id
source coordinate
retained/removed node
callable coordinate
source/output Graph binding
~~~

Trace is a:

~~~text
Transformation Witness
~~~

### 24.2 Certificate

Answers:

> Does this Plan / execution path still correspond to the approved normalized/optimized semantic program?

It records:

~~~text
Graph version/fingerprint
certified opcode rows
types
callables
effects/properties
execution path
ordering
required capabilities
~~~

Certificate is an:

~~~text
Execution Artifact Witness
~~~

So the chain is:

~~~text
Source Graph
    ↓
Optimizer
    ↓
Proof Trace
    ↓
Optimized Graph
    ↓
Plan Compile
    ↓
Certificate
    ↓
Execution
~~~

Future stronger assurance can independently improve:

~~~text
trace checker
certificate checker
artifact identity
generator provenance
~~~

without converting the whole runtime into a theorem prover.

## 11. Formal Trusted Base and Execution Trusted Base Must Be Separate

“Trusted computing base” means different things at different layers.

### 25.1 Formal Proof Trusted Base

At minimum:

~~~text
formal definitions
theorem statements/premises
Lean checker/kernel/toolchain assumptions
semantic model itself
~~~

A theorem is correct only relative to its model and premises.

If observable semantics is specified incorrectly:

~~~text
the proof may be perfectly valid
while proving the wrong thing
~~~

Specification review matters as much as theorem proof.

### 25.2 Bridge Trusted Base

Includes:

~~~text
generators
rule-id mapping
trace construction/checking
certificate construction/checking
type/callable identity mapping
~~~

These connect the formal world to C artifacts.

### 25.3 Execution Trusted Base

Includes:

~~~text
C compiler/linker
C implementation
allocator/thread primitives
OS/runtime
hardware
borrowed callback/user code
~~~

Only parts that are actually formalized/refined inherit theorem guarantees.

Other parts need:

~~~text
tests
sanitizers
ABI qualification
stress
platform CI
benchmark
~~~

### 25.4 External Liveness Assumptions

Statements such as:

~~~text
OS eventually schedules worker
socket eventually becomes ready
device eventually completes
user callback eventually returns
~~~

are usually environment assumptions, not CMeta/CFlow theorems.

The book must label them explicitly so a safety proof is not overstated as “the system can never get stuck.”

## 12. How Proof, Test, and Runtime Checks Work Together

A mature feature should not ask:

~~~text
proof or test?
~~~

It should ask:

> **At which layers does this claim require evidence?**

For idempotent rewrite:

~~~text
Semantic law
    → Lean theorem

Concrete optimizer event
    → proof trace

Graph/optimized binding
    → trace checker

Plan binding
    → certificate

C implementation regression
    → differential tests

memory/lifetime
    → sanitizer

performance benefit
    → benchmark
~~~

For Reactive demand:

~~~text
demand mathematical invariant
    → Lean

runtime state mapping
    → conformance tests

wake/cancel race
    → stress/readiness tests

scheduler capacity behavior
    → bounded protocol tests

latency/throughput
    → benchmark
~~~

A professional verification stack is therefore:

~~~text
Formal proof
+
Generated facts
+
Runtime admission
+
Differential testing
+
Memory/concurrency testing
+
ABI/platform qualification
+
Measurement
~~~

not one of these pretending to replace all others.

## 13. What We Learned

This chapter establishes the book's trust method, not merely “a Lean chapter.”

The evidence chain is:

~~~text
Claim
    ↓
Semantic Definition
    ↓
Proof Obligation
    ↓
Lean Theorem
    ↓
Generated/Registered Rule
    ↓
Concrete Trace
    ↓
Artifact Certificate
    ↓
C Runtime
    ↓
Differential / Sanitizer / ABI Evidence
    ↓
Benchmark
~~~

Not every feature needs every layer.

The rule is:

> **use the kind of evidence that matches the layer of the claim.**

Real examples show different roles:

~~~text
Optimizer:
    theorem licenses transformation

Reactive:
    theorem shapes execution state machine

Machine:
    theorem constrains build/commit semantics
~~~

Manifest generation shows:

~~~text
formal knowledge
    → checked-in ordinary C artifact
~~~

Lean therefore becomes:

> **a design and verification tool in the Modern C control/trust plane, not a new runtime dependency.**
