# 第三章：从函数指针到函数语义——FunctionDesc、Callable、Lambda 与 Bind

> **本章只做一个区分：**
>
> 描述一个 C 函数“是什么”，和决定“怎样执行它”，不是同一件事。

---

## 1. Plain C baseline：函数指针已经足够快

普通 callback：

~~~c
typedef long (*map_fn)(int x);

long square(int x)
{
    return (long)x * x;
}

map_fn fn = square;
long y = fn(7);
~~~

如果调用点只需要保存并调用一个函数地址，停在这里就是正确答案。

问题只在于：function pointer 本身几乎没有 semantic information。

它不知道 parameter direction、ownership、effects、properties，也不能告诉 DataBind、TinyMock、Plugin 或 CFlow 这个函数“意味着什么”。

---

## 2. FunctionDesc：描述 native function 是什么

考虑一个更真实的函数：

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

一个描述性对象至少需要：

~~~c
typedef struct cmeta_param_desc {
    const char *name;
    const cmeta_type_desc *type;
    uint32_t flags; /* IN / OUT / INOUT / ownership */
} cmeta_param_desc;

typedef struct cmeta_function_desc {
    const char *name;
    const cmeta_type_desc *return_type;

    const cmeta_param_desc *params;
    size_t param_count;

    uint32_t effects;
    uint32_t properties;
} cmeta_function_desc;
~~~

它回答的是：

| FunctionDesc fact | 例子 |
|---|---|
| identity | get_user |
| return type | int |
| parameters | repo / id / out_user |
| direction | IN / OUT |
| ownership/nullability | where admitted |
| effects/properties | metadata claims |

FunctionDesc 是 **native semantic truth**，不是 universal invoke object。

---

## 3. Signature：可执行形状必须有限、可检查

CFlow 不需要支持任意 C ABI shape。

它只需要一个有限 admitted universe，例如：

~~~text
int -> bool
int -> long
(long, int) -> long
~~~

可以给每一种 shape 一个稳定 signature id：

~~~c
typedef enum cmeta_signature_id {
    CMETA_SIG_INT_TO_BOOL,
    CMETA_SIG_INT_TO_LONG,
    CMETA_SIG_LONG_INT_TO_LONG
} cmeta_signature_id;
~~~

Admission 只允许已支持 shape：

~~~text
FunctionDesc
    ↓ validate native shape
Signature admitted?
    ├─ no  -> UNSUPPORTED
    └─ yes -> executable projection allowed
~~~

有限 universe 的价值是：dispatch、adapter、formal model、AOT lowering 都可以围绕同一组 shape 工作。

---

## 4. FunctionDesc 不负责 universal dynamic invocation

看到完整参数 metadata 后，很容易设计：

~~~c
invoke(desc, values, count);
~~~

但真实 C ABI 还涉及 calling convention、struct return、alignment、variadic、pointer/ownership、platform differences。

因此边界保持：

| 对象 | 职责 |
|---|---|
| FunctionDesc | description |
| exact adapter | execution |
| Callable | admitted executable representation |

例如 compiler 可以生成 exact adapter：

~~~c
static int
invoke_get_user(
    void *ctx,
    const GetUserRequest *request,
    GetUserResponse *response)
{
    UserRepository *repo = ctx;

    return get_user(
        repo,
        request->id,
        &response->user);
}
~~~

最终仍然是 ordinary C call。

---

## 5. Callable：只保存执行真正需要的信息

概念性 representation：

~~~c
typedef struct cmeta_callable {
    cmeta_signature_id signature;

    cmeta_callable_invoke_fn invoke;
    const void *raw_target;

    uint32_t effects;
    uint32_t properties;

    uint8_t capture[CMETA_CAPTURE_INLINE];
    uint16_t capture_size;
} cmeta_callable;
~~~

这里最重要的是把不同问题分开：

| Field | 作用 |
|---|---|
| signature | type/execution shape |
| invoke/raw_target | dispatch authority |
| capture | environment |
| effects | observable behavior constraints |
| properties | semantic claims used for admission/optimization |

Callable 不是每个 C function 都必须经过的对象。

只有需要存储、组合、Graph execution 或跨模块 executable projection 的函数才需要它。

---

## 6. Lambda 与 Bind：本质是 code + capture + lifetime

传统 callback 常写：

~~~c
typedef void (*callback_fn)(void *user);
~~~

真正难点不是函数地址，而是 user context 的 lifetime。

一个有限 Lambda 可以把 capture 内联保存：

~~~c
typedef struct multiply_capture {
    int factor;
} multiply_capture;

static long
multiply_invoke(const void *capture, int x)
{
    const multiply_capture *c = capture;
    return (long)c->factor * x;
}
~~~

创建：

~~~c
multiply_capture cap = {
    .factor = 10
};

/* generated/builder API copies cap into bounded storage */
~~~

Bind 只是另一种 capture：

~~~text
multiply(a, b)
    + bind b = 10
    ↓
callable(a) = multiply(a, 10)
~~~

这不是“模拟 C++ lambda syntax”，而是显式管理 code、capture、copy/destroy 与 lifetime。

---

## 7. Inline capture 必须 bounded

最危险的设计是：

~~~text
capture too large
    ↓
secret malloc
    ↓
API still reports ordinary value semantics
~~~

更清晰的 contract 是：

~~~text
capture_size <= inline_capacity
    -> OK

capture_size > inline_capacity
    -> TOO_LARGE / explicit heap-backed path
~~~

这样 ordinary Callable 可以保持：

- no hidden allocation；
- predictable object size；
- explicit copy/destroy；
- predictable ABI/lifetime。

如果需要 heap-backed capture，就应该使用显式不同的 owner/type，而不是悄悄改变语义。

---

## 8. Effects 与 Properties 不是一回事

Effects 描述可能观察到的行为，例如：

- IO；
- STATEFUL；
- MAY_FAIL。

Properties 描述更强的 semantic claim，例如：

- DETERMINISTIC；
- IDEMPOTENT；
- ASSOCIATIVE；
- TOTAL；
- NO_ALIAS。

它们都首先是 metadata。

看见 ASSOCIATIVE bit，并不能自动推出任意 reassociation 都语义等价。

真正授权 rewrite 的仍然必须是 semantic law。

---

## 9. Property claim 与 theorem 的边界

以 idempotent 为例。

Metadata：

~~~c
callable.properties |= CMETA_PROP_IDEMPOTENT;
~~~

真正的 law：

~~~text
∀x, f(f(x)) = f(x)
~~~

只有有了 law，optimizer 才能授权：

~~~text
Map(f); Map(f)
    ~>
Map(f)
~~~

因此：

| 层 | 作用 |
|---|---|
| property bit | candidate / admission claim |
| theorem | rewrite authority |
| trace/certificate | concrete rewrite evidence |

Lean 不证明“任意打了 IDEMPOTENT 标签的机器码真的 idempotent”。

它证明的是：**如果前提成立，这个 transformation preserve semantics。**

---

## 10. Callable 进入 Graph 前必须先 admission

完整路径应该是：

~~~text
FunctionDesc
    ↓
native compatibility validation
    ↓
exact adapter / admitted signature
    ↓
Callable
    ↓
CFlow Graph
~~~

连接两个 callable 时先看 type relation：

~~~text
f : A -> B
g : B -> C
────────────────
g ∘ f : A -> C
~~~

如果第二个函数需要 X 而不是 B：

~~~text
B != X
    ↓
construction/admission fails
~~~

不等到 runtime 用 void pointer 猜。

---

## 11. Function capability 与 Interface capability 不要混成一个东西

一个 request-response operation 很适合 FunctionDesc + exact adapter。

一个长期 provider，例如 Executor，更自然地使用：

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

两种 representation 可以进入同一个 Plugin runtime，但 semantic shape 不同：

| Capability | Representation |
|---|---|
| Service / function | FunctionDesc + exact adapter |
| Provider / interface | InterfaceDesc + {self,vtable} |

不要为了统一而把所有 function 拆成 vtable，也不要把所有 provider flatten 成 FunctionDesc。

---

## 12. Engineering Evidence

### Signature admission

Unsupported ABI shape 必须明确失败：

~~~text
unknown signature
    ↓
UNSUPPORTED
~~~

### Capture boundary

测试 inline capacity 前后两个 case：

~~~text
N bytes
    -> accepted

N + 1 bytes
    -> TOO_LARGE
~~~

### Multi-TU identity

不同 Translation Unit 可以拥有不同 descriptor/adapter representation，但 semantic function identity 必须按照 authoritative representation 比较，而不是盲目 pointer equality。

### Performance

至少比较：

- direct ordinary C call；
- typed wrapper；
- adapter/erased callable；
- capturing callable。

不能用“zero-cost”代替 benchmark。

## 13. Canonical Example：为 Graph 准备三个 Callable

后续章节持续使用：

~~~c
bool is_even(int x)
{
    return (x & 1) == 0;
}

long square(int x)
{
    return (long)x * x;
}

long sum(long acc, long x)
{
    return acc + x;
}
~~~

它们对应：

~~~text
is_even : int -> bool
square  : int -> long
sum     : (long, long) -> long
~~~

下一章不再讨论“如何调用函数”，而是讨论：

> **当这些 typed behavior 之间的关系也值得保存时，怎样把它们组成 Graph？**

---

## 14. What We Learned

本章完成了四个边界：

1. FunctionDesc 描述 native function；
2. exact adapter / Callable 负责 admitted execution；
3. capture/lifetime 必须显式且 bounded；
4. metadata property 不能代替 semantic proof。

因此后面的 DataBind、TinyMock、Plugin、CFlow 可以共享同一个 native function semantic source，而不必各自再发明一套函数描述系统。
