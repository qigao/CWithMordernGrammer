# 第二章：从宏到 Generic——把重复的类型契约收成一次定义

> 第一章解决了 code shape 的重复。本章继续问：当同一个类型事实同时被 container、Struct metadata、Traits、TypeFunction 和后续 compiler 使用时，怎样让它只写一次？

---

## 1. 从 Plain C 到一个 Generic 入口

普通 C 里，我们经常为同一个算法族定义多组 concrete type：

~~~c
typedef struct IntVec {
    int *data;
    size_t size;
    size_t capacity;
} IntVec;

typedef struct DoubleVec {
    double *data;
    size_t size;
    size_t capacity;
} DoubleVec;
~~~

如果库继续增加 List、Option、Pair、HashMap，很快会出现多套 declaration grammar。

目标不是“模拟 template”，而是统一 declaration entry：

~~~c
typed(Vec, IntVec, int);
typed(Vec, DoubleVec, double);
typed(Option, MaybeUser, User);
~~~

这里一行声明至少固定三件事：

- Generic kind：Vec / Option；
- concrete C name：IntVec / MaybeUser；
- element/application type：int / User。

调用侧仍然使用 ordinary C 名称，例如 IntVec_init、IntVec_push_back、MaybeUser_has_value。

Generic 主要发生在 declaration/build plane，不要求 hot path 变成动态 runtime。

---

## 2. Struct：让字段事实只有一个来源

Plain C struct：

~~~c
typedef struct User {
    uint64_t id;
    const char *name;
    double score;
} User;
~~~

如果 DataBind、debug tooling、Mock、schema tooling 都需要字段信息，手工再维护一份 metadata 就会漂移。

可以把字段事实写成 rows：

~~~c
Struct(User,
    (uint64_t, id),
    (const char *, name),
    (double, score)
);
~~~

同一组 rows 可以生成：

- C struct declaration；
- field count；
- field descriptors；
- field lookup；
- descriptor-facing structural information。

关键不是少写 typedef，而是：

> User fields 只有一个 authoritative source。

如果一个字段被删除，所有依赖它的 generated artifact 应一起变化，而不是靠开发者记住修改五份表。

---

## 3. Traits：让 Capability 与函数槽来自同一事实

错误设计通常把 capability flag 与 function pointer 分开维护：

~~~c
traits.flags =
    TRAIT_EQUAL |
    TRAIT_HASH |
    TRAIT_DESTROY;

traits.equal = user_equal;
traits.hash = user_hash;
traits.destroy = user_destroy;
~~~

这里同一事实写了两遍。

更好的输入是 tagged rows：

~~~c
Traits(User,
    (equal, user_equal),
    (hash, user_hash),
    (destroy, user_destroy)
);
~~~

Generator 同时产生：

~~~c
flags |= TRAIT_EQUAL;
traits.equal = user_equal;
~~~

以及其他 rows。

因此不存在“flag says HASH but hash slot is NULL”这种内部漂移。

Trait 仍然是 finite capability set；它不需要变成动态 object model。

## 4. Finite Type Universe 与 Generic Identity

一个 type descriptor 可以近似表示为：

~~~c
typedef struct cmeta_type_desc {
    uint64_t semantic_id;
    const char *name;
    size_t size;
    size_t align;
    uint32_t kind;
} cmeta_type_desc;
~~~

最重要的规则不是 pointer equality，而是 semantic identity。

不同 Translation Unit 可能各自产生一个 Pair<int,double> descriptor：

~~~text
TU A descriptor address != TU B descriptor address
~~~

但如果 Generic constructor 与 arguments 相同，它们应代表同一个 semantic type。

可以把 Generic application identity 写成：

~~~text
identity(Vec<int>)
    =
GenericConstructorId(Vec)
+
identity(int)
~~~

更复杂的 Pair：

~~~text
identity(Pair<int,double>)
    =
GenericConstructorId(Pair)
+
identity(int)
+
identity(double)
~~~

这让 Multi-TU、DSO、Plugin 和 generated code 可以比较 meaning，而不是赌 descriptor address 恰好唯一。

支持集合保持 finite：

> supported type set is finite；unsupported type fails explicitly。

有限不是缺陷，它让 dispatch、diagnostics、ABI 和 proof boundary 都可控。

---

## 5. TypeFunction：把有限类型关系写成数据

很多 C 代码需要表达有限 relation，例如 CommonArithmetic：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);
~~~

一条 row：

~~~text
(int, double, double)
~~~

表示：

~~~text
CommonArithmetic(int, double) = double
~~~

它不是 secret compiler，也不做 best-effort conversion。

如果没有：

~~~text
(long, User, ???)
~~~

那么 relation 就不存在，应该在 compile/admission boundary 明确失败。

可以把 rule 写成：

~~~text
lookup(Relation, args)
    = exactly one row
        -> result

lookup(Relation, args)
    = no row
        -> UNSUPPORTED

lookup(Relation, args)
    = multiple rows
        -> INVALID_DEFINITION
~~~

这比 scattered _Generic / #ifdef / manual lookup table 更容易检查和 formalize。

## 6. 从多个 Generic Family 到工程边界

Generic 的目标不是为每个 T 复制整套 runtime algorithm。

这里必须拆成两个时间层次，不能用一条模糊箭头混在一起：

**Build time：**

~~~text
typed(Vec, IntVec, int)
      ↓ generate
concrete C wrapper
~~~

**Runtime call：**

~~~text
concrete C wrapper
      ↓ direct call
shared ordinary C implementation
~~~

例如 wrapper 只负责 size、cast、type descriptor：

~~~c
static inline bool
IntVec_push_back(IntVec *v, int value)
{
    return vec_push_back_raw(
        &v->raw,
        &value,
        sizeof(value),
        CMetaType(int));
}
~~~

真正的 growth / allocation / move algorithm 仍然共享。

这样 Generic 不会迅速变成 code-bloat generator。

工程边界保持明确：

- declaration/type wrapper 可以生成；
- shared algorithm 尽量 compiled once；
- ownership 与 allocator policy 仍然显式；
- unsupported Generic kind/arity 直接 fail；
- 不因为 Generic 而引入 hidden allocation 或 dynamic dispatch。

## 7. Evidence：C / Toolchain Qualification

这层主要靠 toolchain evidence，不靠 Lean 替代 compiler。

### 7.1 Compile-pass

合法 Generic declaration 必须能独立 compile。

### 7.2 Compile-fail

错误 kind、错误 arity、缺失 TypeFunction row、重复 Trait tag 必须 fail early。

### 7.3 Multi-TU

两个 Translation Unit 各自获得同一个 semantic type descriptor：

~~~c
const cmeta_type_desc *a = pair_type_from_tu_a();
const cmeta_type_desc *b = pair_type_from_tu_b();

assert(a != b);
assert(cmeta_type_equal(a, b));
~~~

### 7.4 Cross-compiler

至少覆盖 GCC、Clang、MSVC-compatible mode，特别检查 variadic macro behavior、_Generic、alignment/layout assumption 和 generated public headers。

### 7.5 Code size / performance

比较 handwritten wrapper 与 generated wrapper；确认 Generic 不会因为实例化而复制不必要的大型 algorithm。

## 8. 从 Generic 到 Callable

到这里，data type、container application、Traits、finite relation 和 descriptor 已经拥有统一的 native semantic source。

下一步仍然有一类稳定事实没有统一：

- function input/output type；
- parameter direction；
- capture/context；
- ownership；
- effects；
- semantic properties；
- dispatch authority。

如果这些仍然分散在 function pointer、manual enum、context struct 和 flags 中，就会重复本章刚解决的问题。

因此下一章把同样方法应用到行为。下面表示 **semantic enrichment / executable projection**，不是 runtime 每次调用都会依次经过这些对象：

~~~text
ordinary function pointer
      ↓ describe semantics
FunctionDesc
      ↓ admit executable shape
Callable / exact adapter
~~~

---

## 9. What We Learned

本章真正完成的是一条 **design progression**，不是 runtime dataflow：

~~~text
repeated type facts
      ↓ make facts single-source
single-source rows
      ↓ generate declarations/metadata
generated ordinary C
      ↓ compare by meaning, not address
shared native semantic identity
~~~

其中：

| 问题 | 对象 |
|---|---|
| Generic application | typed(kind, ...) |
| Struct fields | Struct rows |
| capability | Traits rows |
| finite relation | TypeFunction |
| cross-TU meaning | semantic type identity |

所有这些仍然服务 ordinary C。

下一章继续同一个原则：**让一个 native function 的稳定语义也只定义一次。**
