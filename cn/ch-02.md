# 第二章：从宏到 Generic——把重复的类型契约收成一次定义

> **本章只解决一个 C 问题：**
>
> 同一个“类型事实”在 typedef、宏、容器、比较函数、descriptor、dispatch、序列化或回调边界里被反复写了很多次。
>
> 先看代码，再谈抽象。

第一章已经看到，宏最初非常有用：

~~~c
#define DECLARE_BUFFER(T, Name) \
    typedef struct Name {       \
        T *data;                \
        size_t size;            \
        size_t capacity;        \
    } Name
~~~

它可以把一段重复声明压成一行。

真正的问题出现在项目继续增长以后：我们不只有一个 Buffer，而是同时出现 List、Vec、Pair、Option、Result、HashMap、Callback、Range、Collector 等多组“同类但不同类型”的 API。

这时重复的已经不是几行 C 代码，而是这些契约：

- 这个类型叫什么；
- 元素类型是什么；
- 哪些操作属于它；
- 它支持什么能力；
- 怎样在别的模块中识别它；
- 怎样生成对应 wrapper。

本章的目标不是制造更复杂的宏，而是把这些契约收回到少量、统一、有限的定义里。

---

## 1. Plain C：第一个类型通常很好写

假设我们需要一个整数动态数组。

最直接的 C 完全没有问题：

~~~c
typedef struct IntVec {
    int *data;
    size_t size;
    size_t capacity;
} IntVec;

bool IntVec_init(IntVec *v, size_t capacity);
bool IntVec_push_back(IntVec *v, int value);
int *IntVec_at(IntVec *v, size_t index);
void IntVec_destroy(IntVec *v);
~~~

如果程序里只有这一种类型，停在这里就是正确答案。

然后项目又需要：

~~~c
typedef struct DoubleVec {
    double *data;
    size_t size;
    size_t capacity;
} DoubleVec;

bool DoubleVec_init(DoubleVec *v, size_t capacity);
bool DoubleVec_push_back(DoubleVec *v, double value);
double *DoubleVec_at(DoubleVec *v, size_t index);
void DoubleVec_destroy(DoubleVec *v);
~~~

再后来：

~~~c
typedef struct User {
    int id;
    double score;
} User;

typedef struct UserVec {
    User *data;
    size_t size;
    size_t capacity;
} UserVec;

bool UserVec_init(UserVec *v, size_t capacity);
bool UserVec_push_back(UserVec *v, User value);
User *UserVec_at(UserVec *v, size_t index);
void UserVec_destroy(UserVec *v);
~~~

这里真正重复的不是 push_back 的算法。

算法完全可以只有一份。

重复的是 `IntVec -> int`、`DoubleVec -> double`、`UserVec -> User` 这些绑定关系，以及每个绑定对应的 type、wrapper、function names、descriptor、traits、range adapter 和 collector adapter。这类重复一旦散开，维护成本会迅速高于算法本身。

---

## 2. 第一反应：继续写“更聪明的宏”

最自然的下一步通常是：

~~~c
#define DECLARE_VEC(Name, T)            \
    typedef struct Name {               \
        T *data;                        \
        size_t size;                    \
        size_t capacity;                \
    } Name;                             \
    bool Name##_init(Name *, size_t);   \
    bool Name##_push_back(Name *, T);   \
    T *Name##_at(Name *, size_t);       \
    void Name##_destroy(Name *)

DECLARE_VEC(IntVec, int);
DECLARE_VEC(DoubleVec, double);
DECLARE_VEC(UserVec, User);
~~~

这一步确实减少了重复。

但项目里很快会出现另一批宏：

~~~c
#define DECLARE_OPTION(Name, T) ...
#define DECLARE_PAIR(Name, K, V) ...
#define DECLARE_HASHMAP(Name, K, V) ...
#define DECLARE_RESULT(Name, T, E) ...
~~~

然后每个库又建立自己的入口：

~~~c
LIST_OF(int, IntList);
VEC_OF(User, UserVec);
PAIR_OF(int, User, UserById);
OPTION_OF(User, MaybeUser);
~~~

表面上已经“泛型化”了。

但用户必须记住每一种 Generic kind 对应哪个宏、参数顺序、generated name 的位置，以及哪个头文件注册哪个 family。于是宏本身又成为新的重复接口。

真正需要统一的不是宏展开技术，而是：

> **Generic declaration 的入口。**

---

## 3. Generic 的第一价值：把不同宏 family 收成一个入口

本版 CMeta 的公共入口是：

~~~c
typed(kind, generated_name, type_arguments...);
~~~

例如 CMeta value kinds：

~~~c
#include <cmeta/meta.h>

typedef struct User {
    int id;
} User;

typed(Option, MaybeUser, User);
typed(Pair, UserScore, User, double);
typed(Tuple, Point3, double, double, double);
~~~

CSTL 也使用同一个入口注册自己的 container kinds：

~~~c
#include <cstl/typed.h>

typed(List, IntList, int);
typed(Vec, IntVec, int);
typed(HashMap, IntValuesById, int, int);
~~~

用户不再在 `DECLARE_LIST`、`DECLARE_VEC`、`DECLARE_HASHMAP`、`DECLARE_OPTION`、`DECLARE_PAIR` 之间选择，而只写 `typed(kind, name, ...)`。

这不是为了让语法更“漂亮”。

它解决的是更实际的问题：

> **整个工程只有一条 Generic declaration protocol。**

---

## 4. typed(...) 实际做的事情很小

本版 CMeta 的真实 generic 路由核心非常短：

~~~c
#define CMETA_TYPED_GENERIC_I(kind, ...) \
    CMETA_PP_CAT(CMETA_TYPED_, kind)(__VA_ARGS__)

#define CMETA_TYPED_GENERIC(kind, ...) \
    CMETA_TYPED_GENERIC_I(kind, __VA_ARGS__)

#define CMETA_TYPED_ROUTE_1(kind, ...) \
    CMETA_TYPED_GENERIC(kind, __VA_ARGS__)

#define CMETA_TYPED_ROUTE_0(kind, ...) \
    CMETA_TYPED_FALLBACK(kind, __VA_ARGS__)

#define typed(kind, ...) \
    CMETA_TYPED_ROUTE(kind, __VA_ARGS__)
~~~

库只需要注册有限的 generic kind。

于是：

~~~c
typed(Vec, IntVec, int);
~~~

最终路由到这个 kind 对应的 `CMETA_TYPED_Vec(IntVec, int)`。

真正的 container algorithm 仍然可以是普通 compiled C。

也就是说：

~~~text
Generic declaration
        ↓
生成 typed wrapper / metadata
        ↓
调用普通 C algorithm
~~~

而不是让每一种 `T` 都复制一整份 runtime implementation。这是有限 Generic 和“模板化整个程序”的根本区别。

---

## 5. 前后差异：重复的是类型契约，不是容器算法

不用 Generic 时，调用点可能长成这样：

~~~c
IntVec ints = {0};
UserVec users = {0};

IntVec_init(&ints, 64);
UserVec_init(&users, 64);

IntVec_push_back(&ints, 7);

User u = {.id = 42};
UserVec_push_back(&users, u);

IntVec_destroy(&ints);
UserVec_destroy(&users);
~~~

这里本身没有错。

问题是为了得到这些 API，我们往往手写或维护了两套 declaration contract。

使用一个有限 Generic 声明后：

~~~c
#include <cstl/typed.h>

typed(Vec, IntVec, int);
typed(Vec, UserVec, User);

int main(void)
{
    IntVec ints = {0};
    UserVec users = {0};

    IntVec_init(&ints, 64u);
    UserVec_init(&users, 64u);

    IntVec_push_back(&ints, 7);

    User u = {.id = 42};
    UserVec_push_back(&users, u);

    IntVec_destroy(&ints);
    UserVec_destroy(&users);
}
~~~

调用侧仍然是普通、具体、可调试的 C 名字：

~~~text
IntVec_init
IntVec_push_back
UserVec_push_back
~~~

Generic 主要发生在声明阶段。

它没有要求 runtime 变成一个“动态模板系统”。

---

## 6. 生成后的目标仍然应该像普通 C

对于：

~~~c
typed(Vec, IntVec, int);
~~~

可以把生成结果**概念性地**理解为：

~~~c
typedef struct IntVec {
    cstl_vec raw;
} IntVec;

static inline bool
IntVec_push_back(IntVec *self, int value)
{
    return cstl_vec_push_back(&self->raw, &value);
}
~~~

这不是本版源码的逐字展开，而是设计上必须保持三个部分：**具体 C type、具体 typed wrapper、共享的 ordinary C implementation**。

所以本书后面不会反复解释“宏最后还是生成 C”。

这只是基础机制。

更重要的问题是：

> **有了统一、有限、类型化的 Generic 声明以后，我们可以把哪些原来分散的契约变成一次定义？**

---

## 7. 第二类重复：struct 定义与 metadata 定义分离

考虑一个很常见的工程写法：

~~~c
typedef struct User {
    int id;
    double score;
} User;

typedef struct FieldInfo {
    const char *name;
    size_t offset;
    size_t size;
} FieldInfo;

static const FieldInfo user_fields[] = {
    {"id",    offsetof(User, id),    sizeof(int)},
    {"score", offsetof(User, score), sizeof(double)},
};
~~~

这里的 `id`、`score`、`int`、`double` 都写了两遍。

以后再加 serializer、binding、debug printer，可能再写第三遍、第四遍。

这类 bug 很典型：

~~~c
typedef struct User {
    long id;
    double score;
} User;

/* forgotten */
static const FieldInfo user_fields[] = {
    {"id", offsetof(User, id), sizeof(int)},
};
~~~

真正的问题不是 C 不能表达 struct。

而是：

> **同一个 field fact 被多个系统各自维护。**

---

## 8. Struct(...)：让结构事实只写一次

CMeta 的 application DSL 可以直接把这份事实写成：

~~~c
Struct(User,
    (int, id),
    (double, score)
);
~~~

然后同一份 row data 可以产生 C struct declaration、field metadata、field count、field lookup 和 descriptor-facing structure information。

调用代码仍然直接使用：

~~~c
User user = {
    .id = 7,
    .score = 98.5
};

printf("%d %.1f\n", user.id, user.score);
~~~

这里 Meta 的价值不是“少写 typedef”，而是 **User fields 只有一个权威来源**。

以后 Data Binding、debug tooling、RPC schema adapter 等高级层需要结构信息时，不必再分别发明 `UserSchema`、`UserJsonFields`、`UserDbColumns`。

这正是第一部分反复强调的主题：

> **有限 Meta 首先消除的是 knowledge duplication。**

---

## 9. 第三类重复：capability 与函数槽位也会漂移

普通 C 中很容易写出：

~~~c
typedef struct UserOps {
    bool (*equal)(const User *, const User *);
    uint64_t (*hash)(const User *);
    void (*destroy)(User *);
} UserOps;

enum {
    USER_CAN_EQUAL   = 1u << 0,
    USER_CAN_HASH    = 1u << 1,
    USER_CAN_DESTROY = 1u << 2
};

static const UserOps user_ops = {
    .equal = user_equal,
    .hash = user_hash,
    .destroy = user_destroy
};
~~~

这里 capability flags 与 function slots 又在维护同一事实：User 支持 equal、hash、destroy。只要漏改一边，contract 就可能失真。

---

## 10. Traits(...)：从同一行同时生成 capability 与函数槽

本版 CMeta 的 Traits 写法是：

~~~c
Traits(User,
    (equal, user_equal),
    (hash, user_hash),
    (destroy, user_destroy)
);
~~~

实现会从同一组 tagged rows 同时生成 **trait flags** 和 **function slots**。

也就是说，`(equal, user_equal)` 这一个事实同时决定 `CMETA_TRAIT_EQUAL` 存在以及 `traits.equal = user_equal`。这样不会再出现“flag says HASH but hash function slot is NULL”这种漂移。

这就是 Meta 很适合解决的一类 C 问题：

> **两个必须同步变化的声明，应该来自同一个事实源。**

---

## 11. _Generic 很有用，但它不是完整的 Generic 设计

C11 已经有：

~~~c
_Generic
~~~

例如：

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                    \
    double: print_double               \
)(x)
~~~

它可以做 compile-time selection。

但它只能选择已经存在的表达式/函数。它不会自动解决：

- 一个 Generic kind 怎样实例化；
- 不同库怎样共享同一个 generic declaration syntax；
- descriptor 从哪里来；
- traits 怎样和 generated type 关联；
- Generic application 怎样拥有 identity。

所以 `_Generic` 是工具，而 `typed(kind, ...)`

是工程层的 Generic protocol。

两者不是同一个层次。

---

## 12. 有限 Type Universe：只处理我们明确支持的类型

CMeta 不尝试“反射任意 C 类型”。

它维护有限的 known/callable type universe。

调用侧可以使用：

~~~c
const cmeta_type_desc *desc = CMETA_TYPEOF(int);
~~~

而不是：

~~~text
运行时解析一个字符串 "int"
~~~

对于没有注册的类型，系统不猜。

这种设计很适合 C：

~~~text
supported type set
    is finite

unsupported type
    fails explicitly
~~~

有限不是缺陷。

它让：

~~~text
dispatch
descriptor
signature family
generic relation
ABI
compile diagnostics
~~~

都可以保持可控。

---

## 13. Generic Identity：不能把 descriptor 地址当成“类型本身”

一旦同一个 generic type 可能在不同 Translation Unit 生成 header-local metadata：

~~~text
TU A: descriptor A for Pair<int,double>
TU B: descriptor B for Pair<int,double>
~~~

它们的地址完全可能不同。

所以不能写：

~~~c
if (a_desc == b_desc) {
    /* same semantic type */
}
~~~

必须比较 semantic identity。

这是从“宏 demo”进入真实 C library 的关键变化：

> **生成出来的 object 地址只是 representation，不是 semantic type identity。**

这一点后面会在 ABI/Multi-TU 工程章节继续展开。

---

## 14. 第四类重复：类型关系也经常被写成很多 if / _Generic

假设我们希望定义一个很小的 common arithmetic relation：

~~~text
int + int       -> int
int + double    -> double
double + int    -> double
double + double -> double
~~~

普通 C 可以写：

~~~c
enum TypeId {
    TYPE_INT,
    TYPE_DOUBLE
};

enum TypeId common_type(enum TypeId a, enum TypeId b)
{
    if (a == TYPE_INT && b == TYPE_INT)
        return TYPE_INT;

    if (a == TYPE_INT && b == TYPE_DOUBLE)
        return TYPE_DOUBLE;

    if (a == TYPE_DOUBLE && b == TYPE_INT)
        return TYPE_DOUBLE;

    if (a == TYPE_DOUBLE && b == TYPE_DOUBLE)
        return TYPE_DOUBLE;

    abort();
}
~~~

如果 compile-time 还需要同一关系，我们又会写一份 _Generic 或宏 table。

于是同一 relation 又被复制到 compile-time relation、runtime/admission relation、documentation 和 tests。

---

## 15. TypeFunction(...)：把有限类型关系写成数据

CMeta 可以直接声明：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double),
    (double, int, double),
    (double, double, double)
);

typedef TypeEval(CommonArithmetic, int, double) result_type;
~~~

这里真正重要的是 row `(int, double, double)`：它是一条明确关系。

没有隐藏推导。

没有默认分支。

没有“尽量转换”。

如果不存在 `(long, User, ???)` 这条 row，就应该在正确边界失败。

---

## 16. ValueFunction / Predicate：同一种方法也可以表达能力约束

例如：

~~~c
ValueFunction(TypeRank,
    (int, 1),
    (double, 2)
);

enum {
    int_rank = ValueEval(TypeRank, int),
    double_rank = ValueEval(TypeRank, double)
};
~~~

或者：

~~~c
Predicate(Hashable,
    (int, 1),
    (double, 1),
    (opaque, 0)
);

Require(Hashable, int);
~~~

对于一个有限 C 系统，这已经可以覆盖很多以前散落在 `#ifdef`、`_Static_assert`、`_Generic`、macro specialization 和 manual lookup table 中的关系。

---

## 17. 为什么“不提供 Default”反而是优势

假设：

~~~c
TypeFunction(CommonArithmetic,
    (int, int, int),
    (int, double, double)
);
~~~

然后调用：

~~~c
typedef TypeEval(CommonArithmetic, User, double) bad_type;
~~~

CMeta 不会 fallback to `void *`、fallback to `int` 或 try best conversion。缺少 row 本身就是事实：

> **这个 relation 没有定义。**

在系统编程里，这种 fail-fast 往往比一个“聪明默认值”更可靠。

因为默认值会把**设计遗漏**变成**运行时行为**。

---

## 18. 一个完整的 before / after：多个 Generic family

假设应用需要 `List<int>`、`Vec<int>`、`Option<int>` 和 `Pair<int,double>`。

如果每个库都有自己的 macro grammar，可能变成：

~~~c
DECLARE_LIST(IntList, int);
DECLARE_VEC(IntVec, int);
DECLARE_OPTION(MaybeInt, int);
DECLARE_PAIR(IntDouble, int, double);
~~~

甚至不同项目会使用完全不同的参数顺序：

~~~c
MAKE_LIST(int, IntList);
VEC_DECLARE(IntVec, int);
OPTION_OF(int, MaybeInt);
PAIR_OF(int, double, IntDouble);
~~~

维护者必须记住四种“语言”。

统一后：

~~~c
#include <cmeta/meta.h>
#include <cstl/typed.h>

typed(List, IntList, int);
typed(Vec, IntVec, int);
typed(Option, MaybeInt, int);
typed(Pair, IntDouble, int, double);
~~~

这里的价值不是少几个字符，而是 **all finite generic declarations share one grammar**。新增一个 library generic kind 时，也不需要让用户再学一个新的顶层宏语言。

---

## 19. CMeta 的边界：Generic 不应该拥有算法

这是一个很容易走偏的地方。

如果：

~~~c
typed(Vec, IntVec, int);
~~~

如果最终导致复制一份完整 vec algorithm、allocator logic 和 sort/search implementation，那么 Generic 会迅速变成 code-bloat generator。

更合理的边界是：

~~~text
typed declaration
    owns:
        type-safe surface
        names
        metadata
        adapters

ordinary C library
    owns:
        allocation
        growth
        search
        sort
        storage algorithm
~~~

这使 Generic 成为 interface/code-generation layer，而不是另一个 runtime。

---

## 20. 这能解决什么问题：CSTL 是最直接的工程例子

传统 C container API 常见两条路线。

第一条，全部 erased：

~~~c
vec_push(&v, &value, sizeof(value));
~~~

优点是算法复用。

缺点是 `sizeof`、cast、element type、operation naming 都由 caller 自己维护。

第二条，每个类型复制一个 container implementation。

优点是调用类型化。

缺点是代码和契约重复。

有限 Generic 可以把两者组合起来：

~~~c
typed(Vec, UserVec, User);

UserVec users = {0};

UserVec_init(&users, 64u);
UserVec_push_back(&users, (User){.id = 7});
User *u = UserVec_at(&users, 0u);
UserVec_destroy(&users);
~~~

typed wrapper 保留静态类型。

底层算法仍然共享普通 C 实现。

这就是本书所说的：

> **用有限 Meta 改善 C，而不是逃离 C。**

---

## 21. 更重要的结果：后面的高级层可以相信“类型事实只有一份”

当 CFlow 以后看到：

~~~text
Map<int, double>
~~~

它不应该重新建立另一套：

~~~text
FlowTypeInt
FlowTypeDouble
~~~

当 CBind 看到 User，它也不应该再建立 BindUserSchema。

当 RPC 看到 request / response type，它同样不应该创建第三套 type universe。

CMeta 的真正价值从这里开始显现：

> **高级系统可以复用同一个有限 type / trait / generic / identity contract。**

这会直接影响后面 Graph、Stream、State Machine、Actor、Serialization、RPC 的设计复杂度。

---

## 22. 这一章怎样验证：用 C/toolchain 证据

这一章的工程证据很朴素。

### 编译成功

~~~c
typed(Option, MaybeInt, int);
typed(Pair, IntDouble, int, double);
~~~

应该在受支持 compiler 上生成合法 C。

### 编译失败

错误 kind、错误 arity、缺失 relation、重复 trait tag 应该：

~~~text
fail early
~~~

而不是进入 runtime 猜测。

### Multi-TU

两个 Translation Unit 可以拥有不同 representation object，但 semantic type identity 必须一致。

### Installed consumer

用户只包含 installed headers、链接 exported targets，也应该能使用同样的 Generic API。

这些都是 C/toolchain 问题。

## 23. 从 Generic 到 Callable：下一个重复契约是函数

到现在，我们已经可以让：

~~~text
data type
container application
traits
finite relation
descriptor
~~~

拥有统一的事实来源。

下一个问题会更麻烦。

普通 C callback 通常只有：

~~~c
int (*fn)(int);
~~~

或者：

~~~c
void (*fn)(void *);
~~~

但高级执行系统会同时需要知道：

~~~text
输入类型
输出类型
capture/context
ownership
effects
properties
dispatch authority
~~~

如果这些信息也分别维护：

~~~text
function pointer
manual enum
manual context struct
manual flags
~~~

我们又会重新回到本章开头的问题：

> **同一个行为契约被写了很多次。**

所以下一章不再研究“怎么写更多宏”。

下一章研究：

> **怎样让一个函数也成为有限、类型化、可组合的 C value。**

这就是 Callable、Lambda 与 Bind 的起点。

## 24. What We Learned

这一章最重要的不是某个宏技巧。

而是四个工程结论。

第一：

> **宏真正难维护的阶段，不是宏太少，而是不同宏 family 开始维护相同契约。**

第二：

> **Generic 的价值首先是统一声明协议，而不是模拟 C++ template。**

第三：

> **Struct、Traits、typed、TypeFunction 这些能力都应该把“同一事实写多次”收成一个 source of truth。**

第四：

> **最终 API、数据布局和算法仍然应该尽可能是普通 C。**

可以把本章压缩成：

~~~text
duplicated C declarations
        ↓
duplicated macro families
        ↓
one finite Generic protocol
        ↓
single-source type/trait/relation facts
        ↓
ordinary typed C API
~~~

这就是 CMeta 真正开始解决的问题。
