# 第一章：CMeta 的起点——从写 C 宏的痛苦开始

> **本章只回答一个问题：**
>
> 当普通 C 中的重复开始从“几行代码”变成“同一份稳定事实被多处维护”时，应该怎样把这些事实显式化，而不引入新的 runtime？

---

## 1. Plain C：重复代码本身并不可怕

先写最普通的 compare：

~~~c
int int_compare(const int *a, const int *b)
{
    return (*a > *b) - (*a < *b);
}

int long_compare(const long *a, const long *b)
{
    return (*a > *b) - (*a < *b);
}
~~~

如果项目只有两三个函数，停在这里完全合理。

当模式稳定后，宏可以减少机械重复：

~~~c
#define DEFINE_COMPARE(T)                  \
    static int T##_compare(                \
        const T *a,                        \
        const T *b)                        \
    {                                      \
        return (*a > *b) - (*a < *b);      \
    }

DEFINE_COMPARE(int)
DEFINE_COMPARE(long)
DEFINE_COMPARE(float)
~~~

这仍然只是 ordinary C code generation。

---

## 2. 第一层问题：宏调用本身也会重复

项目继续增长后，compare、hash、copy、destroy 都需要同一组类型：

~~~c
DEFINE_COMPARE(int)
DEFINE_COMPARE(long)
DEFINE_COMPARE(float)

DEFINE_HASH(int)
DEFINE_HASH(long)
DEFINE_HASH(float)

DEFINE_COPY(int)
DEFINE_COPY(long)
DEFINE_COPY(float)
~~~

真正重复的已经不是函数体，而是这个事实：

- 系统支持 int；
- 系统支持 long；
- 系统支持 float。

于是把事实写一次：

~~~c
#define BUILTIN_TYPES(X) \
    X(int)               \
    X(long)              \
    X(float)
~~~

不同消费者展开同一份 facts：

~~~c
#define GEN_COMPARE(T) DEFINE_COMPARE(T)
BUILTIN_TYPES(GEN_COMPARE)

#define GEN_HASH(T) DEFINE_HASH(T)
BUILTIN_TYPES(GEN_HASH)
~~~

这一步非常重要：

> **宏从 code reuse 开始，真正有价值的方向却是 fact reuse。**

---

## 3. Preprocessor 的边界很快暴露出来

### 3.1 逗号会破坏“一个参数”的直觉

例如 PAIR(int, double) 对 preprocessor 来说，逗号默认就是参数分隔符。

如果一个“类型表达式”本身含逗号，就必须通过括号、defer/unparen 或专门 protocol 保护：

~~~c
#define UNPAREN(...) __VA_ARGS__
#define TYPE_ARG(x) UNPAREN x

TYPE_ARG((Pair, int, double))
~~~

这说明 preprocessor 并不知道什么是 type expression。

### 3.2 for each 需要显式的有限展开

C preprocessor 没有通用循环。

通常只能提供有限 arity：

~~~c
#define FOR_EACH_1(M, a) \
    M(a)

#define FOR_EACH_2(M, a, b) \
    M(a) M(b)

#define FOR_EACH_3(M, a, b, c) \
    M(a) M(b) M(c)
~~~

然后通过 NARG 选择对应实现。

有限并不是缺陷；它恰好让能力保持 bounded 和可测试。

### 3.3 Nested macro 需要明确 expansion discipline

例如：

~~~c
#define CAT_I(a, b) a##b
#define CAT(a, b) CAT_I(a, b)
~~~

两层宏是为了让参数先展开，再 token-paste。

这种技巧一旦散落到每个 subsystem，维护成本很快超过收益。

---

## 4. 最大限制不是语法，而是“宏不知道类型”

对 preprocessor 来说，int、double、User 都只是 token。

它不知道：

- User 是否支持 hash；
- Vec<int> 的元素类型是什么；
- 两个 type token 是否表示同一个 semantic type；
- 一个 function 的 input/output type 是什么。

这决定了一个边界：

> **Preprocessor 可以生成结构，但不能自己成为 semantic authority。**

真正的 Modern C 设计需要把 type facts 交给更明确的数据模型。

---

## 5. C11 _Generic 打开了 compile-time type selection

C11 提供 _Generic：

~~~c
#define print_value(x) _Generic((x), \
    int: print_int,                  \
    long: print_long,                \
    double: print_double             \
)(x)
~~~

这让 C 可以直接根据 static C type 做有限选择。

但 _Generic 仍然只回答：

> 给定一个已知 C expression，选择哪个已有 expression/function？

它不会自动定义 semantic type identity、Generic constructor、field metadata、traits、FunctionDesc 或 Multi-TU identity。

所以 _Generic 是 semantic layer 的一个工具，不是 semantic layer 本身。

---

## 6. 从 token table 到有限 Native Semantic IR

真正需要保存的，是稳定 native facts：

| C 事实 | Semantic object |
|---|---|
| 一个 type | TypeDesc / semantic identity |
| struct fields | Struct metadata |
| capability | Traits |
| native function | FunctionDesc |
| interface contract | InterfaceDesc |

例如：

~~~c
typedef struct User {
    uint64_t id;
    const char *name;
} User;
~~~

如果 serializer、debugger、DataBind、Mock 都需要知道字段，就不应该各写一份。

可以把事实写成一组 rows：

~~~c
Struct(User,
    (uint64_t, id),
    (const char *, name)
);
~~~

这一份 row data 可以生成 C declaration，也可以生成 metadata。

原则不是“所有 C 都写成 DSL”，而是：

> **只有稳定且被多个消费者重复维护的事实，才值得成为 semantic data。**

---

## 7. 这层抽象必须保持 finite、explicit、bounded

第一章建立三个长期约束。

### Finite

支持的 type family、macro arity、relation row 都是有限集合。

### Explicit

没有隐藏 default；unsupported relation 直接 compile/admission failure。

### Bounded

Macro expansion、generated object size、relation table 都必须有清晰上限。

这使错误可以在 build/control plane 暴露，而不是变成 runtime guess。

---

## 8. Macro 层不应该偷偷拥有 Runtime

真正的链路是 **build-time generation pipeline**，不是 runtime dataflow：

~~~text
facts / schema
      ↓ generate
preprocessor / generator
      ↓ emit
ordinary C declarations / metadata
      ↓ compile
ordinary C compiler
~~~

Macro/Meta 层不应该因为“方便”而偷偷引入 object runtime、dynamic dispatcher、hidden scheduler 或 automatic ownership system。

如果一个能力需要这些东西，它已经属于后面的 Runtime/Execution layer。

---

## 9. Lean 在这一章的边界

这里不需要 Lean 去证明某个 compiler 会正确展开 DEFINE_COMPARE(int)。

这类 claim 应该用：

- preprocess output；
- compile-pass / compile-fail；
- cross-compiler test；
- generated-symbol test。

Lean 真正适合的是下一层 semantic question，例如：

- finite type relation 是否 deterministic；
- normalization 是否 preserve meaning；
- two descriptors 是否代表同一 semantic type；
- rewrite 是否保持 observable semantics。

> **Proof 不能替代 toolchain evidence，toolchain test 也不能替代 semantic proof。**

---

## 10. Engineering Evidence

### Preprocess

~~~bash
cc -E sample.c
~~~

检查 generated C 是否仍然是可读、可调试、愿意手写维护的 C。

### Compile-pass / compile-fail

合法 declaration 必须 compile；unsupported relation 必须在靠近 declaration 的地方失败。

### Cross-compiler

至少覆盖 GCC、Clang 和 MSVC-compatible preprocessing mode。

### Runtime

理想结果是：

> **没有新的 runtime cost center。**

如果 Meta 版本与手写版本最终生成相同或等价的 ordinary C，价值发生在 build/control plane，而不是 hot path。

---

## 11. What We Learned

本章没有发明一个“C 元编程语言”。

只完成了三步：

1. 用 macro 删除机械代码重复；
2. 发现更重要的是稳定 facts 的重复；
3. 把后续设计限制在 finite、explicit、bounded 的 semantic model。

下一章会继续这个方向：

> **当 type facts 有了唯一来源，Generic、Struct、Traits 与 finite type relation 怎样共享同一套 Native Semantic IR？**
