# 第八章：从重复 API 契约到 Contract Compiler——DataBind IDL、FunctionDesc 与多后端生成

> **本章路线**
>
> 这一章不再列举 Serialization、RPC、Plugin、Workflow 等“高级应用”。
>
> 我们只跟踪一个真实问题：
>
> ~~~text
> 同一个业务操作
> 为什么要在
> C prototype / HTTP / RPC / Plugin / OpenAPI / Mock / WASM
> 里重复描述？
> ~~~
>
> 然后一步一步把这些重复收成：
>
> ~~~text
> DataBind Contract IR
>         +
> CMeta Native Semantic IR
>         ↓
> BindingPlan / exact adapter
>         ↓
> HTTP / RPC / Plugin / WASM / OpenAPI / Mock
> ~~~
>
> 本章的目标不是发明更多 runtime。
>
> 目标恰好相反：
>
> **把更多决定提前到 compiler/control plane，让 runtime 只执行已经编译好的 plan。**

---

## 1. Plain C：一个业务函数本身没有问题

假设系统只有一个查询用户的函数：

~~~c
typedef struct UserRepository UserRepository;

typedef struct User {
    uint64_t id;
    const char *name;
} User;

int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

这已经是很好的 C。

调用也很简单：

~~~c
User user = {0};

int rc = get_user(repo, 42u, &user);

if (rc != 0) {
    ...
}
~~~

如果程序只有一个调用点，不需要任何 IDL。

问题出现在这个 operation 开始被多个系统暴露。

---

## 2. HTTP 第一次重复描述它

一个普通 HTTP handler 可能是：

~~~c
static int get_user_http(
    void *ctx,
    const chttp_server_request_view *request,
    chttp_server_response *response)
{
    UserRepository *repo = ctx;

    const char *id_text =
        chttp_server_request_param(request, "id");

    uint64_t id = 0;

    if (parse_u64(id_text, &id) != 0)
        return chttp_server_reply(response, 400, "text/plain",
                                  "invalid id", 10);

    User user = {0};

    if (get_user(repo, id, &user) != 0)
        return chttp_server_reply(response, 404, "text/plain",
                                  "not found", 9);

    char json[1024];
    size_t json_size = encode_user_json(json, sizeof(json), &user);

    return chttp_server_reply(
        response,
        200,
        "application/json",
        json,
        json_size);
}
~~~

然后注册：

~~~c
chttp_server_get(
    server,
    "/users/:id",
    get_user_http,
    repo);
~~~

这里第一次重复出现 operation identity、输入字段 `id`、输入类型 `uint64`、结果 `User` 和 error mapping。HTTP 本身没有错。

重复知识开始出现。

---

## 3. RPC、OpenAPI、Plugin 又各写一次

RPC 可能再写：

~~~c
crpc_server_register(
    rpc,
    "UserService.GetUser",
    get_user_rpc,
    repo);
~~~

OpenAPI 再描述：

~~~text
GET /users/{id}

parameter:
    id : uint64

response 200:
    User

response 404:
    NotFound
~~~

Plugin 再维护 export_id、contract_id、contract_version、function metadata 和 adapter。

Mock 再写一份函数签名。

WASM 再定义 host/guest ABI。

最后我们得到 C prototype、HTTP route/decoder、RPC method/decoder、OpenAPI、Plugin export、Mock declaration 和 WASM ABI。这些代码不一定逐行相同。

但它们共同维护一份事实：

> **UserService.GetUser 是一个 typed logical operation。**

这就是新的重复知识。

---

## 4. FunctionDesc 解决 native truth，但还不是 logical contract

第三章已经把普通 C 函数描述成 `cmeta_function_desc`。

概念上：

~~~c
static const cmeta_param_desc get_user_params[] = {
    { "repo",     CMETA_TYPE(UserRepository_ptr), CMETA_IN },
    { "id",       CMETA_TYPE(uint64_t),           CMETA_IN },
    { "out_user", CMETA_TYPE(User_ptr),           CMETA_OUT }
};

static const cmeta_function_desc get_user_desc = {
    .name = "get_user",
    .return_type = CMETA_TYPE(int),
    .params = get_user_params,
    .param_count = 3
};
~~~

这告诉工具 **native C function 是什么**。

但它仍然没有回答：

- 业务操作叫什么？
- logical request 是什么？
- logical response 是什么？
- `repo` 是业务输入，还是 host dependency？
- HTTP/RPC/Plugin 是否应该看到 `repo`？

所以 **FunctionDesc != Service Contract**。

这就是为什么 Function Reflection 并不能替代 IDL。

---

## 5. DataBind IDL 描述 logical contract

现在把逻辑契约单独写出来：

~~~text
message GetUserRequest {
    uint64 id;
}

message GetUserResponse {
    User user;
}

service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

这里没有：

~~~text
GET
POST
/path
RPC method alias
DLL name
WASM export
C function name
~~~

这很重要。

IDL 回答 **what is promised?**；CMeta 回答 **what is implemented in C?**。

---

## 6. Service、Channel、Component 分别表达什么

DataBind 的核心 vocabulary 应该很小。

### Service

Service 表达 **Request → Response**。

例如：

~~~text
service UserService {
    GetUser: GetUserRequest -> GetUserResponse;
}
~~~

### Channel

Channel 表达 **Message / Event**。

例如：

~~~text
channel UserEvents {
    UserChanged;
}
~~~

### Component

Component 只组合 capability：

~~~text
component UserModule {
    service UserService;
    channel UserEvents;
}
~~~

它表示“哪些 capability 属于一个逻辑模块”，但不表示 DLL、process、HTTP server 或 WASM module；这些是后面的 projection。

---

## 7. 用户实现仍然是普通 C

compiler 可以为标准 Service ABI 生成 header：

~~~c
int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response);
~~~

用户只写：

~~~c
#include "user.generated.h"

int user_service_get_user(
    const GetUserRequest *request,
    GetUserResponse *response)
{
    User user = {0};

    if (repository_get(
            global_repository(),
            request->id,
            &user) != 0) {
        return USER_SERVICE_NOT_FOUND;
    }

    response->user = user;
    return 0;
}
~~~

这是最简单的 convention-first path。

但已有代码不一定长这样。

我们仍然希望能绑定：

~~~c
int get_user(
    UserRepository *repo,
    uint64_t id,
    User *out_user);
~~~

于是需要 compiler join。

---

## 8. Contract IR 与 Native IR 的 binding judgment

逻辑 operation：

~~~text
UserService.GetUser :
    GetUserRequest -> GetUserResponse
~~~

native function：

~~~text
get_user :
    (UserRepository*, uint64_t, User*) -> int
~~~

可以先写一个轻量 judgment：

~~~text
Γ ⊢ UserService.GetUser :
      GetUserRequest -> GetUserResponse

Γ ⊢ get_user :
      (UserRepository*, uint64_t, User*) -> int

Γ ⊢ repo : injected-context
Γ ⊢ GetUserRequest.id ↦ id : exact
Γ ⊢ out_user ↦ GetUserResponse.user : exact
────────────────────────────────────────────
Γ ⊢ bind(UserService.GetUser, get_user) : valid
~~~

这个 judgment 已经明确了四件事：

1. repo 不是 wire request；
2. request.id 绑定 native id；
3. native OUT User 构造 response.user；
4. binding 不是按参数位置盲猜。

---

## 9. 一个 binding compiler 实际做什么

不要写“自动绑定”。

给 pseudocode：

~~~text
compile_binding(operation, function):

    require operation.request exists
    require operation.response exists

    for each native parameter p:

        if p is injected context:
            bind p <- host context
            continue

        if p is IN:
            field = resolve_request_field(operation.request, p)
            require convertible(field.type, p.type)
            append ingress(field -> p)
            continue

        if p is OUT:
            field = resolve_response_field(operation.response, p)
            require writable_as(p.type, field.type)
            append egress(p -> field)
            continue

        reject unsupported direction

    require all required logical fields are satisfied

    invoke = generate_exact_adapter(function)

    return BindingPlan(
        ingress,
        invoke,
        egress)
~~~

关键不是某个具体 API 名。

关键是 compiler 的责任边界。

---

## 10. BindingPlan 是 control plane 的结果

概念性表示：

~~~c
typedef struct service_binding_plan {
    const databind_ingress_step *ingress;
    size_t ingress_count;

    const service_exact_adapter *invoke;

    const databind_egress_step *egress;
    size_t egress_count;
} service_binding_plan;
~~~

这里没有 HTTP request pointer、JSON-RPC envelope、Plugin handle 或 WASM memory pointer，因为 native binding 本身是 transport-neutral。

运行时只需要执行已经编译好的 ingress → native args → exact adapter → native outputs → egress 路径，得到 logical output。

---

## 11. 为什么不能用 universal dynamic invocation

看到 FunctionDesc 后，很容易问：既然参数都知道了，为什么不直接做一个万能 `invoke(desc, values[])`？

这会迅速碰到：

~~~text
ABI calling convention
struct return
alignment
variadic
platform ABI
ownership
typed pointer
compiler differences
~~~

所以职责明确分开：

| 对象 | 作用 |
|---|---|
| FunctionDesc | description |
| exact adapter | execution |

例如 generated adapter 可以只是：

~~~c
static int invoke_get_user(
    void *implementation,
    const void *request_ptr,
    void *response_ptr)
{
    UserRepository *repo = implementation;
    const GetUserRequest *request = request_ptr;
    GetUserResponse *response = response_ptr;

    return get_user(
        repo,
        request->id,
        &response->user);
}
~~~

运行时仍然是普通 C call。

---

## 12. HTTP 是 projection，不是 Service 语义

现在再生成 HTTP。

Service 本身的 `GetUser: GetUserRequest -> GetUserResponse` 并不知道它是不是 `GET /users/{id}`。

HTTP backend 根据 convention 或单独 projection config 编译：

~~~text
HTTP MethodPlan

method = GET
route  = /users/:id

ingress:
    path "id"
        -> GetUserRequest.id

egress:
    GetUserResponse
        -> JSON body

errors:
    NOT_FOUND -> 404
~~~

注意：GET、path、query、header、cookie、body placement 都属于 HTTP projection。

不进入 canonical Service IDL。

---

## 13. CHttp::Service 只执行已经生成的 plan

CHttp::Server 仍然是纯 transport/runtime：

~~~text
H1/H2
router
middleware
JWT
session
body sink
deferred response
streaming
WebSocket
file serving
~~~

它不需要理解 DataBind。

生成的 route 可以挂在已有接口上：

~~~c
chttp_server_route(
    server,
    plan->method,
    plan->route,
    chttp_service_dispatch,
    plan);
~~~

generic handler：

~~~c
static int chttp_service_dispatch(
    void *user,
    const chttp_server_request_view *request,
    chttp_server_response *response)
{
    const http_method_plan *plan = user;

    return http_method_plan_execute(
        plan,
        request,
        response);
}
~~~

hot path：

~~~text
request
    ↓
router
    ↓
HTTP MethodPlan
    ↓
precompiled ingress
    ↓
exact adapter
    ↓
precompiled egress
    ↓
response
~~~

hot path 不再 parse IDL、walk schema AST、lookup FunctionDesc 或 guess native ABI。

---

## 14. RPC 使用同一个 Service，但不同 MethodPlan

RPC backend 可以生成：

~~~text
RPC MethodPlan

wire_name:
    UserService.GetUser

params:
    id -> GetUserRequest.id

result:
    GetUserResponse -> result

errors:
    NOT_FOUND -> application error
~~~

CRPC runtime 仍然拥有 JSON-RPC envelope、batch、notification、deadline、cancel 和 transport；DataBind compiler 只生成 typed params/result binding。

所以 **HTTP runtime != RPC runtime**，但 logical Service Contract 是同一个。

---

## 15. OpenAPI 必须来自 Service + HTTP Projection

Service alone：

~~~text
GetUser:
    Request -> Response
~~~

不能告诉 OpenAPI：

~~~text
GET /users/{id}
~~~

所以正确 source 是：

~~~text
Service Contract
        +
HTTP MethodPlan / projection IR
        ↓
OpenAPI
~~~

例如：

~~~text
HTTP projection says:
    id comes from path

DataBind says:
    id is uint64 and required

        ↓

OpenAPI:
    path parameter id
    integer
    required = true
~~~

runtime 与 docs 从同一个 projection IR 生成。

这样不需要维护第二份 HTTP contract。

---

## 16. Plugin 也是 projection

同一个 component：

~~~text
component UserModule {
    service UserService;
}
~~~

选择：

~~~cmake
PROJECTIONS
    PLUGIN
~~~

compiler 可以生成：

~~~text
Plugin
└── UserService
    └── GetUser
        ├── FunctionDesc
        └── exact adapter
~~~

用户不手写 export table、manifest 或 `salts_plugin_query()`；这些都是 generated runtime machinery。

---

## 17. 但 Provider/vtable 不应该被强行变成 Service

Executor 是典型反例：它天然有 long-lived self 和一组 related operations。

例如：

~~~c
typedef struct cflow_executor {
    void *self;
    const cflow_executor_vtable *vtable;
} cflow_executor;
~~~

Plugin 可以发布 `InterfaceDesc + { self, vtable }`。

而不是拆成 executor_submit / executor_cancel / executor_destroy 三个 FunctionDesc 再拼回对象。

所以 Plugin runtime 支持两种 representation：

| Capability shape | Representation |
|---|---|
| Service / Function | FunctionDesc + exact adapter |
| Provider / Interface | InterfaceDesc + `{self,vtable}` |

它们共享 loader、registry、lease 和 quiescent unload，但不共享 semantic shape。

---

## 18. WASM 证明 Contract 不等于 Native ABI

同一个：

~~~text
component UserModule {
    service UserService;
}
~~~

选择：

~~~cmake
PROJECTIONS
    WASM
~~~

WASM backend 不能把 `UserRepository*`、`User*` 或 native vtable pointer 直接暴露到 guest boundary。

它必须 lowering：

~~~text
DataBind data
    ↓
portable ABI representation
    ↓
host/guest adapter
    ↓
WASM import/export
~~~

如果 ownership 无法安全表示，就直接 generation fail，而不是让 runtime 猜。

这说明：

> **IDL contract 的抽象层次必须高于任何一个 native ABI。**

## 19. 一个 CMake 入口选择所有 backend

不要：

~~~cmake
databind_http(...)
databind_rpc(...)
databind_plugin(...)
databind_wasm(...)
~~~

统一：

~~~cmake
databind_target(
    TARGET users
    IDL users.dbidl
    SOURCES users.c

    PROJECTIONS
        NATIVE
        HTTP
        RPC
        PLUGIN
        WASM
        OPENAPI
        MOCK
)
~~~

compiler pipeline：

~~~text
parse IDL once
    ↓
Canonical Contract IR
    ↓
bind CMeta once
    ↓
Native BindingPlan
    ↓
selected backends
    ├── HTTP
    ├── RPC
    ├── Plugin
    ├── WASM
    ├── OpenAPI
    └── Mock
~~~

不是每个 backend 再发明自己的 frontend。

## 20. 一个明确失败例：request 与 native 参数不兼容

IDL：

~~~text
message GetUserRequest {
    uint64 id;
}
~~~

native function：

~~~c
int get_user(
    UserRepository *repo,
    const char *id,
    User *out);
~~~

如果没有显式 conversion：

~~~text
uint64 -> const char *
~~~

compiler 必须失败：

~~~text
error:
UserService.GetUser
  request field: id : uint64
  native param:   id : const char *
  no admitted conversion
~~~

不能在运行时偷偷 `atoi`、隐式 reinterpret 或 fallback to string。这就是 compiler-driven design 的价值。

## 21. Failure atomicity 也应该成为明确 contract

假设 ingress 已经构造部分 native state，然后字段 3 转换失败。

我们希望：

~~~text
compile/execute binding fails
        ↓
destination is not partially published
~~~

可以写成：

~~~text
bind(input, dst) = error
────────────────────────
observable(dst_after) = observable(dst_before)
~~~

实现可能使用：

~~~text
temporary storage
    ↓
validate all
    ↓
commit
~~~

而不是边解析边修改业务对象。

## 22. 哪些地方值得形式证明

IDL parser 正常解析一个字段，不值得因此引入 Lean。

更值得 formalize 的是：

### Projection preservation

如果 backend 声称保持 logical operation：

~~~text
exec_HTTP(P_HTTP(op), req)
=
exec_Logical(op, decode_HTTP(req))
~~~

至少要说明 observable relation。

### Binding refinement

generated exact adapter 应该 refinement native binding plan：

~~~text
adapter_result
~
logical_service_result
~~~

### Transactional law

~~~text
failure before commit
    -> no observable partial output
~~~

是否进入 Lean，取决于风险和复用程度。

先写清 rule，再决定 machine-check。

## 23. 三种 IR 在这里第一次真正汇合

现在可以看到：

~~~text
DataBind Contract IR
    UserService.GetUser
    Request -> Response

CMeta Native Semantic IR
    get_user
    params / direction / ownership

CFlow Execution IR
    optional admitted execution graph
~~~

关系：

~~~text
Contract IR
    +
Native Semantic IR
    ↓
BindingPlan / exact adapter
    ↓
optional Execution IR
~~~

三个 IR 不能合并成一个“大一统 descriptor”。

因为它们回答三个不同问题。

## 24. Runtime 最后到底剩下什么

最理想的请求路径不是：

~~~text
request
    ↓
reflection
    ↓
schema lookup
    ↓
dynamic invocation
~~~

而是：

~~~text
request
    ↓
precompiled MethodPlan
    ↓
exact C adapter
    ↓
response
~~~

Plugin：

~~~text
lookup once / acquire lease
    ↓
pre-resolved capability
    ↓
exact call
~~~

WASM：

~~~text
generated host adapter
    ↓
defined guest ABI
~~~

这再次回到全书的核心：

> **Know more before execution; do less during execution.**

## 25. Evidence：怎样证明这不是架构图

至少需要下面这些真实 gate。

### IDL/codegen

~~~text
valid IDL -> generated C compiles
invalid IDL -> deterministic diagnostic
~~~

### Native binding

~~~text
Service + FunctionDesc compatible -> plan
incompatible -> generation fails
~~~

### HTTP

~~~text
generated MethodPlan
-> real CHttp::Server
-> request/response integration test
~~~

### RPC

~~~text
typed client
-> CRPC
-> typed server
-> round trip
~~~

### Plugin

~~~text
installed shared library
-> load
-> acquire
-> call
-> quiescent unload
~~~

### WASM

~~~text
host
-> generated adapter
-> .wasm
-> response
~~~

### Cross-TU / DSO identity

~~~text
descriptor address differs
semantic contract still matches
~~~

这些证据分别验证不同 claim。

## 26. 本章最后得到的不是“一个更大的框架”

我们没有得到“HTTP owns Service / RPC owns Service / Plugin owns Function metadata / WASM owns another IDL”，而是：

~~~text
DataBind
    logical contract

CMeta
    native semantics

databindc
    binding + projections

CHttp / CRPC / Plugin / WASM
    runtime consumers

CFlow
    optional execution IR
~~~

减少的是 **duplicated stable knowledge**，不是 ordinary C implementation。

## 27. What We Learned

从一个普通函数：

~~~c
int get_user(UserRepository *, uint64_t, User *);
~~~

我们没有直接跳到“大型 Service Framework”。

我们先发现 HTTP、RPC、Plugin、OpenAPI、Mock、WASM 都在重复描述同一个 logical operation，于是增加最小 Contract IR：message、service、channel、component。

CMeta 继续保留 FunctionDesc 这份 native truth。Compiler 负责 bind、validate、generate exact adapter 和 compile projection；runtime 最终只执行 immutable plan + ordinary C。

> **当 Source 不能总是立即给出值时，Execution IR 怎样增加 WAIT / Wake / Demand，而不复制 Graph semantics？**
