# 第十四章：有限、显式、按需——什么时候应该停止 Meta 化

> **这一章不再列十条抽象原则，然后逐条解释。**
>
> 它只问一个问题：**这个 abstraction 删除的稳定知识重复，是否大于它引入的长期成本？**
>
> 如果答案是否定的，就继续写普通 C。

---

## 1. Decision Tree：先问是否真的需要抽象

~~~text
problem appears
    |
    v
Can ordinary C express it clearly?
    |
   yes
    |
    v
Is stable knowledge duplicated across modules/backends?
    |
   no -----------------> keep ordinary C
    |
   yes
    |
    v
Can the knowledge be made finite/explicit/bounded?
    |
   no -----------------> keep local/manual design
    |
   yes
    |
    v
Does a shared IR remove real maintenance or correctness risk?
    |
   no -----------------> keep ordinary C
    |
   yes
    |
    v
introduce the smallest semantic object
~~~

抽象不是默认答案。

---

## 2. Case A：一个固定 Pipeline，不需要 Graph

需求：

~~~c
size_t copy_even_squares(
    const int *xs,
    size_t n,
    long *out)
{
    size_t m = 0;

    for (size_t i = 0; i < n; ++i) {
        int x = xs[i];

        if ((x & 1) != 0)
            continue;

        out[m++] = (long)x * x;
    }

    return m;
}
~~~

如果只有 one pipeline、one call site，没有 dynamic composition、rewrite 或 alternate execution backend，那么 **Graph cost > shared knowledge removed**。结论就是：**keep the loop**。

只有当需求变成 dozens of pipelines、shared operators、type propagation、optimizer 或 multiple backends 时，才升级到 Graph。

---

## 3. Case B：一个 Callback，不需要 Callable Object

~~~c
typedef void (*done_fn)(void *user);

void request_start(done_fn done, void *user);
~~~

如果 callback 不跨复杂 lifetime 保存、不组合、不反射、也不优化，这个 API 已经足够。

不要为了“typed callback”立刻增加 signature registry、capture object、effects metadata 和 generic dispatcher。

只有当多个模块真的需要共享函数语义时，才引入 FunctionDesc/Callable。

---

## 4. Case C：一个内部函数，不需要 IDL

~~~c
static int
lookup_user(UserRepository *repo, uint64_t id, User *out);
~~~

如果它只在一个 binary 内被直接调用，没有 HTTP、RPC、Plugin、WASM、generated Mock 或 external contract，就不需要 message、service、component 或 `databindc`。IDL 的价值来自 **same logical contract repeated across backends**，不是来自“函数存在”。

---

## 5. Case D：一个实现，不需要 Plugin

如果只有 one implementation、link time 已知、不会 unload、也不需要 dynamic discovery，直接链接：

~~~cmake
target_link_libraries(app PRIVATE image_codec)
~~~

比引入 loader、registry、manifest、lease 和 quiescent unload 更简单。

只有真正需要 dynamic discovery、replaceable implementation、cross-DSO capability 或 safe unload 时，才选择 PLUGIN projection。

---

## 6. Cost Table：每个 abstraction 都要付什么

| Abstraction | 删除什么重复 | 新增什么长期成本 |
|---|---|---|
| Generic | repeated type instantiation facts | generated API / compiler diagnostics |
| FunctionDesc | repeated native function metadata | descriptor ABI / ownership rules |
| Graph | repeated composition/analysis logic | IR + optimizer + qualification |
| DataBind IDL | repeated logical contracts | compiler + versioning + codegen |
| Plugin | dynamic capability publication | loader/lease/unload ABI |
| WASM | portable component ABI | host/guest lowering + runtime boundary |
| Actor | concurrency admission/lifecycle | mailbox/ref/generation protocol |

如果右边长期成本明显大于左边删除的重复，停止抽象。

---

## 7. Hidden Runtime Budget

任何“方便”功能都必须列出隐藏成本。

例如 oversized lambda capture：

错误方向：

~~~text
capture too large
    ↓
secret malloc
    ↓
still reports success
~~~

更好的 contract：

~~~text
capture <= inline_capacity
    -> OK

capture > inline_capacity
    -> TOO_LARGE
~~~

或者调用方显式提供 owner：

~~~c
owned_capture *cap = owned_capture_create(...);

callable_bind_owned(&fn, cap);
~~~

成本不能因为 API 更漂亮就消失。

---

## 8. Evidence Budget

一个 abstraction 进入 core 前，至少写出它需要的新 gate：

~~~text
new generated syntax
    -> compile tests

new identity rule
    -> Multi-TU / DSO tests

new lifecycle
    -> sanitizer/stress

new rewrite
    -> semantic theorem

new performance claim
    -> benchmark

new projection backend
    -> installed integration
~~~

如果维护这些 gate 的价值都无法解释，通常 abstraction 也还不值得进入 core。

## 9. Counterexample Lab：十种“看起来高级，实际上更差”的设计

下面这些反例都不是为了制造稻草人。

它们都很常见，而且在早期通常看起来“更统一、更智能、更自动”。

真正的问题只有在系统变大以后才会暴露。

---

## 9.1 Counterexample 1：只有一次重复，也立刻造 Meta DSL

假设只有：

~~~c
int user_age(const User *u) {
    return u->age;
}

int order_count(const Order *o) {
    return o->count;
}
~~~

看到形状相似，就立刻设计 `FieldGetter(...)`、`GenerateAccessor(...)`、`Reflect(...)`、`GenericInvoke(...)`。

表面收益只是“少写两行函数”；实际成本却是新的 macro vocabulary、错误信息、naming convention、compile-time dependency 和 debugging path。而且 `User.age` 与 `Order.count` 可能只是偶然相似。

### 为什么错

你抽象的不是**稳定知识**，而是**当前代码形状**。

这违反：

> **Code First, Meta Later.**

### 最小修正

继续写普通 C。

直到出现大量稳定字段 schema、多个消费者重复读取同一字段事实，而且 serializer / binder / UI / query 都需要同一信息，再把 **Field Metadata** 抽成真正共享事实。

---

## 9.2 Counterexample 2：为了“像 Template”追求无限类型推导

假设最初只需要 `CommonType(int, long) = long` 和 `CommonType(int, double) = double`。

但很快会产生诱惑：既然叫 TypeFunction，为什么不能支持任意嵌套、任意递归、任意偏特化？于是开始用 preprocessor 模拟 template partial specialization、SFINAE、recursive pattern matching 和 higher-kinded generic。

### 为什么一开始看起来合理

因为 C++ Template 很强，所以很容易把目标错误地改成“C 也应该一样强”。

### 真正问题

C preprocessor 并不是为开放递归类型计算设计的。

结果往往是错误爆炸、compile time 不可预测、compiler divergence、debugging 极差、规则边界没人说得清，formal model 反而更困难。

### 最小修正

把问题重新写成 **finite admitted universe + finite relation rows + explicit unsupported case**。也就是说，**TypeFunction = finite relation**，不是 secret general-purpose compiler。

这正是为什么 No Default 很重要。

未知输入就失败。

---

## 9.3 Counterexample 3：Descriptor Pointer 当 Type Identity

最简单的实现：

~~~c
if (a == b) {
    /* same type */
}
~~~

单 TU 完美工作。

甚至 test 也可能全绿。

直到 TU A、TU B、shared library A/B，或者同一个 static archive 被复制进多个 DSO。同一个 `Pair<int, long>` 可能拥有多个 descriptor object。

于是：

~~~text
pointer differs
    ↓
“type mismatch”
~~~

### 为什么错

地址回答的是“representation object 在哪里”，不是“semantic type 是什么”。

### 最小修正

使用 stable atom id、generic constructor identity、structural arguments 和 pointer/const/application form 建立 semantic identity。如果两个 descriptor 地址不同但 structure/meaning 相同，就应该相等。

这不是 abstraction bonus。

这是 Multi-TU correctness。

---

## 9.4 Counterexample 4：Lambda Capture 超过 Inline Bound 就偷偷 malloc

设计一个带 `inline capture[32]` 的 callable 很好。

然后遇到 80-byte capture。

最“方便”的做法：

~~~text
if too large:
    malloc(...)
    hide pointer inside callable
~~~

用户 API 完全不变。

### 为什么看起来合理

因为用户看起来获得了“任何 capture 都能用”。

### 真正问题

API 原本暗示 bounded value object、copy by value、no hidden allocation、predictable lifetime；现在却悄悄变成 some callables allocate、copy may fail、destroy becomes mandatory、thread/lifetime semantics changed、ABI shape meaning changed，而调用点不知道。

### 最小修正

三种合法选择是：A. compile/admission failure；B. explicit heap-backed callable type；C. caller-owned external context。选择哪一种都可以，但必须 explicit。

> **Hidden convenience that changes ownership is not convenience. It is semantic drift.**

---

## 9.5 Counterexample 5：Actor / Executor Queue 自动无限增长

需求是“send should almost never fail”，于是实现：

~~~text
queue full
    ↓
realloc bigger
    ↓
keep accepting
~~~

甚至直接使用 linked-list unbounded queue。

### 为什么看起来合理

上层不用处理 FULL。

demo 非常顺滑。

### 生产环境会发生什么

当 consumer 变慢并出现 producer rate > consumer rate 时，系统不会 backpressure，只会 memory rises、latency rises、cache locality collapses、event becomes stale，最终 OOM。

问题从“明确返回 FULL”被变成“很晚才发生的全局 failure”。

### 最小修正

固定 capacity。

返回 `FULL`，让上层显式选择 retry later、drop by explicit policy、backpressure upstream、fail operation 或 shed load。

> **Boundedness turns resource pressure into information.**

---

## 9.6 Counterexample 6：Parallel Plan 不可用时 Silent Sequential Fallback

用户显式请求 parallel reduce，但当前输入太小、Executor 满、reducer contract 不满足或 plan 不支持。框架如果擅自说“没关系，我帮你顺序执行，结果一样”，就隐藏了真实的 execution contract。

### 为什么看起来合理

功能似乎“更鲁棒”。

### 为什么实际上危险

虽然结果可能相同，但 latency、CPU topology、resource usage、deadline behavior、load shedding、SLA 和 benchmark 都变了。更糟的是，一个本应暴露的 admission bug 被隐藏。

### 最小修正

返回明确的 `UNSUPPORTED`、`FULL`、`INVALID_OPTIONS` 或 `INELIGIBLE`。

如果 application 真想 fallback：

~~~text
if parallel failed:
    explicitly choose sequential
~~~

由它自己决定。

> **Semantic equivalence does not imply operational equivalence.**

---

## 9.7 Counterexample 7：Everything Is Virtual

为了“统一”，把所有东西都变成 `{ self, vtable }`，包括 Map、Filter、type operations、small value transform、inner-loop compare 和 Graph node execution，于是每个 value 都要付出 vtable lookup、indirect call、metadata check 和 dynamic dispatch。

### 为什么一开始看起来漂亮

表面上获得了“one interface to rule them all”，增加新类型也不用改调用者。

### 真正问题

你把真正需要动态性的 boundary 和编译/构造时已经知道的 interior 混在一起。

结果是 optimizer knowledge 无法消除、hot path 始终保留动态层、debugging stack 膨胀，并失去 cache/inlining opportunities。

### 最小修正

保持明确分层：

| 区域 | 例子 |
|---|---|
| Dynamic Boundary | Publisher / Scheduler / plugin provider |
| Static Interior | known Graph stage / Plan instruction / direct target |

动态性只留在真正动态的边界。

> **Interface is a boundary tool, not a universal object model.**

---

## 9.8 Counterexample 8：把 Raw Parser Token 当 Business Stream

有 JSON parser 输出 `OBJECT_BEGIN`、`KEY`、`STRING`、`ARRAY_BEGIN` 等 token，又已经有 CFlow Stream。

于是自然想到：

~~~text
Stream<Token>
    .filter(...)
    .map(...)
~~~

### 为什么看起来合理

都是“流”。

### 真正问题

token sequence 不是独立 business values，而是 grammar-preserving structural protocol。如果业务 filter 掉 `ARRAY_END`，整个语法失效；此时 field name、number、container boundary 也仍未形成 semantic object。

### 最小修正

正确边界：

~~~text
parser syntax
    ↓
canonical grammar
    ↓
binding / validation
    ↓
complete semantic/native value
    ↓
business CFlow
~~~

> **Same shape “stream of items” does not mean same semantics.**

---

## 9.9 Counterexample 9：为了“形式化”让 Lean 证明 ABI / Benchmark

团队有了 Lean 后，很容易产生新的形式主义：能不能证明 struct ABI stable？能不能证明这个版本快 2x？能不能证明 Linux scheduler 不饿死？

### 为什么错

这些问题依赖 compiler ABI、linker/loader、platform、CPU、OS、allocator、benchmark workload 和 external environment。如果 formal model 没有精确包含这些现实事实，证明的只是**一个抽象模型**，不是实际工具链。

### 最小修正

不同问题使用不同证据：

| Claim | Evidence |
|---|---|
| semantic identity / rewrite preservation / state-machine invariant / bounded protocol relation / refinement | Lean / formal proof |
| ABI / link / install / compiler compatibility | toolchain evidence |
| actual performance | benchmark |
| memory / race bugs | stress + sanitizer |

> **Using proof at the wrong layer is another form of hidden assumption.**

---

## 9.10 Counterexample 10：因为“上层需要”就把 Domain Semantics 塞进 Core

例如 RPC 需要 retry、deadline、service discovery，于是有人想把 retry policy 塞进 Executor；Workflow 需要 compensation，于是把 compensation 塞进 Machine core；JSON 需要 field names，于是把 JSON syntax 塞进 CMeta。

### 为什么错

Core 开始失去 **single semantic ownership**。一个 primitive 同时服务太多 domain，最后只能拥有模糊的“万能”参数。

### 最小修正

问三个问题：

- 这是不是该 domain 独有的 meaning？
- 是否在至少多个独立领域稳定重复？
- 没有它 core 是否仍完整？

如果答案是 domain-specific，就留在上层。

> **Reuse does not require ownership transfer.**

---

## 10. “普通 C 更好”不是失败，而是设计成功

一本讲 Modern C 的书如果最后让读者觉得“每个问题都应该用 CMeta/CFlow”，那就是错误结论。

有大量场景普通 C 明显更好。

## 10.1 一个固定 pipeline

如果只有：

~~~c
for (...) {
    if (...) {
        ...
    }
}
~~~

不会动态组合、不需要复用 Graph、不需要分析/优化：

> 直接写 loop。

## 10.2 一个小状态机

如果只有 3 states、4 events、one file、no dynamic binding、no concurrency，一个 switch 可能比 Machine IR 更好。

## 10.3 一个 callback

如果不需要 capture、signature registry、Graph 或 semantic optimization，就直接：

~~~c
void (*fn)(void *);
~~~

## 10.4 一个固定 struct 的 parser

只有一个 format、一个 object、不需要通用 binding：

> 手写 parser 到 struct。

## 10.5 一个简单同步程序

如果不需要 WAIT、Demand、Scheduler 或 Executor，就不要为了“现代”增加异步模型。

### 判断标准

如果 abstraction 没有删除真实重复知识、真实错误边界或真实 runtime decision duplication，它就可能只是新增一层。

---

## 11. Decision Tree：一个新能力是否值得进入 Meta / Core

可以使用下面的顺序判断。

~~~text
Q1. Plain C 是否已经清楚、短、稳定？
    YES → 保持 Plain C
    NO  ↓

Q2. 重复的是“知识”还是只是代码形状？
    code shape only → 暂不抽象
    stable knowledge ↓

Q3. 是否至少有多个独立消费者需要同一事实？
    NO → 留在模块内部
    YES ↓

Q4. 这份知识是否有限、可显式描述？
    NO → 可能是 runtime/domain feature
    YES ↓

Q5. Ownership / failure / capacity 是否能写清？
    NO → 不进入 Core
    YES ↓

Q6. 它属于已有哪个 semantic owner？
    已有 owner → 扩展/复用 owner
    没有 ↓

Q7. 是否在多个 domain 中稳定重复？
    NO → 上层 feature
    YES ↓

Q8. 能否在执行前消费掉大部分复杂度？
    NO → 明确它是 Runtime Feature
    YES ↓

Q9. 是否有正确的 evidence strategy？
    NO → 设计未完成
    YES ↓

Q10. 加入后系统整体更容易理解吗？
    NO → 删除 abstraction
    YES → 才考虑进入 Core
~~~

最后一个问题最重要。

---

## 12. Anti-Meta Budget：Core 每增加一个 Primitive 都应该付出成本

可以把 Core feature 视为有“长期维护预算”。

一个新 primitive 一旦进入 CMeta、CFlow kernel、public ABI、formal model 或 generated manifest，就需要长期承担 documentation、compiler compatibility、ABI、Multi-TU、tests、formal maintenance、debugging、migration 和 downstream compatibility。

所以判断标准不能只是“实现它是否容易”，而应该是：

> **它值得我们未来 5 年继续解释、测试、兼容吗？**

这会自然降低 Core feature 增长速度。

而这正是好事。

---

## 13. Counterexample Review Checklist

代码审查一个新的 Meta/Runtime abstraction 时，可以直接问：

- [ ] 有没有 Plain C baseline？
- [ ] 重复的知识是什么？
- [ ] 为什么不是 module-local helper？
- [ ] 为什么必须进入 Core？
- [ ] type identity 是否跨 TU？
- [ ] ownership 是否显式？
- [ ] 是否有 hidden allocation？
- [ ] resource 是否 bounded？
- [ ] FULL/CLOSED/STALE 是否被保留为信息？
- [ ] 是否有 silent fallback？
- [ ] dynamic dispatch 是否进入不必要的 hot path？
- [ ] failure 是否尽可能提前？
- [ ] theorem 证明的是正确层次的问题吗？
- [ ] ABI/toolchain claim 是否有真实 consumer test？
- [ ] 性能 claim 是否有 fresh measurement？
- [ ] abstraction 最终能否在 hot path 消失？

如果很多项答不上来：

> 不应该继续“完善 abstraction”，而应该先缩小 abstraction。

---

## 14. What We Learned

第十四章真正建立的是：

> **克制本身也是一种系统能力。**

前面的十条纪律现在有了具体失败模式：

| 纪律 | 防止什么 |
|---|---|
| Finite | preprocessor 变成无限语言 |
| Explicit | ownership/policy 偷偷变化 |
| Bounded | backpressure 变成 OOM |
| Fail-fast | 错误距离不断拉长 |
| No Silent Fallback | operational semantics 被偷偷改变 |
| Static When Possible | 已知 interior 保留动态成本 |
| No Hidden Runtime | API 看起来简单、ownership 却变复杂 |
| Cross-Compiler Semantics First | core 绑定偶然 compiler trick |
| Semantic Identity | 地址偶然成为 meaning |
| Module Owns Meaning | Core 变成 domain feature landfill |

但最重要的一条仍然是 **Ordinary C First**。

不是因为普通 C 更“纯”。

而是：

> **抽象的价值必须被真实复杂度证明。**

所以一个成熟的 Modern C 系统最终应该同时拥有两种能力：知道什么时候应该构造 Typed / Verified abstraction，也知道什么时候应该只写一个普通 C function。

下一章作为全文最终总结，不再列 Feature。

我们只保留一套可重复使用的方法：

~~~text
Understand
→ Model
→ Formalize
→ Verify
→ Implement
→ Lower
→ Measure
~~~

并用它回答：

> **什么才是这本书所说的 Modern C？**
